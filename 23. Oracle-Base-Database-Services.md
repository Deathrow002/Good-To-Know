## 1. Service Fundamentals

### Q1. What is Oracle Base Database Service?

**Answer:**

**Oracle Base Database Service (BaseDB)** runs Oracle Database on **DB systems**—virtual machine or bare metal servers in Oracle Cloud Infrastructure. Oracle supplies the infrastructure and lifecycle automation, while you keep DBA-level control of the database and SSH access to the operating system.

#### a. Key Capabilities

| Capability | What OCI provides |
|---|---|
| Provisioning | Creates the DB system, DB home, container database (CDB), and first PDB in one workflow |
| Scaling | Change OCPUs or shape; increase storage |
| Patching | Pre-checks and guided updates for the DB system and the database |
| Backup and recovery | Automatic RMAN backups, point-in-time restore, and on-demand backups |
| High availability | 2-node RAC on VM DB systems and Data Guard across ADs or regions |
| Security | TDE by default, OCI Vault keys, private networking, and NSGs |

#### b. Ways to Manage BaseDB

| Interface | Example use |
|---|---|
| OCI Console | Interactive provisioning, patching, and backups |
| OCI CLI | `oci db system list --compartment-id <compartment-ocid>` |
| SDKs and REST API | Integration with internal tools and portals |
| Terraform / Resource Manager | Repeatable infrastructure as code |
| On-node tools | `dbcli`, SQL*Plus, RMAN, `srvctl` (Grid Infrastructure systems) |

#### c. Typical Use Cases

- Lift-and-shift of on-premises Oracle databases that need OS access or specific patches.
- Development and test environments that must match production versions exactly.
- Packaged applications certified only on specific Oracle Database releases.

**Bottom Line:** BaseDB is Oracle Database on OCI with automation for routine lifecycle tasks, while you keep full control as the DBA.

### Q2. What does "co-managed" mean in BaseDB?

**Answer:**

"Co-managed" means Oracle and the customer **share** operational responsibility. Oracle runs the cloud infrastructure and supplies automation; the customer decides **when and how** to use that automation and remains responsible for everything inside the database.

#### a. Responsibility Matrix

| Area | Owner |
|---|---|
| Data center, hardware, hypervisor, and network fabric | Oracle |
| Lifecycle tooling (patch, backup, and Data Guard automation) | Oracle |
| Scheduling and running patches and upgrades | Customer |
| OS hardening, OS users, and `sudo` access | Customer |
| Database users, schemas, and privileges | Customer |
| Tuning, initialization parameters, and SQL | Customer |
| Network rules, IAM policies, and encryption keys | Customer |
| Backup configuration and restore testing | Customer |

#### b. Comparison With Other Oracle Database Options

| Aspect | Autonomous Database | Base Database Service | Database on Compute |
|---|---|---|---|
| OS access | No | Yes | Yes |
| Patching | Automatic | Customer-initiated with OCI tooling | Fully manual |
| Backups | Automatic | Automatic (configurable) | Manual |
| Tuning | Largely automatic | Customer | Customer |
| Operational effort | Lowest | Medium | Highest |

#### c. Interview Tip

Describe BaseDB as **co-managed, not maintenance-free**. The tooling is provided, but you remain accountable for applying patches, testing restores, and securing access.

**Bottom Line:** Oracle manages the platform and provides automation; you manage the database and decide when automation runs.

### Q3. How do DB system, DB home, CDB, and PDB relate?

**Answer:**

BaseDB separates **infrastructure**, **software**, and **data** into layers so that each lifecycle operation targets the right level. For example, you patch a DB home, back up a database, and clone a PDB.

#### a. Hierarchy

```text
DB system (compute + storage + network)
└── DB home (Oracle software at a specific release and patch level, e.g., 19.21)
    └── Container database (CDB)
        ├── CDB$ROOT   (Oracle metadata and common users)
        ├── PDB$SEED   (template for new PDBs)
        ├── SALESPDB   (application A)
        └── HRPDB      (application B)
```

#### b. Component Summary

| Component | Description | Typical operations |
|---|---|---|
| DB system | Shape, storage, VNICs, and Grid Infrastructure or LVM | Scale, start or stop nodes, update GI and OS |
| DB home | Oracle Database software installation | Create, patch, delete |
| CDB | Instance, redo, undo, and memory structures | Back up, restore, configure Data Guard, move between homes |
| PDB | Application schemas and data | Create, clone, relocate, open, close |

Bare metal DB systems can host multiple DB homes and databases. VM DB systems are generally limited to a single database, which can still contain multiple PDBs.

#### c. Useful SQL*Plus Commands

```sql
SHOW CON_NAME
SHOW PDBS
ALTER SESSION SET CONTAINER = SALESPDB;
SELECT name, open_mode, restricted FROM v$pdbs;
```

**Bottom Line:** DB system = infrastructure, DB home = software, CDB = database instance, PDB = application data.

### Q4. Compare VM and bare metal DB systems.

**Answer:**

The DB system type determines resource isolation, storage technology, scaling behavior, and high-availability options. Most new deployments use **VM DB systems** because of flexible shapes and RAC support.

#### a. Comparison

| Aspect | VM DB system | Bare metal DB system |
|---|---|---|
| Compute | Flexible shapes such as `VM.Standard.E4.Flex` | Entire physical server |
| Storage | OCI Block Volumes (network-attached) | Local NVMe drives |
| Compute scaling | Change OCPUs or shape (node restart) | Enable or disable CPU cores, typically online |
| Storage scaling | Increase online | Fixed by local disk capacity |
| RAC | Supported as 2-node RAC | Single node only |
| Multiple DB homes | Limited | Supported |
| Provisioning speed | Fast (especially with LVM) | Slower |

#### b. When to Choose Each

| Choose VM when you need | Choose bare metal when you need |
|---|---|
| RAC for node-level high availability | Dedicated hardware with no virtualization layer |
| Flexible OCPU and storage scaling | Very high local NVMe I/O |
| Fast provisioning for dev/test | Consolidation of many databases and homes |

**Bottom Line:** VM DB systems offer flexibility and RAC; bare metal offers dedicated hardware and local NVMe performance.

### Q5. What is the difference between LVM and ASM storage management?

**Answer:**

When you create a VM DB system, you choose how database storage is managed. This choice **cannot be changed later**, so it must match your availability requirements.

#### a. Comparison

| Feature | Logical Volume Manager (LVM) | Automatic Storage Management (ASM) |
|---|---|---|
| Software stack | Linux LVM file systems; no Grid Infrastructure | Grid Infrastructure with ASM |
| Provisioning time | Faster | Longer |
| Node count | Single node only | Single node or 2-node RAC |
| Database file location | Linux file systems | ASM disk groups (such as DATA and RECO) |
| Service management | `DBMS_SERVICE`, `dbcli` | `srvctl` and Oracle Clusterware |
| Changeable later? | No | No |

#### b. How to Identify the Storage Type on a Node

```bash
# ASM-based systems run Grid Infrastructure processes
ps -ef | grep -i asm_pmon
sudo su - grid -c "asmcmd lsdg"

# LVM-based systems expose logical volumes
sudo lvs
```

#### c. Decision Guidance

- Choose **ASM** for RAC, Clusterware-managed services, or alignment with on-premises GI standards.
- Choose **LVM** for fast provisioning of single-instance development, test, or small production databases.

**Bottom Line:** LVM is faster to provision for single-node systems; ASM is required for RAC and Clusterware features.

### Q6. Which database editions does BaseDB offer?

**Answer:**

BaseDB offers four editions. Each higher edition **adds** options and management packs to the previous one, and the edition is fixed after provisioning.

#### a. Edition Feature Map

| Edition | Adds (compared with the previous edition) |
|---|---|
| Standard Edition | Core database features; TDE is included on OCI |
| Enterprise Edition | Enterprise features plus Data Masking and Subsetting, Diagnostics and Tuning Packs, and Real Application Testing |
| Enterprise Edition High Performance | Multitenant, Partitioning, Advanced Compression, Advanced Security, Label Security, Database Vault, OLAP, Spatial and Graph, and management packs |
| Enterprise Edition Extreme Performance | RAC, Database In-Memory, and Active Data Guard |

#### b. Minimum Edition by Requirement

| Requirement | Minimum edition (License Included) |
|---|---|
| Physical standby with Data Guard | Enterprise Edition |
| Partitioning | Enterprise Edition High Performance |
| More than three user-created PDBs per CDB (19c and later) | Enterprise Edition High Performance |
| RAC, Active Data Guard, or In-Memory | Enterprise Edition Extreme Performance |

With BYOL, entitlement depends on the licenses and options you own.

#### c. Check Feature Usage

```sql
SELECT name, currently_used, detected_usages
FROM dba_feature_usage_statistics
WHERE currently_used = 'TRUE'
ORDER BY name;
```

**Bottom Line:** Choose the edition from required features—RAC and Active Data Guard require Extreme Performance—because you cannot change it later.

### Q7. What is the difference between License Included and BYOL?

**Answer:**

OCI offers two license models. **License Included** bundles the Oracle Database license into the hourly price. **Bring Your Own License (BYOL)** uses existing licenses and charges a lower infrastructure rate.

#### a. Comparison

| Aspect | License Included | BYOL |
|---|---|---|
| Price | Infrastructure plus license per OCPU-hour | Lower, infrastructure-focused rate |
| Compliance responsibility | Covered by the subscription | Customer must hold sufficient entitlements |
| Options available | All options of the selected edition | Only options you are licensed for |
| Best for | No existing licenses, short-term projects | Organizations with licenses under active support |

#### b. Key Considerations

1. **Conversion rules:** Oracle's BYOL policy defines how processor licenses map to OCPUs—validate with your licensing team.
2. **Option usage:** With BYOL, using an unlicensed option (for example, Partitioning) creates compliance risk. Review `DBA_FEATURE_USAGE_STATISTICS` regularly.
3. **Flexibility:** The license model can be updated after provisioning, unlike the edition.

**Bottom Line:** License Included buys simplicity; BYOL reduces cost when you already own licenses but makes you responsible for compliance.

### Q8. When would you choose BaseDB instead of Autonomous Database?

**Answer:**

Both run Oracle Database, but they target different operating models. **Autonomous Database** automates most DBA work; **BaseDB** preserves control for workloads that need it.

#### a. Comparison

| Aspect | Base Database Service | Autonomous Database |
|---|---|---|
| OS access | Yes (SSH) | No |
| Version and patch level | You choose, including one-off patches | Managed by Oracle |
| Initialization parameters | Fully configurable | Restricted |
| Third-party agents | Allowed on the node | Not allowed |
| Scaling | Manual OCPU and storage scaling | Online scaling, including CPU auto scaling |
| Tuning | DBA-driven | Automatic indexing and tuning features |
| High availability | Configure RAC and Data Guard yourself | Built-in options such as Autonomous Data Guard |

#### b. Decision Checklist

Choose **BaseDB** if any of these apply:

- The application vendor certifies only specific database versions or patch levels.
- You need OS access, custom agents, or non-default parameters.
- You are migrating an on-premises database with minimal change.

Choose **Autonomous Database** when automation, elastic scaling, and minimal administration are the priority.

**Bottom Line:** Choose BaseDB for control and compatibility; choose Autonomous Database for automation and reduced operations.

## 2. Networking and Provisioning

### Q9. Why should a DB system be placed in a private subnet?

**Answer:**

A **private subnet** prohibits public IP addresses, so the database cannot be reached directly from the internet. All access must come through controlled private paths, which greatly reduces the attack surface.

#### a. Reference Architecture

```text
On-premises ──(VPN / FastConnect)──> DRG ──┐
                                           ▼
VCN 10.0.0.0/16
├── Public subnet  10.0.0.0/24 : Load balancer (optional)
├── App subnet     10.0.1.0/24 : Application servers ──TCP 1521──┐
├── DB subnet      10.0.2.0/24 : DB system (no public IP)  <─────┘
└── OCI Bastion (managed)      : SSH port forwarding ──TCP 22──> DB subnet

Gateways: Service gateway (backups, patches) | NAT gateway (optional outbound)
```

#### b. Access Paths

| Who | Path | Port |
|---|---|---|
| Application servers | Private IP or hostname in the same or a peered VCN | 1521 (or 2484 for TLS) |
| DBAs | OCI Bastion port-forwarding session | 22 |
| On-premises clients | DRG through VPN or FastConnect | 1521 |
| DB system to Object Storage | Service gateway | 443 |

#### c. Best Practices

1. Never assign public IPs to DB nodes.
2. Enforce private placement with **Security Zones** where required.
3. Use **NSGs** that reference application NSGs rather than broad CIDR ranges.

**Bottom Line:** A private subnet removes direct internet exposure and forces every connection through controlled, auditable paths.

### Q10. Which networking components does BaseDB require?

**Answer:**

BaseDB needs a correctly prepared VCN before provisioning. Missing DNS labels, routes, or gateway access are common causes of failed provisioning, backups, and patching.

#### a. Required Components

| Component | Purpose | BaseDB notes |
|---|---|---|
| VCN with DNS label | Private network | DNS hostnames are required for DB nodes |
| Regional private subnet with DNS label | Hosts DB nodes | Size for node IPs, and for RAC, VIPs and SCAN IPs |
| Route table | Directs outbound traffic | Route to the Oracle Services Network through the service gateway |
| NSGs or security lists | Virtual firewall | Allow 1521 from apps and 22 from Bastion |
| Service gateway | Private access to OCI services | Required for backups to Object Storage and patch downloads |
| NAT gateway | Outbound internet | Optional, for external repositories or endpoints |
| DRG | Hybrid and cross-region connectivity | Needed for on-premises access and cross-region Data Guard |

#### b. Example Route Table for the DB Subnet

| Destination | Target |
|---|---|
| All `<region>` Services in Oracle Services Network | Service gateway |
| `0.0.0.0/0` | NAT gateway (optional) |
| On-premises CIDR (for example, `172.16.0.0/12`) | DRG |

#### c. Subnet Planning Rules

- OCI reserves the first two and the last IP address in every subnet.
- Do not use a CIDR that overlaps `192.168.16.16/28`, which is reserved for the Oracle Clusterware private interconnect.
- Leave room for growth, such as a Data Guard peer or future RAC nodes.

**Bottom Line:** Prepare a DNS-enabled VCN, a private subnet, a service gateway route, and least-privilege security rules before provisioning.

### Q11. Which ports must be allowed?

**Answer:**

Open only the ports each tier needs, and restrict sources to specific NSGs or subnets. The listener port and SSH are the minimum; RAC and TLS add more.

#### a. Port Reference

| Port | Protocol | Source | Purpose |
|---|---|---|---|
| 22 | TCP | Bastion or admin subnet | SSH to DB nodes |
| 1521 | TCP | Application subnets, Data Guard peer | Oracle Net listener (SCAN and VIP listeners in RAC) |
| 2484 | TCPS | Application subnets | TLS listener, if configured |
| 6200 | TCP | Application subnets (RAC clients) | Oracle Notification Service for FAN events |
| 5500 | HTTPS | Admin subnet | EM Express (optional) |

#### b. Example NSG Rule (CLI)

```bash
oci network nsg rules add --nsg-id <db-nsg-ocid> --security-rules '[{
  "direction": "INGRESS",
  "protocol": "6",
  "sourceType": "NETWORK_SECURITY_GROUP",
  "source": "<app-nsg-ocid>",
  "isStateless": false,
  "tcpOptions": {"destinationPortRange": {"min": 1521, "max": 1521}}
}]'
```

#### c. Best Practices

1. Reference **NSGs** as sources so rules follow workloads when IPs change.
2. Never allow `0.0.0.0/0` on 1521 or 22.
3. Add bidirectional rules between primary and standby VCNs for Data Guard.

**Bottom Line:** Allow 1521 only from application tiers and 22 only from Bastion, and add RAC or TLS ports only when needed.

### Q12. Why is DNS important for BaseDB?

**Answer:**

Oracle Clusterware, listeners, Data Guard, and clients identify database nodes by **hostname**. If names do not resolve consistently, provisioning, RAC, Data Guard, and client connections can fail.

#### a. How OCI Builds Host Names

```text
<hostname>.<subnet-dns-label>.<vcn-dns-label>.oraclevcn.com

Example node:     proddb1.dbsubnet.prodvcn.oraclevcn.com
Example RAC SCAN: proddb-scan.dbsubnet.prodvcn.oraclevcn.com
```

#### b. Hybrid DNS With the OCI Private Resolver

| Direction | Mechanism |
|---|---|
| On-premises clients resolving OCI database names | Resolver **listening endpoint** in the VCN |
| DB nodes resolving on-premises names | Resolver **forwarding endpoint** with forwarding rules |

#### c. Verification and Common Problems

```bash
nslookup proddb1.dbsubnet.prodvcn.oraclevcn.com
nslookup 10.0.2.15        # reverse lookup
```

| Problem | Effect |
|---|---|
| VCN or subnet created without a DNS label | Provisioning fails or hostnames are unavailable |
| Custom DNS servers that cannot resolve OCI names | Cluster and listener errors |
| Missing reverse lookup | Slow connections and Clusterware warnings |

**Bottom Line:** Enable DNS labels, verify forward and reverse resolution, and plan hybrid resolution before provisioning.

### Q13. What decisions must be made before provisioning?

**Answer:**

Several provisioning choices are **permanent**. Understanding which ones can change later prevents costly rebuilds.

#### a. Decision Matrix

| Decision | Options | Can it change later? |
|---|---|---|
| Region and AD | Any region or AD with capacity | No (use Data Guard to move) |
| Subnet | Private regional subnet | No |
| DB system type | VM or bare metal | No |
| Shape and OCPUs | Flexible VM shapes or bare metal core count | Yes |
| Storage size | Initial data storage | Increase only |
| Storage management | LVM or ASM | No |
| Node count | 1, or 2 for RAC (ASM only) | No |
| Edition | SE, EE, EE-HP, EE-EP | No |
| License model | License Included or BYOL | Yes |
| Database name | Up to 8 alphanumeric characters | No |
| Backups | Destination, retention, and window | Yes |
| Key management | Oracle-managed or OCI Vault | Can switch to customer-managed keys |
| NSGs and SSH keys | Lists | Yes |

#### b. Pre-Provisioning Checklist

1. Service limits and quotas for the shape and storage.
2. IAM permissions for database, network, and Vault resources.
3. VCN, subnet, DNS labels, route tables, and NSGs.
4. SSH key pair stored securely.
5. Admin password and TDE wallet password stored in a vault.
6. Backup policy agreed with RPO and RTO owners.

**Bottom Line:** Decide permanent attributes—edition, storage management, node count, subnet, and DB name—correctly the first time.

### Q14. What is the purpose of `DB_UNIQUE_NAME`?

**Answer:**

`DB_NAME` identifies the database, while `DB_UNIQUE_NAME` identifies **each copy** of it. In a Data Guard configuration, the primary and standby share `DB_NAME` but must have different `DB_UNIQUE_NAME` values.

#### a. Example

| Database | `DB_NAME` | `DB_UNIQUE_NAME` | Role |
|---|---|---|---|
| Phoenix copy | `SALES` | `SALES_PHX` | Primary |
| Ashburn copy | `SALES` | `SALES_IAD` | Physical standby |

`DB_NAME` is limited to 8 characters. OCI generates a unique-name suffix automatically unless you specify one in the advanced options.

#### b. Where It Is Used

- Data Guard configuration (`LOG_ARCHIVE_CONFIG`) and broker member names.
- Directory paths for the fast recovery area and TDE wallets.
- `srvctl` commands (`srvctl status database -db SALES_PHX`).
- Backup destinations and monitoring targets.

#### c. Check the Values

```sql
SELECT name, db_unique_name, database_role, open_mode FROM v$database;
```

**Bottom Line:** `DB_UNIQUE_NAME` distinguishes the primary from each standby and appears throughout Data Guard, storage paths, and tooling.

### Q15. What are OCI work requests, and why are they useful?

**Answer:**

Most BaseDB operations are **asynchronous**: the API accepts the request and the work continues in the background. A **work request** tracks that background operation from start to finish.

#### a. What a Work Request Shows

| Field | Example |
|---|---|
| Operation type | Create DB system, apply patch, create backup |
| Status | `ACCEPTED`, `IN_PROGRESS`, `SUCCEEDED`, `FAILED`, `CANCELED` |
| Progress | Percent complete and timestamps |
| Errors and logs | Error code and message for failures |

#### b. Resource Lifecycle States

| State | Meaning |
|---|---|
| `PROVISIONING` | Resource is being created |
| `AVAILABLE` | Ready for use |
| `UPDATING` | Change in progress (scaling, patching) |
| `FAILED` | Operation failed—check the work request |
| `TERMINATING` / `TERMINATED` | Being deleted / deleted |

#### c. Where to Find Them

- **Console:** DB system or database details → *Work requests*.
- **CLI and SDK:** Asynchronous calls return an `opc-work-request-id` header that can be polled.
- **Events:** Rules on database lifecycle events can notify operators when operations finish or fail.

**Bottom Line:** Always start troubleshooting from the work request—it records exactly what failed and when.

### Q16. A DB system provisioning fails. What do you check?

**Answer:**

Read the **work request error first**, then match the symptom to the most likely cause. Most failures come from limits, networking, IAM, or invalid input.

#### a. Troubleshooting Table

| Symptom | Likely cause | Fix |
|---|---|---|
| `LimitExceeded` | Service limit or compartment quota reached | Request a limit increase or adjust quotas |
| Capacity error for the shape | No capacity in the selected AD | Try another AD or shape |
| Subnet or IP error | Too few free IPs, or overlap with `192.168.16.16/28` | Use a larger or different subnet |
| Hostname or DNS error | VCN or subnet created without a DNS label | Recreate the subnet with DNS labels |
| `NotAuthorizedOrNotFound` | Missing IAM permissions (for example, on the subnet) | Add `use virtual-network-family` or required policies |
| Invalid SSH key | Wrong key format | Provide an OpenSSH-format public key |
| Name validation error | DB name longer than 8 characters or invalid characters | Correct the name |

#### b. Process

1. Open the failed work request and record the error code.
2. Fix the root cause rather than retrying blindly.
3. Retry provisioning and monitor the new work request.
4. If the error is internal or unclear, open a support request with the work request OCID.

**Bottom Line:** Work request error → root cause → fix → retry; never retry repeatedly without understanding the failure.

## 3. Lifecycle, Scaling, and Patching

### Q17. Which lifecycle operations does BaseDB automate?

**Answer:**

BaseDB exposes common DBA and infrastructure tasks through the Console, CLI, API, and Terraform. Automation reduces manual errors, but **you** decide when each operation runs.

#### a. Operations and Examples

| Operation | Console location | CLI example |
|---|---|---|
| Start, stop, or reboot a node | DB system → Nodes | `oci db node stop --db-node-id <node-ocid>` |
| Change OCPUs | DB system → Change shape | `oci db system update --db-system-id <ocid> --cpu-core-count 8` |
| Scale storage | DB system → Scale storage | `oci db system update --db-system-id <ocid> --data-storage-size-in-gbs 1024` |
| On-demand backup | Database → Backups | `oci db backup create --database-id <db-ocid> --display-name pre-change` |
| Patch the DB system or database | Updates | `oci db system patch ...` / `oci db database patch ...` |
| Manage PDBs | Database → Pluggable databases | Create, clone, start, stop |
| Configure Data Guard | Database → Data Guard | Create, switchover, failover, reinstate |

#### b. Billing Note

For VM DB systems, stopping all nodes generally pauses compute billing while **storage continues to be billed**. Verify current billing rules for your shape and license model.

**Bottom Line:** BaseDB automates infrastructure and database lifecycle operations; you schedule and validate them.

### Q18. How does compute scaling work in BaseDB?

**Answer:**

Compute scaling changes the CPU (and, on flexible shapes, memory) available to the database. The method and impact differ between VM and bare metal DB systems.

#### a. VM Versus Bare Metal

| Aspect | VM DB system | Bare metal DB system |
|---|---|---|
| Method | Change the OCPU count or shape | Enable or disable CPU cores |
| Downtime | Node restart (plan a window; RAC reduces impact) | Typically online |
| Memory | Scales with OCPUs on flexible shapes | Fixed by the server |
| Billing | Per enabled OCPU | Per enabled core |

#### b. Before and After Scaling

**Before:**

1. Confirm the workload is CPU-bound using AWR (high DB CPU and CPU waits).
2. Check licensing (BYOL entitlements) and service limits.
3. Schedule a maintenance window for VM restarts.

**After:**

```sql
SHOW PARAMETER cpu_count
SHOW PARAMETER sga_target
SHOW PARAMETER pga_aggregate_target
```

Review Resource Manager plans and compare response times with the baseline.

#### c. Pitfall

Frequent VM scaling requires restarts, so it is not suited to minute-by-minute elasticity. Workloads that need that elasticity are better served by Autonomous Database.

**Bottom Line:** Scale compute from measured evidence, plan for restarts on VMs, and validate memory parameters afterward.

### Q19. Can database storage be reduced after it is increased?

**Answer:**

No. BaseDB storage scaling is **increase-only**; you cannot shrink provisioned storage in place. Over-provisioning wastes money permanently, so plan growth carefully.

#### a. What Storage Is Used For

| Area | Contents |
|---|---|
| Data (DATA disk group or data file system) | Data files and temp files |
| Recovery (RECO disk group or recovery file system) | Fast recovery area: archived redo, flashback logs, local backups |
| Software volumes | Oracle homes, Grid Infrastructure, logs |

#### b. Check Usage Before Scaling

```sql
SELECT tablespace_name, ROUND(used_percent, 1) AS used_pct
FROM dba_tablespace_usage_metrics
ORDER BY used_percent DESC;
```

```bash
sudo su - grid -c "asmcmd lsdg"   # ASM systems
df -h                             # LVM systems and software volumes
```

#### c. Scale Storage

```bash
oci db system update --db-system-id <db-system-ocid> --data-storage-size-in-gbs 1024
```

Scaling is online. VM DB systems may also offer a storage performance option (Balanced or Higher Performance) where available.

**Bottom Line:** Storage only grows, so size it from trend data and increase it in measured steps.

### Q20. What is the difference between patching and upgrading?

**Answer:**

**Patching** applies fixes within the same major release. **Upgrading** moves the database to a newer major release. Upgrades carry more risk and need more testing and a stronger fallback plan.

#### a. Comparison

| Aspect | Patching | Upgrading |
|---|---|---|
| Example | 19.20 → 19.21 Release Update | 19c → 23ai |
| Content | Security and bug fixes | New features and dictionary changes |
| Frequency | Quarterly (January, April, July, October) | Every few years |
| Downtime | Short; rolling with RAC for eligible patches | Longer outage or a migration approach |
| Fallback | Roll back the patch or move back to the old home | Guaranteed restore point or restore |

#### b. Upgrade Options

| Option | Notes |
|---|---|
| OCI Console upgrade | Guided pre-check and upgrade for supported versions |
| AutoUpgrade | Oracle's recommended upgrade utility |
| Data Pump or GoldenGate to a new DB system | Lower downtime and an easy fallback to the old system |

#### c. Best Practices

1. Create a **guaranteed restore point** before upgrading.
2. Test application compatibility and SQL performance in a clone.
3. Keep `COMPATIBLE` at the old value until the upgrade is accepted, because raising it prevents downgrade.

**Bottom Line:** Patching is routine maintenance within a release; upgrading is a project that requires testing and a fallback plan.

---

### Q21. What is the recommended BaseDB patching order?

**Answer:**

Update the **infrastructure layer first** (DB system, including Grid Infrastructure and OS where applicable), then the **database layer**. Run a pre-check before every step.

#### a. Order of Operations

```text
1. Pre-check DB system update
2. Apply DB system update (Grid Infrastructure / OS)
3. Pre-check database (DB home) patch
4. Apply database patch (datapatch runs automatically)
5. Validate services, SQL patch registry, backups, and applications
```

#### b. CLI Example

```bash
# List available DB system patches
oci db patch list by-db-system --db-system-id <db-system-ocid>

# Pre-check, then apply
oci db system patch --db-system-id <db-system-ocid> --patch-id <patch-ocid> --patch-action PRECHECK
oci db system patch --db-system-id <db-system-ocid> --patch-id <patch-ocid> --patch-action APPLY

# Repeat for the database
oci db database patch --database-id <db-ocid> --patch-id <patch-ocid> --patch-action APPLY
```

#### c. Data Guard Note

For eligible patches, use **Standby-First Patch Apply**: patch the standby, switch over, then patch the former primary to minimize downtime.

**Bottom Line:** Pre-check everything, patch the DB system before the database, and validate after each step.

---

### Q22. What is out-of-place patching?

**Answer:**

**Out-of-place patching** creates a **new DB home** at the target patch level and moves the database to it, leaving the original home untouched. This reduces risk and makes rollback simple.

#### a. Steps

1. Create a **custom database software image** with the target Release Update and any required one-off patches.
2. Create a new DB home on the DB system from that image.
3. **Move** the database to the new home (the database restarts and `datapatch` applies SQL changes).
4. Validate the database and applications.
5. Keep the old home for rollback, and delete it after the change is accepted.

#### b. In-Place Versus Out-of-Place

| Aspect | In-place | Out-of-place |
|---|---|---|
| Changes the active home | Yes | No |
| Rollback | Roll back the patch | Move the database back to the old home |
| Downtime | Patch duration | Restart duration |
| Standardization | Patch levels can drift | Custom images enforce one patch level |

**Bottom Line:** Out-of-place patching with custom software images is safer, more consistent, and easier to roll back.

---

### Q23. How does RAC reduce patching downtime?

**Answer:**

With RAC, eligible patches are applied in **rolling** mode: one node is patched while the other continues serving users. Applications stay available only if they connect through **services** and handle connection moves correctly.

#### a. Rolling Timeline

```text
Node 1: [drain services] → [patch] → [restart] → [services back]
Node 2:                                            [drain] → [patch] → [restart]
Users:  served by Node 2 ......................... served by Node 1 ............
```

#### b. Service Configuration for Continuous Availability

```bash
srvctl add service -db SALES_PHX -service app_svc -pdb SALESPDB \
  -preferred "SALES1,SALES2" -failovertype AUTO -commit_outcome TRUE \
  -notification TRUE -drain_timeout 300 -stopoption IMMEDIATE
```

`-failovertype AUTO` enables Transparent Application Continuity, and `-drain_timeout` lets sessions finish before the instance stops.

#### c. Client Side (Java UCP)

```java
PoolDataSource pds = PoolDataSourceFactory.getPoolDataSource();
pds.setConnectionFactoryClassName("oracle.jdbc.replay.OracleDataSourceImpl");
pds.setURL("jdbc:oracle:thin:@" + connectDescriptor);
pds.setFastConnectionFailoverEnabled(true);
```

Not every patch is rolling-installable; check the patch README.

**Bottom Line:** RAC enables rolling patches, but zero downtime also requires services, FAN, and Application Continuity on the client side.

### Q24. What should be checked after patching?

**Answer:**

A successful work request does not prove the database is healthy. Validate the **patch level**, **database state**, **services**, and **dependent operations** before closing the change.

#### a. Validation Commands

```sql
-- SQL patch registry
SELECT patch_id, action, status, action_time, description
FROM dba_registry_sqlpatch
ORDER BY action_time DESC;

-- PDB state
SELECT name, open_mode, restricted FROM v$pdbs;

-- Invalid objects

```

```bash
$ORACLE_HOME/OPatch/opatch lspatches

lsnrctl status
```

#### b. Post-Patch Checklist

| Check | Expected result |
|---|---|
| `DBA_REGISTRY_SQLPATCH` | Latest patch `SUCCESS` (rerun `datapatch -verbose` if not) |
| PDBs | `READ WRITE` and not restricted |
| Invalid objects | No new invalid objects (recompile with `utlrp.sql`) |
| Services and listener | All application services registered |
| Backups | Next automatic backup succeeds |
| Data Guard | Transport and apply lag back to normal |
| Application | Smoke tests pass and performance matches the baseline |

**Bottom Line:** Patching is complete only after the database, services, backups, standby, and application are verified.

## 4. Backup and Recovery

### Q25. What backup options does BaseDB provide?

**Answer:**

BaseDB supports **managed automatic backups**, **on-demand full backups**, and **customer-managed RMAN** for special cases. Most production databases should use automatic backups as the foundation.

#### a. Options

| Option | Destination | Lifecycle | Typical use |
|---|---|---|---|
| Automatic backups | Object Storage or Autonomous Recovery Service | Tied to the database and its retention policy | Daily protection and point-in-time recovery |
| On-demand full backup | Object Storage | Kept until you delete it | Before major changes, long-term copies |
| Customer-managed RMAN | Object Storage (Cloud Backup Module) or other targets | Customer-defined | Special retention or compliance requirements |

#### b. Autonomous Recovery Service

A managed backup destination for Oracle databases in OCI that offers incremental-forever backups, backup validation, and optional **real-time data protection** for near-zero data loss.

#### c. Pitfall

Do not configure conflicting RMAN settings or schedules on a database that uses automatic backups—they can interfere with OCI-managed retention and deletion.

**Bottom Line:** Use automatic backups as the baseline, add on-demand backups before risky changes, and use custom RMAN only for special requirements.

---

### Q26. How do automatic backups work conceptually?

**Answer:**

OCI schedules **incremental RMAN backups** plus frequent **archived redo log backups**, which together allow restore to any point inside the retention window.

#### a. Backup Schedule

| Backup type | Frequency | Purpose |
|---|---|---|
| Level 0 (full) | Weekly, on a selectable day | Baseline copy of all blocks |
| Level 1 (incremental) | Daily, in a preferred window (UTC) | Changed blocks since the last backup |
| Archived redo logs | Frequently throughout the day | Point-in-time recovery between backups |

#### b. Retention

| Destination | Retention options |
|---|---|
| Object Storage | 7, 15, 30, 45, or 60 days |
| Autonomous Recovery Service | Protection policies (for example, 14 to 95 days) |

#### c. Enable Automatic Backups (CLI)

```bash
oci db database update --database-id <db-ocid> \
  --db-backup-config '{"autoBackupEnabled": true, "recoveryWindowInDays": 30}'
```

#### d. Best Practices

1. Choose a backup window outside peak business hours.
2. Alert on failed backups through Events and Notifications.
3. Align the retention period with the longest recovery requirement.

**Bottom Line:** Weekly level 0, daily level 1, and frequent archived-log backups enable point-in-time restore within the retention window.

---

### Q27. What are RPO and RTO?

**Answer:**

**RPO (Recovery Point Objective)** is how much data the business can afford to lose. **RTO (Recovery Time Objective)** is how long the business can wait for service to return. Both are business requirements that drive the technical design.

#### a. Timeline

```text
     last recoverable point            failure             service restored
  ───────────●──────────────────────────────X──────────────────────●──────▶ time
             |<─────── RPO (data lost) ────>|<─── RTO (downtime) ──>|
```

#### b. Typical Protection Levels

| Design | Typical RPO | Typical RTO |
|---|---|---|
| Automatic backups only | Minutes to an hour | Hours (depends on size) |
| Data Guard, Maximum Performance | Seconds | Minutes |
| Data Guard, Maximum Availability | Zero (when synchronized) | Minutes |
| Recovery Service with real-time protection | Near zero | Hours (restore required) |

#### c. Example

A 5 TB order database with an RPO of 5 minutes and an RTO of 30 minutes cannot meet its RTO by restoring backups alone. It needs a Data Guard standby, with backups as a second layer.

**Bottom Line:** RPO and RTO come from the business; they determine whether backups are enough or a standby is required.

---

### Q28. What restore options are available for automatic backups?

**Answer:**

You can restore **in place** to a chosen point, or create a **new database** from a backup to recover data without touching production.

#### a. Restore Options

| Option | Restores to | Effect on current database |
|---|---|---|
| Latest | The most recent recoverable state | Overwrites it |
| Timestamp | A specific date and time | Overwrites it; later changes are lost |
| SCN | A specific system change number | Overwrites it; later changes are lost |
| Create database from backup | A new DB system | None—production is unchanged |

#### b. Equivalent RMAN Logic (for Understanding)

```text
RUN {
  SET UNTIL TIME "TO_DATE('2026-10-07 08:00:00','YYYY-MM-DD HH24:MI:SS')";
  RESTORE DATABASE;
  RECOVER DATABASE;
}
ALTER DATABASE OPEN RESETLOGS;
```

For OCI-managed backups, use the Console, CLI, or `dbcli` so that OCI metadata stays consistent.

#### c. Best Practice

For **logical errors** (for example, rows deleted by mistake), restore to a **new database** and copy the data back instead of rolling back all of production.

**Bottom Line:** Restore in place for full recovery; restore to a new database when you only need to recover specific data.

---

### Q29. What is the fast recovery area?

**Answer:**

The **fast recovery area (FRA)** is a disk location managed by the database for recovery-related files. If it fills, the database **cannot archive redo** and stops accepting transactions until space is freed.

#### a. FRA Contents and Parameters

| Item | Description |
|---|---|
| Archived redo logs | Required for recovery and Data Guard gap resolution |
| Flashback logs | Used by Flashback Database |
| Local RMAN backups | Backup pieces stored on disk |
| `DB_RECOVERY_FILE_DEST` | FRA location (disk group or directory) |
| `DB_RECOVERY_FILE_DEST_SIZE` | Maximum space the FRA can use |

#### b. Monitoring Queries

```sql
SELECT file_type, percent_space_used, percent_space_reclaimable, number_of_files
FROM v$recovery_area_usage;

SELECT name,
       ROUND(space_limit / 1024 / 1024 / 1024) AS limit_gb,
       ROUND(space_used  / 1024 / 1024 / 1024) AS used_gb
FROM v$recovery_file_dest;
```

#### c. Related Errors

| Error | Meaning |
|---|---|
| ORA-19809 / ORA-19815 | Recovery file limit reached or nearly reached |
| ORA-00257 | Archiver error; only SYSDBA can connect until space is freed |

Alert at around 80% usage so there is time to act.

**Bottom Line:** The FRA holds recovery files; a full FRA stops the database, so monitor it with alarms.

---

### Q30. Does Data Guard replace backups?

**Answer:**

No. **Data Guard** protects against **infrastructure and site failures**, but it faithfully replicates **logical errors**. Backups protect against mistakes and provide long-term retention. A resilient design uses both.

#### a. Threat Matrix

| Threat | Backups protect? | Data Guard protects? |
|---|---|---|
| Node or host failure | Yes (slow restore) | Yes (fast failover) |
| AD or region outage | Yes, if stored elsewhere | Yes |
| Accidental `DELETE` or `DROP TABLE` | Yes | No (replicated) |
| Physical block corruption | Yes | Yes (Active Data Guard can auto-repair) |
| Logical corruption from a bad application release | Yes | No |
| Malicious data destruction | Yes, if backups are protected | No |
| Long-term retention and compliance | Yes | No |

#### b. Best Practice

Configure Data Guard for **availability** (low RTO) and backups for **recoverability** (logical errors and retention). Many teams also take backups from the standby to offload the primary.

**Bottom Line:** Data Guard keeps you running; backups let you go back in time—you need both.

---

### Q31. What is Flashback Database, and why is it not a backup?

**Answer:**

**Flashback Database** rewinds the whole database to an earlier time, SCN, or restore point by using **flashback logs** in the FRA. It is much faster than restore and recovery, but it depends on the current data files being intact.

#### a. Flashback Technologies Compared

| Feature | Scope | Relies on |
|---|---|---|
| Flashback Query | Read past data with `AS OF` | Undo |
| Flashback Table | Rewind one table | Undo (requires row movement) |
| Flashback Drop | Recover a dropped table | Recycle bin |
| Flashback Database | Rewind the entire database | Flashback logs in the FRA |

#### b. Commands

```sql
ALTER DATABASE FLASHBACK ON;
ALTER SYSTEM SET db_flashback_retention_target = 1440;   -- minutes

CREATE RESTORE POINT before_release GUARANTEE FLASHBACK DATABASE;

-- To rewind (database must be mounted)
SHUTDOWN IMMEDIATE
STARTUP MOUNT
FLASHBACK DATABASE TO RESTORE POINT before_release;
ALTER DATABASE OPEN RESETLOGS;

DROP RESTORE POINT before_release;   -- prevents FRA from filling
```

#### c. Why It Is Not a Backup

- It cannot recover from **media loss**—if data files are gone, flashback logs are useless.
- Retention is limited by FRA space.
- Guaranteed restore points left in place can fill the FRA.

**Bottom Line:** Flashback Database provides a fast rewind for logical mistakes and failed releases, but backups are still required for media failure.

---

### Q32. How do you prove a backup strategy works?

**Answer:**

A backup is only proven when it has been **restored successfully** within the RTO. A restore-testing program turns assumptions into evidence.

#### a. Validation Techniques

| Technique | What it proves |
|---|---|
| `RESTORE DATABASE VALIDATE;` | Backup pieces exist and are readable |
| `RESTORE DATABASE PREVIEW;` | Which backups RMAN would use |
| `BACKUP VALIDATE CHECK LOGICAL DATABASE;` | No physical or logical block corruption |
| Full test restore to a new DB system | End-to-end recoverability and actual RTO |

#### b. Restore-Testing Program

1. Restore to an **isolated** DB system on a regular schedule (for example, quarterly).
2. Open the database, run integrity checks, and run application smoke tests.
3. Record the **achieved RPO and RTO** and compare them with objectives.
4. Verify dependencies: TDE keys or wallet, credentials, network access, and runbooks.
5. Fix gaps and update the runbook.

#### c. Metrics to Track

| Metric | Target example |
|---|---|
| Hours since last successful backup | Less than 24 |
| Days since last successful restore test | Less than 90 |
| Achieved RTO in the last test | At or below the agreed RTO |

**Bottom Line:** Untested backups are assumptions—schedule restore tests and measure the RTO you actually achieve.

## 5. High Availability and Data Guard

### Q33. What does Oracle Data Guard provide?

**Answer:**

**Oracle Data Guard** maintains one or more **standby databases** by shipping redo from the primary and applying it continuously. In BaseDB, OCI automates creating the standby DB system, configuring the broker, and performing role transitions.

#### a. Architecture

```text
Primary (SALES_PHX)                             Standby (SALES_IAD)
  LGWR ── redo transport (SYNC/ASYNC) ──> RFS ──> standby redo logs ──> MRP (apply)
          managed by the Data Guard broker (DGMGRL) on both sides
```

#### b. OCI Requirements

| Requirement | Detail |
|---|---|
| Edition | Enterprise Edition or higher (Active Data Guard needs Extreme Performance) |
| Versions | Same database version and patch level on both sides |
| Network | Port 1521 open between primary and standby; DRG peering for cross-region |
| Placement | Another fault domain, AD, or region |

#### c. Broker Commands

```text
DGMGRL> SHOW CONFIGURATION;
DGMGRL> SHOW DATABASE VERBOSE 'SALES_IAD';
DGMGRL> VALIDATE DATABASE 'SALES_IAD';
```

**Bottom Line:** Data Guard keeps a synchronized standby for planned and unplanned role changes, and OCI automates its setup and management.

---

### Q34. Compare switchover, failover, and reinstate.

**Answer:**

These are the three Data Guard **role transitions**. Switchover is planned and lossless, failover is an emergency action, and reinstate rebuilds the old primary as a standby after a failover.

#### a. Comparison

| Operation | When | Data loss | Old primary afterward |
|---|---|---|---|
| Switchover | Planned maintenance or DR testing | None | Becomes the standby |
| Failover | Primary unavailable | Depends on protection mode and synchronization | Disabled until reinstated |
| Reinstate | After a failover | Not applicable | Converted into a standby |

#### b. Commands

```bash
# OCI CLI
oci db data-guard-association switchover --database-id <primary-db-ocid> \
  --data-guard-association-id <dg-association-ocid> --database-admin-password '<password>'
oci db data-guard-association failover  --database-id <standby-db-ocid> \
  --data-guard-association-id <dg-association-ocid> --database-admin-password '<password>'
oci db data-guard-association reinstate --database-id <old-primary-db-ocid> \
  --data-guard-association-id <dg-association-ocid> --database-admin-password '<password>'
```

```text
DGMGRL> SWITCHOVER TO 'SALES_IAD';
DGMGRL> FAILOVER TO 'SALES_IAD';
DGMGRL> REINSTATE DATABASE 'SALES_PHX';
```

Reinstate requires Flashback Database on the former primary. Avoid passing passwords on the command line in production; read them from a vault.

#### c. Pre-Switchover Checklist

1. `VALIDATE DATABASE` reports **Ready for Switchover**.
2. Transport and apply lag are near zero.
3. Application services are role-based and connection strings include both sites.
4. Stakeholders are notified and a fallback plan exists.

**Bottom Line:** Use switchover for planned moves, failover only for emergencies, and reinstate to restore protection afterward.

---

### Q35. What are the Data Guard protection modes?

**Answer:**

The **protection mode** balances data protection against primary performance and availability. It is enforced through the redo transport mode (`SYNC`, `ASYNC`, or `FASTSYNC`).

#### a. Modes

| Mode | Transport | Data loss | If the standby is unreachable |
|---|---|---|---|
| Maximum Performance | ASYNC | Small amount possible | Primary continues unaffected |
| Maximum Availability | SYNC or FASTSYNC | Zero when synchronized | Primary continues after a timeout (unprotected) |
| Maximum Protection | SYNC | Zero | **Primary shuts down** rather than run unprotected |

`FASTSYNC` (`SYNC NOAFFIRM`) acknowledges redo when it reaches standby memory, reducing commit latency compared with `SYNC AFFIRM`.

#### b. Choosing a Mode

| Situation | Recommended |
|---|---|
| Standby in another region (high latency) | Maximum Performance |
| Standby in another AD (low latency), zero data loss goal | Maximum Availability |
| Regulatory requirement for zero data loss above all | Maximum Protection (rare) |

#### c. Change the Mode With the Broker

```text
DGMGRL> EDIT DATABASE 'SALES_IAD' SET PROPERTY LogXptMode='SYNC';
DGMGRL> EDIT CONFIGURATION SET PROTECTION MODE AS MaxAvailability;
```

Check which modes the OCI automation supports for your configuration before changing them manually.

**Bottom Line:** Choose the mode from RPO and network latency—Maximum Availability for nearby standbys, Maximum Performance for distant ones.

---

### Q36. What is the difference between transport lag and apply lag?

**Answer:**

Lag tells you how far the standby is behind the primary. **Transport lag** measures redo not yet **received**; **apply lag** measures redo received but not yet **applied**. Separating them points you to the right bottleneck.

#### a. Comparison

| Metric | Meaning | Common causes |
|---|---|---|
| Transport lag | Redo generated but not yet received by the standby | Network bandwidth or latency, DRG issues, primary archiver problems |
| Apply lag | Redo received but not yet applied | Apply stopped, standby CPU or I/O limits, large redo bursts |

Transport lag affects **RPO** (data at risk). Apply lag affects **RTO** (failover must finish applying before opening).

#### b. Monitoring

```sql
SELECT name, value, unit, time_computed
FROM v$dataguard_stats
WHERE name IN ('transport lag', 'apply lag');

SELECT * FROM v$archive_gap;
```

```text
DGMGRL> SHOW DATABASE 'SALES_IAD';
```

**Bottom Line:** Transport lag is a network or primary problem that risks data; apply lag is a standby problem that lengthens failover.

---

### Q37. What is Active Data Guard?

**Answer:**

**Active Data Guard (ADG)** lets a physical standby open **read-only while redo apply continues**, turning the standby into a usable reporting and offload resource. It is included in Enterprise Edition Extreme Performance or available through BYOL with the option licensed.

#### a. Key Features

| Feature | Benefit |
|---|---|
| Real-time query | Run reports on the standby with current data |
| Automatic block repair | Corrupt blocks on the primary are repaired from the standby, and vice versa |
| DML redirection (19c and later) | Occasional writes on the standby are redirected to the primary |
| Fast incremental backups on the standby | Offload backups from the primary |
| Rolling upgrades with `DBMS_ROLLING` | Reduce upgrade downtime |

#### b. Check the Open Mode

```sql
SELECT database_role, open_mode FROM v$database;
-- PHYSICAL STANDBY   READ ONLY WITH APPLY
```

#### c. Design Notes

- Reports on the standby can see slightly stale data; set expectations with users.
- Heavy queries on the standby compete with redo apply for resources—monitor apply lag.

**Bottom Line:** Active Data Guard makes the standby useful every day for reporting, backups, and corruption repair.

---

### Q38. Where should the standby be placed?

**Answer:**

Standby placement determines **which failures** you survive and **how much latency** redo transport adds. The farther away the standby, the larger the failure it protects against.

#### a. Placement Options

| Placement | Protects against | Latency | Typical mode |
|---|---|---|---|
| Different fault domain, same AD | Rack and hardware failure | Lowest | Maximum Availability |
| Different AD, same region | Data-center failure | Low | Maximum Availability |
| Different region | Regional disaster | Higher | Maximum Performance |

#### b. Network Requirements for Cross-Region

1. Non-overlapping VCN CIDRs.
2. DRGs in both regions with a **remote peering connection**.
3. Route rules and NSG rules allowing 1521 in both directions.
4. DNS resolution of the peer's host names.

#### c. Single-AD Regions

Use another **fault domain** for local protection and another **region** for disaster recovery.

**Bottom Line:** Place the standby according to the largest failure you must survive, and choose the protection mode that matches the resulting latency.

---

### Q39. When should RAC and Data Guard be combined?

**Answer:**

**RAC** and **Data Guard** protect against different failures, so mission-critical databases often use both. Oracle describes these layered designs as the **Maximum Availability Architecture (MAA)** tiers.

#### a. What Each Protects

| Failure | RAC | Data Guard |
|---|---|---|
| Instance or node crash | Yes (surviving node continues) | Yes (failover, slower) |
| Rolling patch maintenance | Yes | Yes (standby-first) |
| Storage or database corruption | No | Yes |
| AD or region outage | No | Yes |

#### b. Oracle MAA Tiers

| Tier | Components | Typical workload |
|---|---|---|
| Bronze | Single instance with backups | Development, non-critical |
| Silver | Bronze plus RAC | Business-important applications |
| Gold | Silver plus Active Data Guard | Mission-critical applications |
| Platinum | Gold plus GoldenGate and advanced techniques | Zero-downtime requirements |

**Bottom Line:** RAC handles local node failures and rolling maintenance; Data Guard handles site and data failures—critical systems use both.

---

### Q40. How should applications connect so they survive role changes?

**Answer:**

After a switchover or failover, the database runs on **different hosts**. Applications survive only if they connect to a **role-based service** and know about both sites.

#### a. Recommended Connect Descriptor

```text
APP_SVC =
 (DESCRIPTION =
   (CONNECT_TIMEOUT=90)(RETRY_COUNT=30)(RETRY_DELAY=3)(TRANSPORT_CONNECT_TIMEOUT=3)
   (ADDRESS_LIST =
     (LOAD_BALANCE=on)
     (ADDRESS = (PROTOCOL = TCP)(HOST = sales-phx-scan.example.com)(PORT = 1521)))
   (ADDRESS_LIST =
     (LOAD_BALANCE=on)
     (ADDRESS = (PROTOCOL = TCP)(HOST = sales-iad-scan.example.com)(PORT = 1521)))
   (CONNECT_DATA = (SERVICE_NAME = app_svc.example.com)))
```

The client tries both sites and retries until the service starts on the new primary.

#### b. Role-Based Service

```bash
srvctl add service -db SALES_PHX -service app_svc -pdb SALESPDB -role PRIMARY
```

On LVM-based systems without Grid Infrastructure, start the service with `DBMS_SERVICE` from a trigger on `STARTUP` and `DB_ROLE_CHANGE` events instead.

#### c. Best Practices

1. Never connect applications to host names, node IPs, or SIDs.
2. Use FAN-aware pools (such as UCP) to remove dead connections quickly.
3. Test reconnection during every switchover rehearsal.

**Bottom Line:** Role-based services plus multi-site connect strings make role changes transparent to applications.

## 6. Security

### Q41. How do OCI IAM and database security differ?

**Answer:**

BaseDB has **three security layers**. **OCI IAM** controls the cloud control plane, **database security** controls data access, and **OS security** controls node access. Securing one layer does not secure the others.

#### a. Layers

| Layer | Controls | Example question it answers |
|---|---|---|
| OCI IAM | Console, CLI, and API actions on DB systems, backups, and networks | Who can terminate this DB system? |
| Database | Users, roles, privileges, VPD, and auditing | Who can read the `SALARY` column? |
| Operating system | SSH keys, OS users (`opc`, `oracle`, `grid`), and `sudo` | Who can log in to the node? |

#### b. Best Practices

1. Separate network, database, security, and audit duties into different IAM groups.
2. Use named database accounts instead of shared `SYSTEM` logins.
3. Restrict SSH to Bastion sessions and audit `sudo` usage.
4. Newer database releases can use OCI IAM or Microsoft Entra ID for database user authentication—check version support.

**Bottom Line:** IAM protects the cloud resources, database security protects the data, and OS security protects the host—secure all three.

---

### Q42. Give an example IAM policy for database administrators.

**Answer:**

Policies should give each role **only** what it needs. Database administrators need the database family plus permission to **use** (not manage) the network.

#### a. Role-Based Policy Set

```text
Allow group DBAdmins to manage database-family in compartment Prod-DB
Allow group DBAdmins to use virtual-network-family in compartment Prod-Network
Allow group DBOperators to read database-family in compartment Prod-DB
Allow group DBAuditors to inspect database-family in compartment Prod-DB
```

#### b. Prevent Accidental Deletion

```text
Allow group DBOperators to manage db-systems in compartment Prod-DB
  where request.permission != 'DB_SYSTEM_DELETE'
```

#### c. Role Matrix

| Role | Database resources | Network | Vault keys |
|---|---|---|---|
| DB administrator | manage | use | use (if customer-managed keys) |
| DB operator | read or limited manage | none | none |
| Auditor | inspect or read | read | read |
| Network administrator | none | manage | none |

**Bottom Line:** Grant `manage database-family` only to DBAs, `use` on the network, and read-only access to operators and auditors.

### Q43. How is data encrypted in BaseDB?

**Answer:**

Data at rest is protected with **Transparent Data Encryption (TDE)**, which is enabled by default on OCI. Data in transit is protected with Oracle native network encryption or **TLS**.

#### a. TDE Key Hierarchy

```text
Master encryption key (Oracle-managed wallet or OCI Vault)
 └── encrypts tablespace keys
      └── encrypt data blocks in data files, redo, undo, and backups
```

#### b. Key Management Options

| Option | Control | Notes |
|---|---|---|
| Oracle-managed (wallet on the node) | Basic | Simplest; wallet password must be protected |
| Customer-managed in OCI Vault | Full: rotation, revocation, audit | Meets stricter compliance; Vault availability becomes critical |

#### c. Useful Commands

```sql
SELECT wrl_type, wrl_parameter, status, wallet_type FROM v$encryption_wallet;
SELECT tablespace_name, encrypted FROM dba_tablespaces;
SHOW PARAMETER encrypt_new_tablespaces
```

Rotate the master key from the Console or with `ADMINISTER KEY MANAGEMENT` (for wallet-based keys), and always keep backups of the keys.

#### d. In Transit

OCI DB systems typically enable **native network encryption** by default. Configure a **TCPS (TLS)** listener when certificate-based authentication or TLS compliance is required.

**Bottom Line:** TDE encrypts data at rest with Oracle- or customer-managed keys, and network encryption or TLS protects data in transit.

### Q44. How should administrative access to DB nodes be secured?

**Answer:**

DB nodes should have **no public IP**. Administrators connect through **OCI Bastion**, which creates time-limited, audited SSH sessions into the private subnet.

#### a. Bastion Port-Forwarding Session

```bash
# 1. Open the tunnel created by the Bastion session
ssh -i ~/.ssh/bastion_key -N -L 2222:10.0.2.15:22 -p 22 \
  <bastion-session-ocid>@host.bastion.<region>.oci.oraclecloud.com

# 2. Connect to the DB node through the tunnel
ssh -i ~/.ssh/db_node_key -p 2222 opc@localhost
sudo su - oracle
```

#### b. Controls

| Control | Purpose |
|---|---|
| Bastion CIDR allowlist | Only corporate IP ranges can create sessions |
| Session time-to-live (maximum of a few hours) | Access expires automatically |
| NSG rule: port 22 only from the Bastion | No other SSH path exists |
| Separate keys per administrator | Accountability |
| OCI Audit and OS logs | Who connected and what they did |

**Bottom Line:** Use Bastion sessions with short time-to-live values, restricted sources, and individual keys—never public IPs on DB nodes.

### Q45. How should applications handle database credentials?

**Answer:**

Credentials should never live in code or configuration files. Store them in **OCI Vault**, retrieve them at runtime with a **resource or instance principal**, and grant the database account only the privileges it needs.

#### a. Retrieve a Secret (Java SDK)

```java
var provider = InstancePrincipalsAuthenticationDetailsProvider.builder().build();
try (SecretsClient secrets = SecretsClient.builder().build(provider)) {
    var response = secrets.getSecretBundle(
            GetSecretBundleRequest.builder().secretId(secretOcid).build());
    var content = (Base64SecretBundleContentDetails)
            response.getSecretBundle().getSecretBundleContent();
    String password = new String(Base64.getDecoder().decode(content.getContent()),
            StandardCharsets.UTF_8);
}
```

#### b. Least-Privilege Database Account

```sql
CREATE USER orders_app IDENTIFIED BY "<from-vault>";
GRANT CREATE SESSION TO orders_app;
GRANT SELECT, INSERT, UPDATE ON orders.order_items TO orders_app;
```

#### c. Best Practices

1. Use a separate account per application—never `SYSTEM` or schema owners.
2. Apply password profiles and rotate secrets with versioned Vault secrets.
3. Keep credentials out of images, logs, Git, and Terraform state.

**Bottom Line:** Vault plus principals removes stored credentials, and least-privilege accounts limit damage if a secret leaks.

### Q46. What should database auditing cover?

**Answer:**

**Unified auditing** records security-relevant activity in a single audit trail. Audit what matters—privileged actions, logon failures, and sensitive data access—without auditing everything.

#### a. Example Audit Policies

```sql
CREATE AUDIT POLICY dba_actions_pol
  PRIVILEGES CREATE USER, ALTER USER, DROP USER, GRANT ANY PRIVILEGE
  ACTIONS ALTER SYSTEM;
AUDIT POLICY dba_actions_pol;

CREATE AUDIT POLICY salary_access_pol
  ACTIONS SELECT, UPDATE ON hr.employees;
AUDIT POLICY salary_access_pol;
```

#### b. Query the Audit Trail

```sql
SELECT event_timestamp, dbusername, action_name, object_schema, object_name
FROM unified_audit_trail
ORDER BY event_timestamp DESC
FETCH FIRST 20 ROWS ONLY;
```

#### c. Best Practices

| Practice | Why |
|---|---|
| Keep predefined policies such as `ORA_SECURECONFIG` and `ORA_LOGON_FAILURES` | Baseline coverage |
| Restrict access to audit data (`AUDIT_ADMIN`, `AUDIT_VIEWER`) | Prevent tampering |
| Forward audit records to **OCI Data Safe** or a SIEM | Central analysis and retention |
| Purge on a schedule with `DBMS_AUDIT_MGMT` | Control storage growth |

**Bottom Line:** Audit privileged and sensitive actions, protect the audit trail, and centralize it for analysis.

## 7. Monitoring, Migration, and Automation

### Q47. Which signals should be monitored for BaseDB?

**Answer:**

Monitor across **infrastructure**, **database**, and **service** layers. Infrastructure metrics alone miss database problems such as blocking locks or plan regressions.

#### a. Monitoring Layers

| Layer | Signals | OCI tool |
|---|---|---|
| Infrastructure | CPU, memory, storage capacity and latency | OCI Monitoring |
| Database | Sessions, wait events, top SQL, tablespace and FRA usage | Database Management (Performance Hub, AWR) |
| Availability | Listener, services, Data Guard lag | Database Management, custom checks |
| Operations | Backup status, patch compliance | Events, Notifications |
| Capacity trends | Long-term CPU and storage growth | Ops Insights |
| Logs | Alert log, listener log | Logging Analytics |

#### b. Example Alarm Query (MQL)

```text
CpuUtilization[5m]{resourceId = "<db-system-ocid>"}.mean() > 80
```

#### c. Alarm Design

1. Use warning (for example, 80%) and critical (for example, 95%) thresholds.
2. Route alarms to an owned Notifications topic.
3. Include runbook links in alarm bodies.

**Bottom Line:** Combine OCI Monitoring, Database Management, and Ops Insights so that infrastructure, database, and capacity issues are all visible.

### Q48. How do you diagnose high database CPU?

**Answer:**

High CPU is a **symptom**. Find **which SQL or sessions** consume it and **why** before adding OCPUs.

#### a. Investigation Steps

1. Confirm the time window and user impact.
2. Compare with a baseline period (AWR compare-periods report).
3. Identify top SQL and sessions.
4. Check for execution plan changes.
5. Decide whether to tune, reschedule, or scale.

#### b. Diagnostic Queries

```sql
-- Top SQL by CPU since it was loaded
SELECT sql_id, executions,
       ROUND(cpu_time / 1e6) AS cpu_sec,
       ROUND(elapsed_time / 1e6) AS elapsed_sec,
       SUBSTR(sql_text, 1, 60) AS sql_text
FROM v$sql
ORDER BY cpu_time DESC
FETCH FIRST 10 ROWS ONLY;

-- Active session activity in the last 15 minutes (ASH)
SELECT sql_id, session_state, event, COUNT(*) AS samples
FROM v$active_session_history
WHERE sample_time > SYSDATE - INTERVAL '15' MINUTE
GROUP BY sql_id, session_state, event
ORDER BY samples DESC
FETCH FIRST 10 ROWS ONLY;

-- Actual execution plan of a suspect statement
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR('<sql_id>', NULL, 'ALLSTATS LAST'));
```

Run `@?/rdbms/admin/awrrpt.sql` for an AWR report covering the problem window.

#### c. Common Fixes

| Cause | Fix |
|---|---|
| Plan regression | SQL Plan Baseline to pin the good plan |
| Missing index or stale statistics | Add the index or gather statistics |
| Batch job during peak hours | Reschedule, or limit it with Resource Manager |
| Legitimate growth | Scale OCPUs |

**Bottom Line:** Use ASH and AWR to find the SQL driving CPU, fix inefficiency first, and scale only for legitimate demand.

### Q49. Which migration methods can move a database to BaseDB?

**Answer:**

The right method depends on **database size**, **allowed downtime**, **source and target versions**, and **platform compatibility**.

#### a. Methods

| Method | Type | Downtime | Best for |
|---|---|---|---|
| Data Pump | Logical | Hours (size-dependent) | Selected schemas, version changes, reorganization |
| RMAN backup and restore | Physical | Restore time plus redo apply | Large databases with a planned outage |
| Data Guard | Physical | Minutes (switchover) | Compatible platforms, minimal downtime |
| Zero Downtime Migration (ZDM) | Physical or logical | Minimal (online modes) | Automated, repeatable migrations |
| GoldenGate / OCI Database Migration | Logical replication | Near zero | Cross-platform, cross-version, phased cutovers |

#### b. Data Pump Example

```bash
expdp system@SRCPDB schemas=HR directory=DATA_PUMP_DIR dumpfile=hr_%U.dmp \
  parallel=4 logfile=hr_exp.log
# Copy dump files through Object Storage, then:
impdp system@TGTPDB schemas=HR directory=DATA_PUMP_DIR dumpfile=hr_%U.dmp \
  parallel=4 logfile=hr_imp.log
```

#### c. ZDM Tip

Run ZDM in **evaluation mode** (`zdmcli migrate database ... -eval`) first to detect issues before the real migration.

**Bottom Line:** Choose Data Pump for flexibility, RMAN or Data Guard for large physical moves, and ZDM or GoldenGate when downtime must be minimal.

### Q50. What should be validated after migration?

**Answer:**

A migration is successful only when the **data**, **objects**, **security**, **operations**, and **performance** match expectations. Use a checklist and compare source and target.

#### a. Validation Queries

```sql
-- Object counts by schema and type (compare with the source)
SELECT owner, object_type, COUNT(*) AS objects
FROM dba_objects WHERE owner IN ('HR', 'SALES')
GROUP BY owner, object_type ORDER BY owner, object_type;

-- Invalid objects (recompile with @?/rdbms/admin/utlrp.sql)
SELECT owner, object_name, object_type FROM dba_objects WHERE status = 'INVALID';

-- Character set
SELECT value FROM nls_database_parameters WHERE parameter = 'NLS_CHARACTERSET';
```

#### b. Checklist

| Area | Checks |
|---|---|
| Data | Row counts, checksums, or `DBMS_COMPARISON` for critical tables |
| Objects | Counts, invalid objects, sequences, synonyms |
| Security | Users, roles, grants, password profiles |
| Integrations | Database links, directories, external tables, scheduler jobs |
| Settings | Character set, time zone, NLS parameters |
| Operations | Automatic backups, monitoring, alarms |
| Performance | Key transactions compared with source baselines |

**Bottom Line:** Validate data, objects, security, and operations—not just whether the database opens.

### Q51. Why automate BaseDB with Terraform or the OCI CLI?

**Answer:**

**Infrastructure as code** makes DB systems reproducible, reviewable, and consistent across environments. It also documents exactly how production was built.

#### a. Terraform Example

```hcl
resource "oci_database_db_system" "prod" {
  compartment_id          = var.compartment_ocid
  availability_domain     = var.availability_domain
  subnet_id               = oci_core_subnet.db.id
  nsg_ids                 = [oci_core_network_security_group.db.id]
  shape                   = "VM.Standard.E4.Flex"
  cpu_core_count          = 4
  database_edition        = "ENTERPRISE_EDITION"
  license_model           = "BRING_YOUR_OWN_LICENSE"
  data_storage_size_in_gb = 256
  node_count              = 1
  hostname                = "proddb"
  ssh_public_keys         = [var.ssh_public_key]

  db_system_options {
    storage_management = "LVM"
  }

  db_home {
    db_version = "19.0.0.0"
    database {
      db_name        = "PRODDB"
      pdb_name       = "APPPDB"
      admin_password = var.db_admin_password   # declare as sensitive

      db_backup_config {
        auto_backup_enabled     = true
        recovery_window_in_days = 30
      }
    }
  }

  lifecycle {
    prevent_destroy = true
  }
}
```

#### b. Best Practices

1. Store Terraform state remotely with encryption and restricted access—state can contain passwords.
2. Mark secret variables `sensitive = true` and supply them from a vault.
3. Use `prevent_destroy` on production databases.
4. Avoid manual Console changes that cause **drift**; run `terraform plan` regularly to detect it.

**Bottom Line:** Terraform makes database infrastructure repeatable and reviewable, provided state and secrets are protected.

### Q52. How can BaseDB costs be controlled?

**Answer:**

BaseDB cost is driven mainly by **OCPUs**, **license model**, **storage**, and **backup retention**. Optimize them without weakening agreed availability and recovery objectives.

#### a. Cost Levers

| Lever | Action |
|---|---|
| OCPUs | Right-size from AWR and Ops Insights data |
| License model | Use BYOL where licenses are owned |
| Non-production | Stop nodes outside working hours |
| Storage | Increase in steps because it cannot shrink |
| Backups | Match retention to real recovery requirements |
| Edition | Avoid paying for Extreme Performance when RAC and ADG are not needed |

#### b. Scheduled Stop for Development Systems

```bash
oci db node stop  --db-node-id <node-ocid>   # evening
oci db node start --db-node-id <node-ocid>   # morning
```

#### c. Governance

Apply **cost-tracking tags** (owner, environment, cost center), set **budgets** with alert rules, and review Cost Analysis monthly.

**Bottom Line:** Right-size OCPUs, use BYOL where possible, stop idle non-production systems, and track spending with tags and budgets.

## 8. Scenario-Based Questions

### Q53. An automatic backup failed. What do you do?

**Answer:**

Treat a failed backup as a **risk to the RPO**. Find the cause, fix it, take a successful backup immediately, and confirm recoverability.

#### a. Troubleshooting Steps

| Step | Action |
|---|---|
| 1 | Read the backup work request error in the Console |
| 2 | On the node, check jobs: `dbcli list-jobs` and `dbcli describe-job -i <job-id>` |
| 3 | Review RMAN logs under the DCS log directories (`/opt/oracle/dcs/log/`) |
| 4 | Test Object Storage access: `curl -I https://objectstorage.<region>.oraclecloud.com` |
| 5 | Verify the service gateway route and NSG egress rules |
| 6 | Check FRA and file-system space (`v$recovery_area_usage`, `df -h`) |
| 7 | Confirm the TDE wallet is open or the Vault key is enabled |
| 8 | Confirm the DCS agent and Oracle Cloud Agent are running |

#### b. Recovery Actions

1. Fix the root cause.
2. Run an **on-demand backup** and confirm it succeeds.
3. Calculate whether the RPO was breached and report it.
4. Add an alarm or Events rule so the next failure is detected immediately.

**Bottom Line:** Diagnose from the work request and logs, fix the cause, back up immediately, and close the monitoring gap.

### Q54. The FRA is 95% full. How do you respond?

**Answer:**

Act quickly: at 100%, archiving stops and the database stops accepting transactions. Identify **what is consuming space** before deleting anything.

#### a. Diagnose

```sql
SELECT file_type, percent_space_used, percent_space_reclaimable
FROM v$recovery_area_usage;

-- Guaranteed restore points silently consume space
SELECT name, guarantee_flashback_database, storage_size FROM v$restore_point;
```

#### b. Remediate

| Cause | Action |
|---|---|
| Archived logs not backed up | Run a backup, then delete logs that are backed up |
| Data Guard gap blocking deletion | Fix transport to the standby |
| Forgotten guaranteed restore point | Drop it after confirming it is no longer needed |
| Long flashback retention | Reduce `db_flashback_retention_target` |
| FRA genuinely too small | Increase `db_recovery_file_dest_size` and storage |

```text
RMAN> BACKUP ARCHIVELOG ALL NOT BACKED UP 1 TIMES;
RMAN> DELETE NOPROMPT ARCHIVELOG ALL BACKED UP 1 TIMES TO DEVICE TYPE SBT;
```

```sql
ALTER SYSTEM SET db_recovery_file_dest_size = 400G SCOPE = BOTH SID = '*';
```

On systems with automatic backups, coordinate manual RMAN actions with the OCI-managed configuration.

#### c. Never Do This

Do **not** delete archived logs with OS commands—RMAN and the control file lose track of them and recovery can fail.

**Bottom Line:** Find the space consumer, free space through RMAN or configuration, and add an 80% alarm to prevent recurrence.

### Q55. Apply lag is increasing, but transport lag is near zero. What does it mean?

**Answer:**

Redo **arrives** at the standby on time but is **not applied** fast enough. The bottleneck is on the **standby**, not the network. If a failover happens now, it will take longer because the backlog must be applied first.

#### a. Diagnose

```sql
SELECT name, value FROM v$dataguard_stats WHERE name IN ('transport lag', 'apply lag');
SELECT name, role, action, sequence# FROM v$dataguard_process;
```

```text
DGMGRL> SHOW DATABASE 'SALES_IAD';
```

#### b. Causes and Fixes

| Cause | Fix |
|---|---|
| Redo apply stopped | `DGMGRL> EDIT DATABASE 'SALES_IAD' SET STATE='APPLY-ON';` |
| Standby smaller than the primary | Scale the standby shape to match the primary |
| Slow standby storage | Review I/O metrics and the storage performance option |
| Large batch or index rebuild on the primary | Expect a temporary spike; confirm it drains |
| Heavy Active Data Guard queries | Tune or move reporting workloads |

**Bottom Line:** Apply lag with low transport lag is a standby capacity or apply problem—fix it to keep failover time within the RTO.

### Q56. A patch pre-check fails. What do you do?

**Answer:**

A failed pre-check is **good news**: it stopped a patch that would probably have failed mid-way. Read the exact error, fix the cause, and rerun the pre-check.

#### a. Common Failures

| Failure | Check | Fix |
|---|---|---|
| Insufficient space | `df -h /u01` | Clean old logs or patch files, or extend the volume |
| Patch conflict with a one-off patch | `opatch prereq CheckConflictAgainstOHWithDetail -ph ./` | Obtain a merged patch from Oracle Support |
| Cluster resources offline | `crsctl stat res -t` | Start or repair resources |
| Agent or DCS issue | Check the DCS agent status and logs | Restart the agent or open a support request |
| Database or PDB not in the expected state | `SELECT name, open_mode FROM v$pdbs;` | Open the required PDBs |

#### b. Process

1. Capture the error from the work request and node logs.
2. Fix the cause and rerun the pre-check until it passes.
3. Confirm a recent, validated backup exists.
4. Apply the patch in the approved window.

**Bottom Line:** Treat pre-check failures as early warnings—fix the cause, rerun, and patch only with a clean pre-check and a backup.

### Q57. Users deleted critical rows two hours ago. How do you recover?

**Answer:**

Choose the **least disruptive** method that recovers the data, preferably without losing legitimate changes made since the mistake.

#### a. Option 1: Flashback Query (Preferred if Undo Covers the Period)

```sql
INSERT INTO orders o
SELECT * FROM orders AS OF TIMESTAMP (SYSTIMESTAMP - INTERVAL '125' MINUTE) h
WHERE NOT EXISTS (SELECT 1 FROM orders c WHERE c.order_id = h.order_id);
COMMIT;
```

If undo has been overwritten, this fails with ORA-01555; check `UNDO_RETENTION`.

#### b. Option 2: Flashback Table

```sql
ALTER TABLE orders ENABLE ROW MOVEMENT;
FLASHBACK TABLE orders TO TIMESTAMP (SYSTIMESTAMP - INTERVAL '125' MINUTE);
```

This also reverts legitimate changes to the table made after that time.

#### c. Option 3: Restore to a New Database

Restore an automatic backup to a **new DB system** at the required time, then copy the missing rows back with a database link or Data Pump.

#### d. Last Resort

**Point-in-time recovery** of the whole database loses all later transactions—use it only when the business accepts that loss. If a table was dropped, use `FLASHBACK TABLE orders TO BEFORE DROP;`.

**Bottom Line:** Try Flashback Query first, restore to a separate database next, and roll back the entire database only as a last resort.

### Q58. After a switchover, the application cannot connect. What do you check?

**Answer:**

The database is fine on the new primary, but the **connection path** is not. Check the service, the connect string, the network, and the client pool in order.

#### a. Checklist

| Step | Check | Command or action |
|---|---|---|
| 1 | Service running on the new primary | `srvctl status service -db SALES_IAD` or `lsnrctl services` |
| 2 | Service is role-based (`-role PRIMARY`) | `srvctl config service -db SALES_IAD -service app_svc` |
| 3 | Connect string includes both sites | Review the TNS descriptor or JDBC URL |
| 4 | DNS resolves the standby SCAN name | `nslookup sales-iad-scan.example.com` |
| 5 | NSG and route rules allow app → standby site | Network Path Analyzer |
| 6 | Connection pool discarded dead connections | FAN/ONS configuration, pool validation |

#### b. Quick Test From the Application Host

```bash
sqlplus app_user@"//sales-iad-scan.example.com:1521/app_svc.example.com"
```

**Bottom Line:** Verify the role-based service, the multi-site connect string, network access, and pool recovery—then add them to the DR rehearsal checklist.

### Q59. CPU reaches 95% every business morning. Should you scale immediately?

**Answer:**

Not automatically. High CPU is acceptable if users are unaffected. Scale only when **legitimate** demand exceeds capacity after **inefficiency** is removed.

#### a. Investigation

1. Check whether response times or queues degrade during the peak.
2. Generate an AWR compare-periods report (`@?/rdbms/admin/awrddrpt.sql`) for a normal and a peak morning.
3. Identify top SQL by CPU and check for plan regressions.
4. List jobs that run at the same time:

```sql
SELECT job_name, last_start_date, last_run_duration
FROM dba_scheduler_jobs
WHERE enabled = 'TRUE'
ORDER BY last_start_date DESC;
```

#### b. Decision Table

| Finding | Action |
|---|---|
| A few inefficient SQL statements | Tune them or add SQL Plan Baselines |
| Batch jobs overlapping the business peak | Reschedule them |
| Mixed workloads competing | Prioritize OLTP with Resource Manager |
| Efficient workload that genuinely grew | Scale OCPUs |

**Bottom Line:** Measure impact, tune and reschedule first, and scale when real demand still exceeds capacity.

### Q60. How would you describe a production incident in an interview?

**Answer:**

Interviewers assess **judgment**, **ownership**, and **learning**. Use the **STAR** structure and quantify impact and results.

#### a. Example Answer

| STAR element | Example |
|---|---|
| **Situation** | A month-end batch generated three times the normal redo, and the FRA reached 98% on the production database. |
| **Task** | As the on-call DBA, I had to prevent an archiver hang without compromising recoverability. |
| **Action** | I confirmed the latest backup, ran an RMAN archived-log backup and deletion, temporarily increased the FRA size, and paused a non-critical reporting job. |
| **Result** | There was no outage and no data loss. Afterward, we added an 80% FRA alarm and increased archived-log backup frequency during month-end. |

#### b. What Makes the Answer Strong

1. Quantify impact (duration, users, data at risk).
2. Explain **why** each action was chosen.
3. Show that recoverability was protected before making changes.
4. End with a **preventive control**, not just the fix.

**Bottom Line:** Tell a concise STAR story with measurable impact and finish with how you prevented a recurrence.
