## 1. Core Architecture

### Q1. Explain regions, availability domains, and fault domains.

**Answer:**

OCI's physical infrastructure is organized in three levels. Each level is an **isolation boundary**, and resilient architectures spread redundant components across the strongest boundary their requirements and budget allow.

#### a. The Hierarchy

| Level | Description | Protects against |
|---|---|---|
| Region | Geographic area with one or more availability domains | Regional disaster (with a second region) |
| Availability domain (AD) | One or more isolated data centers with independent power, cooling, and network | Data-center failure |
| Fault domain (FD) | Grouping of hardware inside an AD; each AD has three | Hardware failure and some planned maintenance |

```text
Region (us-ashburn-1)
├── AD-1 ── FD-1 | FD-2 | FD-3
├── AD-2 ── FD-1 | FD-2 | FD-3
└── AD-3 ── FD-1 | FD-2 | FD-3
```

#### b. Resource Scope

| Scope | Examples |
|---|---|
| Global | IAM users, groups, policies, compartments, tag namespaces |
| Regional | VCNs, regional subnets, Object Storage, load balancers, Autonomous Database |
| AD-specific | Compute instances, block volumes, DB systems, AD-specific subnets |

#### c. CLI

```bash
oci iam availability-domain list
oci iam fault-domain list --availability-domain <ad-name> --compartment-id <tenancy-ocid>
```

**Bottom Line:** Spread replicas across FDs for hardware failures, across ADs for data-center failures, and across regions for disasters.

### Q2. How do you achieve high availability in a single-AD region?

**Answer:**

Many OCI regions have **only one availability domain**. In these regions, the **three fault domains** provide local redundancy, and a **second region** provides disaster recovery.

#### a. Reference Design

```text
Single-AD region
└── AD-1
    ├── FD-1: web-1, app-1, DB primary
    ├── FD-2: web-2, app-2, DB standby (Data Guard)
    └── FD-3: web-3, app-3
Load balancer (regional, managed redundancy) in front of the web tier
DR: second region with a cross-region standby and replicated Object Storage
```

#### b. Techniques

| Layer | Technique |
|---|---|
| Compute | Instance pool placement across all three FDs |
| Load balancing | OCI Load Balancer with health checks |
| Database | Data Guard standby in another FD, plus a cross-region standby |
| Storage | Object Storage (regional) plus cross-region replication |
| DR | Infrastructure as code and runbooks for the second region |

**Bottom Line:** In a single-AD region, fault domains provide HA and a second region provides DR.

### Q3. What is a tenancy?

**Answer:**

A **tenancy** is the secure, isolated partition of OCI created when an organization signs up. It is also the **root compartment**, the top of the IAM hierarchy, and the boundary for billing.

#### a. Key Attributes

| Attribute | Description |
|---|---|
| Tenancy OCID | Unique identifier of the tenancy (root compartment) |
| Home region | Region where IAM resources are created and mastered |
| Region subscriptions | Additional regions the tenancy can use |
| Object Storage namespace | Unique, auto-generated namespace used in OCIR and Object Storage |
| Service limits | Tenancy-wide maximums for each service |

#### b. Useful Commands

```bash
oci iam region-subscription list
oci os ns get
```

#### c. Best Practices

1. Do not create workload resources directly in the root compartment.
2. Protect tenancy administrators with MFA and keep a break-glass account.
3. Make IAM changes in the home region; they replicate to other regions.

**Bottom Line:** The tenancy is your organization's root container, IAM boundary, and billing boundary in OCI.

### Q4. What is a compartment, and is it a network boundary?

**Answer:**

A **compartment** is a logical container for organizing resources and controlling access with IAM policies. It is **not** a network boundary—resources in different compartments communicate freely if the network allows it.

#### a. Properties

| Property | Detail |
|---|---|
| Scope | Global (spans all regions) |
| Nesting | Up to six levels deep |
| Membership | Each resource belongs to exactly one compartment |
| Policies | Inherited by child compartments |
| Governance | Budgets and quotas can target compartments |
| Movement | Most resources can be moved between compartments |
| Deletion | Compartment must be empty |

#### b. Example Hierarchy

```text
Tenancy (root)
├── Shared
│   ├── Network     (VCNs, DRGs)
│   └── Security    (Vault, Cloud Guard)
└── Applications
    ├── Shop-Prod
    └── Shop-Dev
```

#### c. Compartment Versus VCN

| Question | Answered by |
|---|---|
| Who can manage this resource? | Compartment and IAM policy |
| What can communicate with this resource? | VCN, subnet, and security rules |

**Bottom Line:** Compartments control who can manage resources; VCNs and security rules control what can communicate.

### Q5. What is an OCID?

**Answer:**

An **Oracle Cloud Identifier (OCID)** is the unique ID that OCI assigns to every resource. Policies, the CLI, SDKs, Terraform, and support requests all reference resources by OCID.

#### a. Format

```text
ocid1.<resource-type>.<realm>.[region][.future-use].<unique-id>

ocid1.instance.oc1.iad.anuwcljr...   (regional resource: region is present)
ocid1.compartment.oc1..aaaaaaaa...   (global resource: region is empty)
```

#### b. Parts

| Part | Example | Meaning |
|---|---|---|
| Version | `ocid1` | OCID format version |
| Resource type | `instance`, `vcn`, `bucket` | Kind of resource |
| Realm | `oc1` | Commercial realm (government realms differ) |
| Region | `iad`, `phx` | Region of regional resources |
| Unique ID | `anuwcljr...` | Unique portion |

#### c. Usage Examples

```text
Allow group Auditors to read all-resources in tenancy
  where target.compartment.id = 'ocid1.compartment.oc1..<unique-id>'
```

**Bottom Line:** OCIDs uniquely identify every resource and are the reliable way to reference resources in automation and policies.

### Q6. What is the OCI shared responsibility model?

**Answer:**

Security and operations are **shared**. Oracle secures the cloud itself; the customer secures what they put **in** the cloud. The split moves toward Oracle as services become more managed.

#### a. Responsibility by Service Type

| Layer | IaaS (Compute) | PaaS (Autonomous Database) |
|---|---|---|
| Physical facilities, hardware, hypervisor | Oracle | Oracle |
| Operating system patching | Customer | Oracle |
| Database patching | Customer | Oracle |
| Network configuration (VCN, NSGs) | Customer | Customer |
| IAM policies and users | Customer | Customer |
| Data classification and encryption choices | Customer | Customer |
| Application security | Customer | Customer |

#### b. Interview Tip

The customer **always** owns identities, access policies, data, and configuration. Misconfiguration—such as public buckets or broad policies—remains the most common cause of cloud incidents.

**Bottom Line:** Oracle secures the platform; you secure identities, networks, data, and configuration on top of it.

## 2. Identity and Access Management

### Q7. What are the building blocks of OCI IAM?

**Answer:**

OCI IAM controls **who** can do **what** on **which** resources. Every authorization decision combines a principal, a group, a policy, and a target compartment.

#### a. Components

| Component | Description |
|---|---|
| Identity domain | Container for users, groups, applications, and authentication settings |
| User | A person or service account that signs in or calls APIs |
| Group | Collection of users that receive the same permissions |
| Dynamic group | Collection of resources (instances, functions) selected by rules |
| Policy | Allow statements that grant groups permissions |
| Compartment | Scope where policies apply |
| Principal | Any identity that calls OCI: user, instance, resource, or workload |

#### b. Authorization Flow

```text
Principal (user or resource) → member of group / dynamic group
   → policy: "Allow group X to <verb> <resource-type> in compartment Y"
   → request permitted only if a policy allows it
```

**Bottom Line:** Users and resources are placed in groups, and policies grant those groups verbs on resource types in compartments.

---

### Q8. What is the IAM policy syntax?

**Answer:**

A policy is a set of human-readable **Allow** statements. There are **no deny statements**—anything not explicitly allowed is denied.

#### a. Anatomy

```text
Allow <subject> to <verb> <resource-type> in <location> [where <conditions>]

Allow group NetworkAdmins to manage virtual-network-family in compartment Network
Allow group AppDevs to manage objects in compartment Shop where target.bucket.name = 'shop-assets'
Allow group Ops to use instances in compartment Shop where request.region = 'iad'
```

| Part | Examples |
|---|---|
| Subject | `group <name>`, `dynamic-group <name>`, `any-user`, `service <name>` |
| Verb | `inspect`, `read`, `use`, `manage` |
| Resource type | Individual (`instances`) or family (`instance-family`), or `all-resources` |
| Location | `tenancy` or `compartment <name>` (including nested paths) |
| Conditions | `target.bucket.name`, `request.permission`, `request.region` |

#### b. Where Policies Live

- A policy must be attached to the compartment it applies to **or an ancestor**.
- Policies in a parent compartment are **inherited** by all child compartments.
- Cross-tenancy access uses `Define`, `Endorse`, and `Admit` statements.

**Bottom Line:** Policies are allow-only statements: subject, verb, resource type, location, and optional conditions.

### Q9. What are the policy verbs?

**Answer:**

The four verbs are **cumulative**: each includes the permissions of the previous one. Choose the lowest verb that satisfies the requirement.

#### a. Verbs

| Verb | Access level | Typical audience |
|---|---|---|
| `inspect` | List resources without confidential details | Auditors |
| `read` | `inspect` plus view details and metadata | Read-only operators |
| `use` | `read` plus work with existing resources (actions vary by type) | Application operators |
| `manage` | Full control, including create and delete | Administrators |

#### b. Example: Object Storage

| Verb | Allows |
|---|---|
| `inspect buckets` | List buckets |
| `read objects` | List and download objects |
| `use objects` | `read` plus limited changes to existing objects |
| `manage objects` | Upload, overwrite, and delete objects |

Permissions for `use` differ by resource type—check the policy reference for each service.

**Bottom Line:** `inspect` < `read` < `use` < `manage`—grant the smallest verb that works.

### Q10. What are resource families? Give examples.

**Answer:**

A **resource family** groups related resource types so one statement can cover a whole service area. Families are convenient but broad; use individual types for least privilege.

#### a. Common Families

| Family | Includes (examples) |
|---|---|
| `instance-family` | Instances, instance images, volume attachments, console histories |
| `virtual-network-family` | VCNs, subnets, route tables, security lists, NSGs, gateways, DRGs |
| `volume-family` | Block volumes, boot volumes, backups, volume groups |
| `object-family` | Buckets and objects |
| `database-family` | DB systems, DB homes, databases, backups |
| `cluster-family` | OKE clusters and node pools |
| `all-resources` | Every resource type |

#### b. Family Versus Individual Type

```text
# Broad: everything networking
Allow group NetAdmins to manage virtual-network-family in compartment Network

# Narrow: only manage NSGs
Allow group AppTeam to manage network-security-groups in compartment Shop
```

**Bottom Line:** Families simplify policies; individual resource types tighten them.

### Q11. What is a dynamic group?

**Answer:**

A **dynamic group** contains **OCI resources** rather than users. Membership is defined by **matching rules** and is evaluated automatically, so new instances or functions gain permissions without manual steps.

#### a. Matching Rule Syntax

```text
ANY {rule1, rule2}     -- matches if any rule matches
ALL {rule1, rule2}     -- matches only if all rules match
```

#### b. Examples

| Purpose | Matching rule |
|---|---|
| All instances in a compartment | `ALL {instance.compartment.id = '<compartment-ocid>'}` |
| One specific instance | `ANY {instance.id = '<instance-ocid>'}` |
| Functions in a compartment | `ALL {resource.type = 'fnfunc', resource.compartment.id = '<compartment-ocid>'}` |
| Instances with a defined tag | `ALL {tag.Operations.Role.value = 'batch'}` |

#### c. Policy

```text
Allow dynamic-group batch-servers to manage objects in compartment Data
  where target.bucket.name = 'batch-output'
```

**Bottom Line:** Dynamic groups give resources an identity through rules, enabling keyless, least-privilege API access.

### Q12. What is an instance principal?

**Answer:**

An **instance principal** lets a compute instance call OCI APIs **as itself**. The instance obtains short-lived certificates from the instance metadata service, so no API keys are stored on the server.

#### a. How It Works

```text
Instance → instance metadata service → short-lived certificate (auto-rotated)
        → OCI API call signed with the certificate
        → IAM checks dynamic-group membership and policies
```

#### b. Setup

1. Create a dynamic group that matches the instance.
2. Write a policy for that dynamic group.
3. Use the instance principal authentication provider in code or the CLI.

#### c. Examples

```bash
oci os object list --bucket-name app-data --auth instance_principal
```

```java
var provider = InstancePrincipalsAuthenticationDetailsProvider.builder().build();
var objectStorage = ObjectStorageClient.builder().build(provider);
```

**Bottom Line:** Instance principals replace stored API keys with automatically rotated, instance-bound credentials.

### Q13. Which credential types does OCI use?

**Answer:**

Different interfaces use different **credential types**. Each must be scoped, rotated, and revoked when no longer needed.

#### a. Credential Types

| Credential | Used for | Per-user limit (typical) |
|---|---|---|
| Console password | Console sign-in | 1 |
| API signing key | CLI, SDKs, Terraform | 3 |
| Auth token | OCIR, Streaming Kafka API, some third-party integrations | 2 |
| Customer secret key | Amazon S3–compatible API | 2 |
| SMTP credentials | Email Delivery | Limited |

#### b. CLI Configuration File (`~/.oci/config`)

```ini
[DEFAULT]
user=ocid1.user.oc1..<unique-id>
fingerprint=<key-fingerprint>
key_file=~/.oci/oci_api_key.pem
tenancy=ocid1.tenancy.oc1..<unique-id>
region=us-ashburn-1
```

#### c. Best Practices

1. Prefer instance principals, resource principals, and workload identity for workloads.
2. Never commit private keys or tokens to source control.
3. Rotate keys regularly and remove unused credentials.

**Bottom Line:** Humans use passwords and MFA, tools use API keys or tokens, and workloads should use principals instead of stored credentials.

### Q14. How is federation used in OCI?

**Answer:**

**Federation** lets users sign in to OCI with an **existing corporate identity provider** (IdP), such as Microsoft Entra ID or Okta, using SAML. Identity is managed centrally, and OCI permissions come from **group mappings**.

#### a. Sign-In Flow

```text
User → OCI Console → redirect to corporate IdP (SAML)
     → IdP authenticates (MFA) → SAML assertion with group claims
     → OCI identity domain maps IdP groups to OCI groups → policies apply
```

#### b. Benefits

| Benefit | Description |
|---|---|
| Single sign-on | One corporate identity for all systems |
| Central lifecycle | Leavers lose access when disabled in the IdP |
| MFA | Enforced by the IdP or the identity domain |
| Provisioning | SCIM can synchronize users and groups |

#### c. Best Practices

1. Map IdP groups to OCI groups by role, not by individual user.
2. Keep at least one local break-glass administrator with strong MFA.
3. Review group mappings regularly.

**Bottom Line:** Federation centralizes authentication in the corporate IdP while OCI policies still control authorization.

## 3. Networking

### Q15. What is a Virtual Cloud Network?

**Answer:**

A **Virtual Cloud Network (VCN)** is a private, software-defined network in **one region**. It contains subnets, routing, security rules, and gateways, much like a traditional data-center network.

#### a. Properties

| Property | Detail |
|---|---|
| Scope | Regional (spans all ADs in the region) |
| Address space | One or more IPv4 CIDR blocks (each between /16 and /30), optional IPv6 |
| Default components | Default route table, default security list, default DHCP options |
| DNS | Optional DNS label enabling `<host>.<subnet>.<vcn>.oraclevcn.com` names |
| Reserved IPs | First two and last IP of each subnet |

#### b. Create a VCN (CLI)

```bash
oci network vcn create --compartment-id <compartment-ocid> \
  --cidr-blocks '["10.0.0.0/16"]' --display-name prod-vcn --dns-label prodvcn
```

#### c. Planning Tips

1. Choose CIDRs that do not overlap on-premises or other VCNs you may peer with.
2. Leave room for growth—adding CIDRs later is possible but complicates routing.
3. Create a DNS label at creation time.

**Bottom Line:** A VCN is your private regional network—plan non-overlapping CIDRs and DNS before creating it.

### Q16. Compare public and private subnets, and regional and AD-specific subnets.

**Answer:**

A subnet has two independent characteristics: **public or private** (whether VNICs may have public IPs) and **regional or AD-specific** (where its resources can be placed).

#### a. Comparison

| Type | Description | Typical use |
|---|---|---|
| Public subnet | VNICs can have public IP addresses | Load balancers, Bastion hosts |
| Private subnet | Public IPs prohibited | Application servers, databases |
| Regional subnet | Spans all ADs in the region | Recommended for HA |
| AD-specific subnet | Exists in one AD only | Legacy designs |

The public or private setting **cannot be changed** after creation.

#### b. Example Three-Tier Layout

| Subnet | CIDR | Type | Contents |
|---|---|---|---|
| `lb-subnet` | 10.0.0.0/24 | Public, regional | Load balancer |
| `app-subnet` | 10.0.1.0/24 | Private, regional | Application instances |
| `db-subnet` | 10.0.2.0/24 | Private, regional | Databases |

#### c. Subnet Settings

Each subnet has one route table, up to five security lists, DHCP options, and an optional DNS label.

**Bottom Line:** Use regional subnets, keep application and data tiers private, and expose only load balancers publicly.

### Q17. Which gateway meets each requirement?

**Answer:**

**Gateways** connect a VCN to destinations outside it. Each gateway serves a specific direction and destination.

#### a. Gateway Reference

| Requirement | Gateway | Notes |
|---|---|---|
| Inbound and outbound internet for public subnets | Internet gateway | One per VCN; instances need public IPs |
| Outbound-only internet for private subnets | NAT gateway | Hides private IPs; no inbound connections |
| Private access to OCI services | Service gateway | One per VCN; no internet path |
| On-premises connectivity | Dynamic Routing Gateway (DRG) | VPN and FastConnect attachments |
| VCN-to-VCN in the same region | DRG (or local peering gateway) | DRG is the modern approach |
| VCN-to-VCN across regions | DRG with a remote peering connection | Uses Oracle's backbone |

#### b. Service Gateway Targets

| CIDR label | Access |
|---|---|
| All `<region>` Services in Oracle Services Network | Object Storage plus other supported OCI services |
| OCI `<region>` Object Storage | Object Storage only |

**Bottom Line:** Internet gateway for public inbound, NAT for private outbound, service gateway for OCI services, and DRG for everything hybrid or cross-VCN.

### Q18. What is a route table?

**Answer:**

A **route table** sends traffic **leaving a subnet** to a target based on the destination. Traffic within the VCN is routed automatically and needs no rules.

#### a. Example: Private Application Subnet

| Destination | Target | Purpose |
|---|---|---|
| `0.0.0.0/0` | NAT gateway | Outbound internet |
| All `<region>` Services in Oracle Services Network | Service gateway | Object Storage and OCI services |
| `172.16.0.0/12` | DRG | On-premises networks |

#### b. Rules

1. The **most specific** matching route (longest prefix) wins.
2. Each subnet uses exactly **one** route table; several subnets can share one.
3. Gateways and DRG attachments can have their own route tables for **transit routing** (for example, through a firewall).

**Bottom Line:** Route tables direct outbound subnet traffic to gateways, with the most specific route winning.

### Q19. Compare security lists and network security groups.

**Answer:**

Both are **virtual firewalls** with ingress and egress rules. **Security lists** apply to an entire subnet; **network security groups (NSGs)** apply to selected VNICs and can reference other NSGs.

#### a. Comparison

| Aspect | Security list | NSG |
|---|---|---|
| Applies to | All VNICs in the subnet | VNICs added to the NSG |
| Limit (typical) | Up to 5 per subnet | Up to 5 per VNIC |
| Source or destination | CIDR or service | CIDR, service, or another NSG |
| Best for | Subnet baseline rules | Application-tier segmentation |

When both apply, traffic is allowed if **any** rule in any applicable list or NSG allows it.

#### b. NSG-to-NSG Example

| NSG | Ingress rule |
|---|---|
| `lb-nsg` | TCP 443 from `0.0.0.0/0` |
| `app-nsg` | TCP 8080 from `lb-nsg` |
| `db-nsg` | TCP 1521 from `app-nsg` |

Rules follow workloads automatically when instances scale or change IPs.

**Bottom Line:** Use security lists for subnet baselines and NSGs for precise, workload-based rules.

### Q20. What is the difference between stateful and stateless rules?

**Answer:**

A **stateful** rule tracks connections and automatically allows the **return traffic**. A **stateless** rule does not track connections, so return traffic needs its **own rule**.

#### a. Comparison

| Aspect | Stateful | Stateless |
|---|---|---|
| Return traffic | Allowed automatically | Requires an explicit rule |
| Connection tracking | Yes | No |
| Performance at very high volume | Limited by tracking tables | Better |
| Configuration effort | Lower | Higher |

#### b. Stateless Example

To allow HTTPS to a server with stateless rules, you need:

| Direction | Rule |
|---|---|
| Ingress | TCP destination port 443 from clients |
| Egress | TCP source port 443 to clients (ephemeral ports 1024–65535) |

**Bottom Line:** Stateful rules are simpler and the default; stateless rules suit very high-volume traffic but need explicit return rules.

### Q21. What is a Dynamic Routing Gateway?

**Answer:**

A **Dynamic Routing Gateway (DRG)** is a virtual router that connects VCNs to **on-premises networks**, **other VCNs**, and **other regions**. Modern DRGs support many attachments and their own route tables, enabling **transit routing**.

#### a. Attachment Types

| Attachment | Connects to |
|---|---|
| VCN attachment | VCNs in the same region |
| IPSec tunnel | On-premises through Site-to-Site VPN |
| Virtual circuit | On-premises through FastConnect |
| Remote peering connection (RPC) | A DRG in another region |

#### b. Routing Features

| Feature | Purpose |
|---|---|
| DRG route tables | Control routing per attachment |
| Import route distributions | Control which routes each table learns |
| VCN ingress route tables | Steer traffic through firewalls in a hub VCN |

**Bottom Line:** The DRG is OCI's central router for hybrid, multi-VCN, and cross-region connectivity.

---

### Q22. Compare Site-to-Site VPN and FastConnect.

**Answer:**

Both connect on-premises networks to OCI through a DRG. **VPN** uses encrypted tunnels over the internet; **FastConnect** uses a private, dedicated connection.

#### a. Comparison

| Aspect | Site-to-Site VPN | FastConnect |
|---|---|---|
| Path | IPSec over the public internet | Private dedicated circuit |
| Setup time | Quick | Requires a provider, partner, or colocation |
| Bandwidth | Moderate, variable | High (1 Gbps to 100 Gbps class ports) |
| Latency | Variable | Predictable |
| Encryption | IPSec built in | Optional (IPSec over FastConnect or MACsec) |
| Typical role | Low cost or backup | Primary enterprise connectivity |

#### b. Redundancy Design

```text
On-premises ──FastConnect (primary, BGP preferred)──┐
            ──FastConnect (second circuit) ────────┼──> DRG ──> VCNs
            ──Site-to-Site VPN (backup, 2 tunnels)──┘
```

Each IPSec connection provides **two tunnels**; configure both. Use BGP so failover between paths is automatic.

**Bottom Line:** VPN is fast and cheap to set up; FastConnect provides private, predictable bandwidth, often with VPN as backup.

### Q23. What is required for VCN peering?

**Answer:**

**Peering** connects VCNs so resources communicate using private IPs. It requires **non-overlapping address space**, connections, routes, and security rules on both sides.

#### a. Requirements

| Requirement | Detail |
|---|---|
| Non-overlapping CIDRs | Overlapping ranges cannot be peered |
| Peering connection | DRG attachments or local peering gateways (same region); RPC between DRGs (cross-region) |
| Routes | Each side routes the peer's CIDR to the DRG or peering gateway |
| Security rules | Each side allows the required traffic |
| IAM | Policies to create connections across compartments or tenancies |

#### b. Steps (Cross-Region)

1. Attach each VCN to a DRG in its region.
2. Create a remote peering connection on each DRG and connect them.
3. Add route rules for the peer CIDR.
4. Add NSG or security list rules.
5. Test connectivity and DNS resolution.

#### c. Note

Peering is **not transitive** by default. VCN A peered with B and B with C does not connect A to C unless transit routing is configured.

**Bottom Line:** Peering needs unique CIDRs, a connection, routes, and security rules on both sides.

### Q24. Compare the Load Balancer and Network Load Balancer.

**Answer:**

OCI offers two managed load balancers. The **Load Balancer** works at layer 7 with HTTP features; the **Network Load Balancer (NLB)** works at layer 4 with very low latency.

#### a. Comparison

| Feature | Load Balancer | Network Load Balancer |
|---|---|---|
| Layer | 7 (HTTP, HTTPS, HTTP/2) and 4 (TCP) | 4 (TCP, UDP) |
| Routing | Host and path rules, header rules | 5-tuple hashing |
| TLS | Termination, end-to-end, or passthrough | Passthrough |
| Client IP | Via `X-Forwarded-For` header | Preserved |
| WAF | Can attach a WAF policy | No |
| Shapes | Flexible bandwidth (minimum and maximum) | No shape selection |
| Visibility | Public or private | Public or private |

#### b. Choosing

| Requirement | Choose |
|---|---|
| Path-based routing for microservices | Load Balancer |
| TLS termination and WAF | Load Balancer |
| UDP or non-HTTP TCP protocols | Network Load Balancer |
| Source IP preservation and lowest latency | Network Load Balancer |

**Bottom Line:** Use the Load Balancer for HTTP-aware routing and TLS; use the NLB for raw layer 4 performance and source IP preservation.

### Q25. What are backend sets, health checks, and policies?

**Answer:**

A **backend set** is a group of backend servers that share a **load-balancing policy**, a **health check**, and optional **session persistence** and TLS settings. Listeners send traffic to backend sets.

#### a. Load-Balancing Policies

| Policy | Behavior | Use case |
|---|---|---|
| Weighted round robin | Rotates through backends by weight | Similar servers |
| Least connections | Chooses the backend with the fewest connections | Variable request durations |
| IP hash | Same client IP to the same backend | Simple stickiness |

#### b. Health Check Settings

| Setting | Example |
|---|---|
| Protocol and port | HTTP on 8080 |
| URL path | `/actuator/health/readiness` |
| Interval | 10 seconds |
| Timeout | 3 seconds |
| Retries | 3 |
| Expected status | 200 |

#### c. Other Options

- **Session persistence:** application cookie or load-balancer cookie stickiness.
- **TLS:** terminate at the listener, re-encrypt to backends, or pass through.

**Bottom Line:** Backend sets define where traffic goes, how it is distributed, and how unhealthy servers are detected and removed.

### Q26. Design a hub-and-spoke network for many workloads.

**Answer:**

A **hub-and-spoke** design centralizes shared services and inspection in a **hub VCN**, while workloads live in isolated **spoke VCNs**. The DRG routes all inter-spoke and on-premises traffic through the hub.

#### a. Topology

```text
                 On-premises (FastConnect / VPN)
                              │
                            [DRG]
              ┌───────────────┼───────────────┐
         Spoke VCN A      Hub VCN          Spoke VCN B
         (Shop-Prod)   (Network Firewall,   (HR-Prod)
                        DNS, shared tools)
```

#### b. Routing Steps

1. Attach the hub and all spokes to the DRG.
2. In each spoke subnet, route other spokes and on-premises CIDRs to the DRG.
3. In the DRG route table for spoke attachments, route everything to the **hub VCN attachment**.
4. In the hub VCN, use a **VCN ingress route table** on the DRG attachment to send traffic to the **Network Firewall**.
5. After inspection, route traffic from the firewall subnet back to the DRG.

#### c. Governance

| Practice | Benefit |
|---|---|
| Hub owned by the network team (separate compartment) | Central control of routing and inspection |
| Spokes owned by application teams | Autonomy without routing access |
| Non-overlapping CIDR plan | Future peering and growth |

**Bottom Line:** Hub-and-spoke with a DRG and firewall gives centralized inspection and control while isolating workloads in spokes.

### Q28. What are flexible shapes and OCPUs?

**Answer:**

A **shape** defines an instance's CPU, memory, network, and storage characteristics. **Flexible shapes** let you choose OCPUs and memory independently, so instances can be sized precisely.

#### a. Shape Naming

```text
VM.Standard.E5.Flex
│  │        │  └── Flexible shape
│  │        └───── Processor family and generation (E = AMD, A = Ampere Arm)
│  └────────────── Series (Standard, DenseIO, GPU, Optimized)
└───────────────── VM or BM (bare metal)
```

#### b. OCPU Versus vCPU

| Processor | 1 OCPU equals |
|---|---|
| x86 (Intel or AMD) | 1 physical core = 2 vCPUs (hardware threads) |
| Ampere Arm (A1) | 1 core = 1 vCPU |

#### c. Burstable Instances

Burstable flexible VMs run at a **baseline** (12.5% or 50% of the OCPUs) and burst to full capacity when needed—cost-effective for mostly idle workloads.

#### d. Launch Example

```bash
oci compute instance launch --compartment-id <compartment-ocid> \
  --availability-domain <ad-name> --subnet-id <subnet-ocid> \
  --image-id <image-ocid> --shape VM.Standard.E5.Flex \
  --shape-config '{"ocpus": 2, "memoryInGBs": 16}' --display-name app-1
```

**Bottom Line:** Flexible shapes size OCPUs and memory independently; on x86 one OCPU equals two vCPUs.

### Q29. What are custom images and boot volumes?

**Answer:**

An **image** is a template for an instance's boot disk. A **boot volume** is the block volume created from that image that holds the running instance's operating system.

#### a. Image Types

| Image type | Source |
|---|---|
| Platform images | Oracle-provided Oracle Linux, Ubuntu, Windows, and others |
| Custom images | Created from your configured instance |
| Marketplace images | Partner and Oracle software |
| Imported images | QCOW2 or VMDK files imported from Object Storage |

#### b. Boot Volume Capabilities

| Capability | Benefit |
|---|---|
| Preserve on termination | Keep the OS disk after deleting the instance |
| Backup and restore | Point-in-time protection |
| Clone | Fast copies for testing |
| Resize (increase) | More OS disk space |
| Launch from a boot volume | Recreate an instance from an existing disk |

#### c. Golden Image Pipeline

```text
Platform image → harden and install agents (Packer or scripts) → custom image
             → instance configuration → instance pool → patch and rebuild regularly
```

**Bottom Line:** Custom images standardize builds; boot volumes are independent disks that can be preserved, backed up, and cloned.

### Q30. What are instance configurations and instance pools?

**Answer:**

An **instance configuration** is a reusable **template** (shape, image, subnet, metadata). An **instance pool** uses that template to create and manage a **group of identical instances**.

#### a. Relationship

```text
Instance configuration (template)
        │
        ▼
Instance pool (size = 4, placement across ADs or FDs)
        ├── app-1 (FD-1)   ├── app-2 (FD-2)
        ├── app-3 (FD-3)   └── app-4 (FD-1)
        └── attached to a load balancer backend set
```

#### b. Features

| Feature | Benefit |
|---|---|
| Placement across ADs and FDs | Built-in high availability |
| Load balancer attachment | New instances register automatically |
| Autoscaling | Size changes from metrics or schedules |
| Pool-level actions | Start, stop, and reboot all instances together |

#### c. Updating Instances

Instance configurations are immutable. To roll out a new image, create a **new configuration**, update the pool to use it, and replace instances gradually.

**Bottom Line:** Instance configurations define what to launch; instance pools launch and manage identical instances at scale.

### Q31. How does compute autoscaling work?

**Answer:**

**Autoscaling** changes the size of an **instance pool** automatically. It works best for **stateless** tiers behind a load balancer.

#### a. Autoscaling Types

| Type | Trigger | Example |
|---|---|---|
| Metric-based | CPU or memory thresholds | Add 2 instances when CPU > 70%; remove 1 when CPU < 30% |
| Schedule-based | Cron schedule | Scale to 10 instances at 08:00 on weekdays, 3 at 20:00 |

#### b. Configuration Elements

| Element | Purpose |
|---|---|
| Minimum, maximum, initial size | Bounds for scaling |
| Scale-out and scale-in rules | Thresholds and step sizes |
| Cooldown period | Waiting time between actions (minimum around 300 seconds) |

#### c. Best Practices

1. Combine schedules for predictable peaks with metrics for surprises.
2. Use instance images that start quickly and register health checks.
3. Keep application state outside instances.

**Bottom Line:** Metric-based autoscaling handles unpredictable load, schedule-based autoscaling handles known peaks, and both require stateless instances.

### Q32. Compare vertical and horizontal scaling.

**Answer:**

**Vertical scaling** makes one instance bigger. **Horizontal scaling** adds more instances. Cloud architectures favor horizontal scaling because it also improves availability.

#### a. Comparison

| Aspect | Vertical (scale up) | Horizontal (scale out) |
|---|---|---|
| Method | Change shape, OCPUs, or memory | Add instances behind a load balancer |
| Downtime | Usually a reboot | None |
| Limit | Largest available shape | Practically unlimited |
| Availability | Single point of failure remains | Redundancy improves |
| Application requirement | None | Stateless design |

#### b. When to Use Each

| Situation | Approach |
|---|---|
| Legacy or stateful application | Vertical |
| Database that cannot scale out | Vertical (or read replicas) |
| Stateless web or API tier | Horizontal with autoscaling |

**Bottom Line:** Scale out stateless tiers for capacity and resilience; scale up when the workload cannot be distributed.

## 5. Storage

### Q33. Compare OCI storage services.

**Answer:**

OCI provides storage for every access pattern: **block** for disks, **file** for shared NFS, **object** for unstructured data, and **archive** for long-term retention.

#### a. Comparison

| Service | Access | Scope | Size range | Typical use |
|---|---|---|---|---|
| Block Volume | Attached disk (iSCSI or paravirtualized) | AD | 50 GB to 32 TB per volume | Databases, boot volumes |
| File Storage | NFSv3 shared file system | AD | Grows automatically | Shared content, lift-and-shift apps |
| Object Storage | HTTPS API (native and S3-compatible) | Region | Objects up to 10 TiB | Backups, media, data lakes, logs |
| Archive tier | Restore before reading | Region | Same as Object Storage | Compliance retention |

#### b. Decision Guide

```text
Needs a raw disk for one instance?        → Block Volume
Many instances share the same files?      → File Storage
Unstructured data accessed over HTTP?     → Object Storage
Rarely read, kept for years?              → Archive tier
```

**Bottom Line:** Match storage to the access pattern—block, file, object, or archive.

### Q34. What are the Block Volume performance levels?

**Answer:**

Block Volume performance is set by **Volume Performance Units (VPUs) per GB**. More VPUs give more IOPS and throughput per GB at a higher price, and performance can be changed **online**.

#### a. Performance Levels

| Level | VPUs per GB | Typical use |
|---|---|---|
| Lower Cost | 0 | Large sequential workloads, cold data |
| Balanced | 10 | Most workloads (default) |
| Higher Performance | 20 | Databases and I/O-intensive applications |
| Ultra High Performance | 30 to 120 | Most demanding databases (multipath attachment) |

IOPS and throughput scale with both **volume size** and **VPUs per GB**.

#### b. Auto-Tune

| Option | Behavior |
|---|---|
| Detached volume auto-tune | Lowers performance to Lower Cost while detached to save money |
| Performance-based auto-tune | Adjusts performance automatically within the limits you set |

#### c. Attachment Types

| Type | Notes |
|---|---|
| Paravirtualized | Simple, managed by the hypervisor |
| iSCSI | Higher performance; required for some features |

**Bottom Line:** Choose VPUs per GB for the workload's I/O needs, adjust online, and use auto-tune to control cost.

### Q35. Compare volume backups, clones, and volume groups.

**Answer:**

Block storage offers several ways to copy and protect data. They differ in **speed**, **storage location**, and **purpose**.

#### a. Comparison

| Feature | Description | Use case |
|---|---|---|
| Backup | Point-in-time copy stored in Object Storage | Recovery and retention |
| Clone | Immediate, independent copy in the same AD | Test environments, fast duplication |
| Volume group | Multiple volumes treated as one unit | Crash-consistent backups of multi-volume apps |
| Volume replication | Asynchronous copy to another AD or region | Disaster recovery |
| Cross-region backup copy | Copy backups to another region | Regional DR |

#### b. Backup Policies

| Policy | Description |
|---|---|
| Oracle-defined Bronze, Silver, Gold | Increasing backup frequency and retention |
| Custom policies | Your own schedule and retention, including cross-region copies |

#### c. Example

A three-volume database (data, logs, binaries) uses a **volume group backup** so all volumes reflect the same moment, plus **volume replication** to another region for DR.

**Bottom Line:** Back up for retention, clone for speed, group for consistency, and replicate for DR.

### Q36. Compare the Object Storage tiers.

**Answer:**

Object Storage tiers trade **access speed** against **storage cost**. Lower-cost tiers add **minimum retention periods** and **retrieval** costs or delays.

#### a. Tiers

| Tier | Access | Minimum retention | Typical use |
|---|---|---|---|
| Standard | Immediate | None | Frequently accessed data |
| Infrequent Access | Immediate, with retrieval fee | 31 days | Data read occasionally |
| Archive | Must be restored first (typically about an hour) | 90 days | Compliance and long-term retention |

### Q37. What are lifecycle policies, versioning, and retention rules?

**Answer:**

These bucket features automate **cost control**, **recovery**, and **compliance** for Object Storage.

#### a. Comparison

| Feature | Purpose |
|---|---|
| Lifecycle policies | Move objects to cheaper tiers or delete them by age and prefix |
| Versioning | Keep previous versions when objects are overwritten or deleted |
| Retention rules | Make objects immutable for a period (can be locked for compliance) |

#### b. Lifecycle Policy Example

```json
{
  "items": [
    {
      "name": "logs-to-infrequent-access",
      "action": "INFREQUENT_ACCESS",
      "timeAmount": 30,
      "timeUnit": "DAYS",
      "isEnabled": true,
      "objectNameFilter": { "inclusionPrefixes": ["logs/"] }
    },
    {
      "name": "logs-to-archive",
      "action": "ARCHIVE",
      "timeAmount": 180,
      "timeUnit": "DAYS",
      "isEnabled": true,
      "objectNameFilter": { "inclusionPrefixes": ["logs/"] }
    },
    {
      "name": "delete-old-logs",
      "action": "DELETE",
      "timeAmount": 2555,
      "timeUnit": "DAYS",
      "isEnabled": true,
      "objectNameFilter": { "inclusionPrefixes": ["logs/"] }
    }

```

- **Time-bound** rules protect objects for a period; **indefinite** rules protect until removed.

**Bottom Line:** Lifecycle policies cut cost, versioning enables recovery, and retention rules enforce immutability.

### Q38. What is a pre-authenticated request?

**Answer:**

A **pre-authenticated request (PAR)** is a URL that grants **time-limited** access to a bucket, prefix, or object **without OCI credentials**. Anyone who has the URL has the access, so treat it as a secret.

#### a. Access Types

| Access type | Allows |
|---|---|
| `ObjectRead` | Download one object |
| `ObjectWrite` | Upload one object |
| `ObjectReadWrite` | Read and write one object |
| `AnyObjectRead` | Download any object in the bucket |
| `AnyObjectWrite` | Upload any object to the bucket |
| `AnyObjectReadWrite` | Read and write any object in the bucket |

#### b. Create and Revoke

```bash
oci os preauth-request create --bucket-name partner-uploads --name partner-week41 \
  --access-type AnyObjectWrite --time-expires 2026-10-14T00:00:00Z

oci os preauth-request delete --bucket-name partner-uploads --par-id <par-id>
```

#### c. Best Practices

1. Use the shortest practical expiry and the narrowest access type.
2. Deny bucket listing unless it is required.
3. The URL is shown only once—share it through a secure channel.
4. Delete PARs when they are no longer needed.

**Bottom Line:** PARs give scoped, expiring access without accounts—keep them narrow, short-lived, and secret.

### Q39. How does Object Storage support disaster recovery?

**Answer:**

Object Storage is already highly durable within a region. For **regional** disaster recovery, use **cross-region replication** to copy objects asynchronously to a bucket in another region.

#### a. How Replication Works

| Aspect | Behavior |
|---|---|
| Configuration | Replication policy on the source bucket |
| Direction | One-way, source to destination |
| Timing | Asynchronous |
| Existing objects | Not copied—only objects created after the policy |
| Destination bucket | Read-only while replication is active |
| Failover | Stop replication to make the destination writable |

#### b. Required Policy

```text
Allow service objectstorage-us-ashburn-1 to manage object-family in compartment Data
```

#### c. DR Checklist

1. Copy pre-existing objects separately (for example, bulk copy).
2. Monitor replication lag.
3. Document how applications switch to the destination region.

**Bottom Line:** Cross-region replication protects new objects against regional loss; plan separately for existing data and failover.

### Q40. When do you use File Storage instead of Block Volume?

**Answer:**

Use **File Storage** when **multiple instances** need to read and write the **same files** concurrently over NFS. Block Volume is designed for a single instance at a time unless you use shareable attachments with a cluster-aware file system.

#### a. Comparison

| Aspect | File Storage | Block Volume |
|---|---|---|
| Protocol | NFSv3 | iSCSI or paravirtualized disk |
| Concurrent access | Many clients | Single instance (shareable only with a cluster file system) |
| Capacity | Grows automatically | Fixed size, can be expanded |
| Snapshots | File system snapshots | Volume backups |

#### b. Setup Components

| Component | Purpose |
|---|---|
| File system | The shared storage |
| Mount target | NFS endpoint (IP address) in a subnet |
| Export | Path plus export options (allowed source CIDRs, read-write or read-only, identity squash) |

#### c. Network Rules and Mounting

| Protocol | Ports |
|---|---|
| TCP | 111, 2048, 2049, 2050 |
| UDP | 111, 2048 |

```bash
sudo mount -t nfs -o vers=3 10.0.2.20:/shared /mnt/shared
```

**Bottom Line:** File Storage provides shared NFS access for many instances; Block Volume provides dedicated disks.

### Q42. What is the difference between HA and DR?

**Answer:**

**High availability (HA)** keeps the service running through **local** failures with little or no interruption. **Disaster recovery (DR)** restores service after a **large-scale** failure, usually in another region.

#### a. Comparison

| Aspect | High availability | Disaster recovery |
|---|---|---|
| Failure scope | Instance, FD, or AD | Entire region |
| Location | Same region | Second region |
| Recovery | Automatic, seconds to minutes | Planned failover, minutes to hours |
| Techniques | Load balancers, instance pools, RAC, local Data Guard | Cross-region Data Guard, replication, IaC rebuild |

#### b. Example by Tier

| Tier | HA | DR |
|---|---|---|
| Web and app | Instance pool across FDs or ADs | Infrastructure as code in a second region |
| Database | RAC or local standby | Cross-region standby |
| Files and objects | Regional durability | Cross-region replication |

**Bottom Line:** HA survives local failures automatically; DR recovers from regional disasters in another region.

---

### Q43. What are RPO and RTO?

**Answer:**

**RPO (Recovery Point Objective)** is the maximum acceptable **data loss**, measured in time. **RTO (Recovery Time Objective)** is the maximum acceptable **downtime**. Both are business decisions that drive architecture and cost.

#### a. Timeline

```text
  last recoverable point          disaster             service restored
  ──────────●───────────────────────X──────────────────────●──────▶ time
            |<──── RPO (data lost) ─>|<──── RTO (downtime) ──>|
```

#### b. Cost Trade-Off

| Target | Typical approach | Relative cost |
|---|---|---|
| RPO hours, RTO days | Backups to another region | Low |
| RPO minutes, RTO hours | Asynchronous replication plus pilot light | Medium |
| RPO seconds, RTO minutes | Warm standby with Data Guard | High |
| RPO near zero, RTO near zero | Active-active | Highest |

**Bottom Line:** Lower RPO and RTO cost more—agree on them with the business before designing DR.

---

### Q44. Compare DR models.

**Answer:**

DR models range from **backups only** to **active-active**. Each step up lowers RTO and RPO but increases cost and complexity.

#### a. Models

| Model | Standby state | Cost | Recovery speed |
|---|---|---|---|
| Backup and restore | No running resources; backups in the DR region | Lowest | Slowest (hours to days) |
| Pilot light | Data replicated; minimal core services running | Low | Moderate (hours) |
| Warm standby | Scaled-down full environment running | Medium | Fast (minutes) |
| Active-active | Full capacity serving traffic in both regions | Highest | Near instant |

#### b. OCI Building Blocks

| Need | OCI capability |
|---|---|
| Rebuild infrastructure | Terraform and Resource Manager stacks |
| Replicate data | Data Guard, Object Storage replication, volume replication |
| Orchestrate failover | **OCI Full Stack Disaster Recovery** plans |
| Redirect users | DNS traffic management steering policies |

**Bottom Line:** Pick the cheapest DR model that meets RTO and RPO, and automate failover with Full Stack DR and infrastructure as code.

### Q45. How does DNS support failover?

**Answer:**

OCI **DNS traffic management** returns different answers based on **health checks** and **steering policies**. When the primary region fails its health check, DNS directs users to the standby region.

#### a. Steering Policy Types

| Policy | Behavior |
|---|---|
| Failover | Primary answer while healthy; secondary when it fails |
| Load balancer | Weighted distribution across answers |
| Geolocation | Answer based on the user's location |
| ASN and IP prefix | Answer based on the user's network |

#### b. Failover Flow

```text
Health check fails for app.example.com in region A
  → steering policy returns region B's load balancer IP
  → clients resolve the new IP after the TTL expires
```

#### c. Requirements for It to Work

1. Data is replicated and the standby application is **ready**.
2. Low DNS TTLs (for example, 30–60 seconds).
3. Health checks test real application health, not just a port.
4. Regular failover tests.

**Bottom Line:** DNS steering with health checks redirects users, but only replicated data and a ready standby make failover succeed.

### Q46. How do you make an OCI database highly available?

**Answer:**

Database HA combines **redundant instances**, **replicated data**, **tested backups**, and **resilient application connections**.

#### a. Options by Service

| Service | HA mechanism | DR mechanism |
|---|---|---|
| Autonomous Database | Built-in redundancy | Autonomous Data Guard (local or cross-region) |
| Base Database Service | 2-node RAC (VM) | Data Guard across ADs or regions |
| Exadata Database Service | RAC across database servers | Data Guard |
| MySQL HeatWave | High-availability DB system (three instances across ADs or FDs) | Cross-region replication or backups |

#### b. Application Side

1. Connect through **database services**, not node addresses.
2. Configure connection retries and include both sites in connect strings.
3. Use connection pools that detect failover quickly.

**Bottom Line:** Use the service's built-in redundancy plus Data Guard or replication, and make applications reconnect automatically.

## 7. Security, Observability, and Governance

### Q47. What does OCI Vault provide?

**Answer:**

**OCI Vault** centrally manages **encryption keys** and **secrets**. It lets you control key lifecycles for OCI services and keep credentials out of code.

#### a. Capabilities

| Capability | Detail |
|---|---|
| Key protection | HSM-protected (FIPS 140-2 Level 3) or software-protected keys |

  where target.key.id = '<key-ocid>'

#### c. Best Practices

1. Separate key administrators from data owners.

3. Never delete a key until no data or backups depend on it.

**Bottom Line:** Vault manages keys and secrets with HSM protection, rotation, and IAM control.

### Q48. What are Cloud Guard and Security Zones?

|---|---|

#### b. Security Zone Examples

| Policy type | Example |
|---|---|
| Storage | Deny public buckets |
| Encryption | Require customer-managed Vault keys |
| Network | Deny public subnets or public IPs for databases |
| Resource movement | Deny moving resources out of the zone |

#### c. Detective Versus Preventive

| Control | When it acts | Example |
|---|---|---|
| Security Zones | Before the change | Public bucket creation is rejected |
| Cloud Guard | After the change | Public bucket is detected and can be made private |

**Bottom Line:** Security Zones prevent risky configurations; Cloud Guard detects and responds to the rest.

|---|---|---|
| Monitoring | Metrics and alarms | Alarm when CPU > 80% for 5 minutes |
| Logging | Service, custom, and audit logs | VCN flow logs, load balancer access logs |
| Audit | Records every OCI API call (who, what, when) | Who deleted a bucket? (default retention 365 days) |
| Events | React to resource state changes | Trigger a function when an object is uploaded |
| Notifications | Deliver messages to subscribers | Email, Slack, PagerDuty, SMS, HTTPS, Functions |

#### b. Event Rule Example

```json
{
  "eventType": ["com.oraclecloud.objectstorage.createobject"],
  "data": { "additionalDetails": { "bucketName": ["invoices"] } }
}
```

#### c. Typical Flow

```text
Metric alarm or event rule → Notifications topic → email, chat, pager, or function
```

**Bottom Line:** Monitoring detects, Logging and Audit record, Events react, and Notifications deliver.

### Q51. How are costs tracked and controlled?

### Q52. Compare service limits and compartment quotas.

**Answer:**

**Service limits** are tenancy-wide maximums set by Oracle. **Compartment quotas** are restrictions **you** define to control how much each compartment can use within those limits.

#### a. Comparison

| Aspect | Service limits | Compartment quotas |
|---|---|---|
| Set by | Oracle | Tenancy administrators |
| Scope | Tenancy (often per region or AD) | Compartment |
| Change | Request an increase | Edit the quota policy |
| Purpose | Platform protection | Governance and cost control |

#### b. Quota Statements

```text
zero compute-core quotas in compartment Sandbox
set compute-core quota standard-e4-core-count to 20 in compartment Dev
set compute-core quota standard-e4-core-count to 40 in compartment Prod where request.region = us-ashburn-1
```

#### c. Check Availability

```bash
oci limits resource-availability get --compartment-id <compartment-ocid> \
  --service-name compute --limit-name standard-e4-core-count \
  --availability-domain <ad-name>
```

**Bottom Line:** Service limits cap the tenancy; quotas divide that capacity among compartments.

### Q53. How should an enterprise landing zone be structured?

**Answer:**

A **landing zone** is a pre-built, secure foundation—compartments, IAM, networking, security services, and governance—that all workloads build on. Oracle provides the **OCI CIS Landing Zone** Terraform templates aligned with the CIS OCI Foundations Benchmark.

#### a. Compartment Design

```text
Tenancy (root)
└── Landing-Zone
    ├── Network        (hub VCN, DRG, firewalls)
    ├── Security       (Vault, Cloud Guard, Bastion, logging)
    ├── Shared-Services
    └── Applications
        ├── App1-Prod   └── App1-NonProd
        └── App2-Prod   └── App2-NonProd
```

#### b. Group and Policy Design

| Group | Permissions |
|---|---|
| Network admins | Manage networking in `Network` |
| Security admins | Manage Vault, Cloud Guard, and Security Zones in `Security` |
| Application admins | Manage application resources in their compartments; use the network |
| Auditors | Read-only across the tenancy |
| Break-glass admins | `manage all-resources` in the tenancy, tightly controlled |

#### c. Guardrails

1. Budgets, quotas, and tag defaults per compartment.
2. Cloud Guard enabled at the root and Security Zones for sensitive compartments.
3. Audit and flow logs archived through Connector Hub.
4. Infrastructure changes only through Terraform.

**Bottom Line:** A landing zone gives every workload a secure, governed foundation with separation of duties from day one.

## 8. Scenario-Based Questions

### Q54. A private instance cannot download OS patches. How do you troubleshoot it?

**Answer:**

Work **layer by layer** from the instance outward: route, gateway, security rules, DNS, and OS configuration.

#### a. Checklist

| Layer | Check | How |
|---|---|---|
| Route | Subnet route table sends `0.0.0.0/0` to a NAT gateway | `oci network route-table get --rt-id <ocid>` |
| Gateway | NAT gateway exists and is not blocking traffic | Console or CLI |
| Security | Egress allowed on 80 and 443 | Security lists and NSGs |
| DNS | Repository host names resolve | `nslookup yum.us-ashburn-1.oci.oraclecloud.com` |
| OS | No local firewall or proxy blocking | `sudo firewall-cmd --list-all` |

#### b. Note on Oracle Linux

Oracle Linux instances can use **regional OCI yum mirrors** through a **service gateway**, so a NAT gateway is not required for Oracle-provided packages.

#### c. Validate the Path

Use **VCN Network Path Analyzer** to simulate the path from the instance to the destination and identify the blocking component.

**Bottom Line:** Check the route, gateway, security rules, DNS, and OS in order, and use Network Path Analyzer to confirm.

### Q55. A user gets `NotAuthorizedOrNotFound` when launching an instance. What do you check?

**Answer:**

Launching an instance touches **several resource types**, often in **different compartments**. The error means at least one required permission is missing (or the resource truly does not exist).

#### a. Policies Typically Required

```text
Allow group InstanceLaunchers to manage instance-family in compartment App
Allow group InstanceLaunchers to use volume-family in compartment App
Allow group InstanceLaunchers to use virtual-network-family in compartment Network
Allow group InstanceLaunchers to read app-catalog-listing in tenancy
```

#### b. Checklist

| Check | Why |
|---|---|
| User is in the expected group | Policies apply to groups |
| Policy is attached to the correct compartment or an ancestor | Location matters |
| Network permissions cover the subnet's compartment | Subnet is often in a shared `Network` compartment |
| Image access (Marketplace images need catalog permissions) | Image read is part of launch |
| Region subscription and service limits | Can block launches |

**Bottom Line:** Instance launches need compute, volume, network, and image permissions—often across compartments.

### Q56. Two VCNs with overlapping CIDRs must communicate. What do you do?

**Answer:**

OCI cannot route between overlapping address spaces, so **peering is impossible** until the overlap is removed. Choose the least disruptive remediation.

#### a. Options

| Option | Effort | Notes |
|---|---|---|
| Re-address one VCN | High | Cleanest long-term fix |
| Add a new non-overlapping CIDR and migrate workloads | Medium | Gradual migration |
| Expose services through private load balancers or private endpoints | Medium | Avoids full network connectivity |
| NAT appliance between networks | Medium to high | Complex; last resort |

#### b. Prevention

1. Maintain an **IP address management (IPAM)** plan for all VCNs and on-premises ranges.
2. Allocate VCN CIDRs from a central registry.
3. Review CIDRs during architecture approval.

**Bottom Line:** Remove the overlap (re-address or migrate), and prevent recurrence with central IP address planning.

### Q57. Object Storage costs rose unexpectedly. How do you investigate?

**Answer:**

Identify **which bucket** is growing and **why**, then apply lifecycle and cleanup controls.

#### a. Investigation Steps

| Step | Action |
|---|---|
| 1 | Cost Analysis filtered by service, compartment, and tags |
| 2 | Check bucket size and object count |
| 3 | Look for many previous object versions |
| 4 | Look for incomplete multipart uploads |
| 5 | Check replication, retrieval, and data transfer charges |

```bash
oci os bucket get --bucket-name app-logs --fields approximateSize --fields approximateCount
oci os multipart list --bucket-name app-logs
```

#### b. Remediation

| Finding | Fix |
|---|---|
| Cold data in Standard | Lifecycle rules to Infrequent Access or Archive |
| Old versions accumulating | Lifecycle rule for previous versions |
| Abandoned multipart uploads | Lifecycle `ABORT` rule for uploads |
| No ownership tags | Enforce tag defaults |

Add a **budget alert** so the next increase is detected early.

**Bottom Line:** Find the growing bucket, remove waste, tier cold data, and alert on future growth.

### Q58. A partner needs write access to one bucket for one week without an OCI account. What do you use?

**Answer:**

Use a **pre-authenticated request (PAR)** scoped to write-only access with a one-week expiry. It avoids creating users for external parties.

#### a. Create a Narrow PAR

```bash
oci os preauth-request create --bucket-name partner-uploads --name acme-week41 \
  --access-type AnyObjectWrite --bucket-listing-action Deny \
  --time-expires 2026-10-14T00:00:00Z
```

#### b. Security Controls

| Control | Purpose |
|---|---|
| Dedicated bucket | Isolates partner data |
| Write-only, no listing | Partner cannot read other files |
| One-week expiry | Access ends automatically |
| Events rule on object creation | Notify the team of new uploads |
| Delete the PAR after use | Early revocation |

**Bottom Line:** A write-only, non-listable, short-lived PAR on a dedicated bucket gives partners safe temporary access.

### Q59. Design a secure, highly available three-tier web application.

**Answer:**

Combine **regional networking**, **redundant tiers**, **least-privilege security**, and **DR** into one design.

#### a. Architecture

```text
Internet ──> WAF ──> Public Load Balancer (public subnet, lb-nsg)
                         │ HTTPS 443 → 8080
                         ▼
            Instance pool across ADs/FDs (private app subnet, app-nsg)
                         │ TCP 1521
                         ▼
            Database primary + Data Guard standby (private db subnet, db-nsg)

NAT gateway (patches) | Service gateway (Object Storage, backups) | Bastion (admin)
Vault (keys, secrets) | Cloud Guard | Monitoring and Logging
DR: standby region with cross-region Data Guard, replicated buckets, Terraform
```

#### b. Security Rules

| NSG | Ingress |
|---|---|
| `lb-nsg` | TCP 443 from the internet (through WAF) |
| `app-nsg` | TCP 8080 from `lb-nsg`; TCP 22 from Bastion |
| `db-nsg` | TCP 1521 from `app-nsg`; TCP 22 from Bastion |

#### c. Availability and Recovery

| Tier | HA | DR |
|---|---|---|
| Load balancer | Managed redundancy | DNS failover to the second region |
| Application | Instance pool with autoscaling | Terraform-built pool in the DR region |
| Database | Data Guard across ADs or FDs | Cross-region standby |
| Files and objects | Regional durability | Cross-region replication |

**Bottom Line:** Public entry only through WAF and the load balancer, private tiers with NSG chaining, redundancy across ADs or FDs, and a tested DR region.

### Q60. How do you justify an architecture decision in an interview?

**Answer:**

Interviewers want to see **structured trade-off thinking**, not memorized services. Use a consistent framework and connect each choice to a requirement.

#### a. Framework

| Step | Question |
|---|---|
| Requirement | What must the design achieve (availability, RPO/RTO, security, cost)? |
| Options | Which alternatives did you consider? |
| Trade-offs | What does each cost and risk? |
| Decision | Which option did you choose? |
| Validation | How do you prove it meets the requirement? |

#### b. Worked Example: Hybrid Connectivity

| Step | Answer |
|---|---|
| Requirement | 2 Gbps of steady replication traffic with predictable latency |
| Options | Site-to-Site VPN, or FastConnect with VPN backup |
| Trade-offs | VPN is cheap but variable; FastConnect costs more but is predictable |
| Decision | Redundant FastConnect circuits with VPN as backup |
| Validation | Load test, failover test, and latency monitoring |

**Bottom Line:** Tie every decision to a requirement, explain trade-offs, and show how you validated the result—choose the simplest design that meets the need.
