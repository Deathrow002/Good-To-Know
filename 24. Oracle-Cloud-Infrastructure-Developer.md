## 1. Cloud-Native Fundamentals

### Q1. What is a cloud-native application?

**Answer:**

A **cloud-native application** is designed to exploit cloud capabilities—elastic infrastructure, managed services, automation, and on-demand scaling—and to **expect failure**. It is typically built from small, independently deployable services packaged as containers or functions.

#### a. Core Characteristics

| Characteristic | Meaning |
|---|---|
| Microservices | Small services organized around business capabilities |
| Containers or functions | Immutable, portable deployment units |
| Dynamic orchestration | Platforms such as Kubernetes schedule, heal, and scale workloads |
| Automation | CI/CD pipelines and infrastructure as code |
| Observability | Metrics, logs, and traces built in from the start |
| Resilience | Timeouts, retries, and graceful degradation |

#### b. Mapping to OCI Services

| Need | OCI service |
|---|---|
| Container images | OCI Container Registry (OCIR) |
| Container orchestration | Oracle Kubernetes Engine (OKE), Container Instances |
| Serverless code | OCI Functions |
| API exposure | API Gateway |
| Messaging and events | Streaming, Queue, Events, Notifications |
| CI/CD | OCI DevOps |
| Observability | Monitoring, Logging, Application Performance Monitoring (APM) |
| Secrets and keys | OCI Vault |

**Bottom Line:** Cloud-native applications are built from automated, observable, independently deployable components that assume failure and scale elastically.

### Q2. What are the trade-offs of microservices?

**Answer:**

Microservices trade **in-process simplicity** for **independent deployability and scaling**. They solve organizational and scaling problems but introduce distributed-system complexity.

#### a. Benefits Versus Costs

| Benefits | Costs |
|---|---|
| Independent deployment and scaling | Network latency and partial failures |
| Team autonomy and ownership | Distributed data consistency (no simple ACID transactions) |
| Fault isolation | Complex testing, debugging, and observability |
| Technology flexibility | More infrastructure, pipelines, and security boundaries |

#### b. When a Modular Monolith Is Better

- A small team owns the whole application.
- The domain boundaries are not yet well understood.
- Scaling needs are uniform across the application.

#### c. Common Pitfalls

1. **Distributed monolith:** services that must be deployed together because they share databases or synchronous call chains.
2. **Chatty APIs:** many fine-grained calls per user request, multiplying latency.
3. **Shared database:** schema changes break multiple services.

Design services around **bounded contexts**, give each service its own data, and prefer asynchronous events between services.

**Bottom Line:** Adopt microservices when independent deployment and scaling justify the added operational cost—not by default.

### Q3. Why should services be stateless?

**Answer:**

A **stateless** service keeps no client or session data in local memory or disk between requests. Any instance can serve any request, so instances can be added, removed, or replaced at any time.

#### a. Where State Should Live

| State type | Anti-pattern | Cloud-native pattern on OCI |
|---|---|---|
| User sessions | In-memory session on one instance | OCI Cache (Redis) or a database |
| Uploaded files | Local disk | Object Storage |
| Business data | Embedded database file | Autonomous Database, MySQL HeatWave |
| Background work | In-memory queue | OCI Queue or Streaming |
| Configuration | Hard-coded values | Environment variables, ConfigMaps, Vault |

#### b. Benefits

- Load balancers can route to any healthy instance.
- Autoscaling adds and removes instances without data loss.
- Rolling updates and node failures do not drop user sessions.

**Bottom Line:** Externalize state to managed services so compute instances become disposable and horizontally scalable.

### Q4. What is idempotency, and why does it matter?

**Answer:**

An operation is **idempotent** if performing it multiple times has the same effect as performing it once. In distributed systems, clients retry, queues redeliver, and events are duplicated, so non-idempotent operations create duplicate side effects such as double charges.

#### a. HTTP Method Semantics

| Method | Idempotent? | Example |
|---|---|---|
| GET | Yes | Read an order |
| PUT | Yes | Replace an order's address |
| DELETE | Yes | Cancel an order |
| POST | No (by default) | Create an order |
| PATCH | Not necessarily | Increment a counter |

#### b. Idempotency Key Example (Spring Boot)

```java
@PostMapping("/orders")
public ResponseEntity<Order> create(@RequestHeader("Idempotency-Key") String key,
                                    @RequestBody OrderRequest request) {
    return idempotencyStore.find(key)
        .map(ResponseEntity::ok)                      // duplicate: return the original result
        .orElseGet(() -> {
            Order order = orderService.create(request);
            idempotencyStore.save(key, order);        // unique constraint on the key
            return ResponseEntity.status(HttpStatus.CREATED).body(order);
        });
}
```

A **unique constraint** on the key protects against concurrent duplicates that pass the lookup at the same time.

#### c. Techniques

1. Client-generated idempotency keys.
2. Unique business keys (order number, event ID).
3. Conditional writes (optimistic locking with version columns).
4. Deduplication tables for consumed events.

**Bottom Line:** Assume every request and message can arrive more than once, and design writes so duplicates are harmless.

### Q5. What resilience patterns should cloud-native services use?

**Answer:**

Remote calls fail, slow down, and time out. **Resilience patterns** stop one failing dependency from cascading into a full outage.

#### a. Core Patterns

| Pattern | Problem solved | Typical setting |
|---|---|---|
| Timeout | Threads blocked on slow calls | Shorter than the caller's own timeout |
| Retry with exponential backoff and jitter | Transient failures | 2–3 attempts, randomized delays |
| Circuit breaker | Repeated calls to a failing dependency | Open after a failure-rate threshold |
| Bulkhead | One dependency exhausting all threads | Separate pools per dependency |
| Fallback | Total failure of a non-critical dependency | Cached or default response |

#### b. Circuit Breaker Example (Resilience4j)

```java
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
        .failureRateThreshold(50)
        .slidingWindowSize(20)
        .waitDurationInOpenState(Duration.ofSeconds(30))
        .build();

CircuitBreaker breaker = CircuitBreaker.of("inventory", config);
Supplier<Stock> guarded = CircuitBreaker.decorateSupplier(breaker,
        () -> inventoryClient.getStock(sku));
```

#### c. Backoff With Jitter

```text
delay = random(0, min(maxDelay, baseDelay * 2^attempt))
```

Jitter prevents many clients from retrying at the same instant and overwhelming a recovering service.

**Bottom Line:** Combine timeouts, bounded retries with jitter, circuit breakers, and fallbacks so failures stay contained.

### Q6. How should configuration be managed?

**Answer:**

Following the **twelve-factor** principle, configuration that differs between environments must live **outside the code and image**. The same immutable image is then promoted from development to production with different configuration.

#### a. Configuration Sources on OCI

| Configuration type | Mechanism |
|---|---|
| Non-sensitive settings on OKE | Kubernetes ConfigMaps or environment variables |
| Non-sensitive settings for Functions | Application or function configuration |
| Secrets (passwords, tokens, keys) | OCI Vault secrets |
| Secrets inside OKE pods | Secrets Store CSI Driver with the OCI provider, or the SDK at runtime |
| Pipeline secrets | Vault variables in OCI DevOps build specifications |

#### b. Examples

```bash
# Functions configuration (non-sensitive)
fn config app orders-app ORDERS_API_URL https://api.example.com
fn config function orders-app orders-fn LOG_LEVEL INFO
```

```yaml
# Kubernetes ConfigMap consumed as environment variables
apiVersion: v1
kind: ConfigMap
metadata:
  name: orders-config
data:
  SPRING_PROFILES_ACTIVE: "prod"
  ORDERS_PAGE_SIZE: "50"
```

#### c. Rules

1. Never commit secrets to Git, images, or ConfigMaps.
2. Validate configuration at startup and fail fast when values are missing.
3. Version configuration changes and roll them out like code.

**Bottom Line:** Keep configuration external, keep secrets in Vault, and promote one immutable image across environments.

## 2. Containers and OCI Container Registry

### Q7. What is the difference between a container and a virtual machine?

**Answer:**

A **virtual machine** virtualizes hardware and runs a full guest operating system. A **container** virtualizes the operating system: it packages the application and its dependencies but **shares the host kernel**, isolated with namespaces and cgroups.

#### a. Comparison

| Aspect | Virtual machine | Container |
|---|---|---|
| Isolation | Strong (hypervisor boundary) | Process-level (kernel namespaces) |
| Startup time | Tens of seconds to minutes | Milliseconds to seconds |
| Size | Gigabytes | Megabytes |
| Density | Lower | Higher |
| OS | Any guest OS | Must match the host kernel type |

#### b. Layering

```text
VM:        App | Libraries | Guest OS | Hypervisor | Host hardware
Container: App | Libraries | Container runtime | Host OS kernel | Host hardware
```

#### c. OCI Options

| Need | Option |
|---|---|
| Full OS control or legacy software | Compute VM |
| Run a container without managing servers | Container Instances |
| Orchestrate many containers | OKE |

**Bottom Line:** Containers are lightweight and fast because they share the host kernel; VMs provide stronger isolation with more overhead.

### Q8. Why use a multi-stage Docker build?

**Answer:**

A **multi-stage build** compiles the application in a build stage with a full JDK and tools, then copies **only the runtime artifact** into a small final image. The final image contains no compilers, source code, or build caches.

#### a. Example

```dockerfile
# Build stage
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY . .
RUN ./mvnw -q -DskipTests package

# Runtime stage
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/target/app.jar app.jar
USER 10001
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75"
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

#### b. Benefits

| Benefit | Why it matters |
|---|---|
| Smaller image | Faster pulls, faster scaling, lower storage cost |
| Smaller attack surface | Fewer packages with vulnerabilities |
| No source or build secrets | Reduced data exposure |
| Reproducible builds | Same Dockerfile everywhere |

#### c. Tips

1. Add a `.dockerignore` file to exclude `target/`, `.git/`, and local secrets.
2. Copy dependency descriptors first to reuse layer caching.
3. Consider Cloud Native Buildpacks (`./mvnw spring-boot:build-image`) or Jib for Java images without a Dockerfile.

**Bottom Line:** Multi-stage builds produce small, secure runtime images that contain only what the application needs.

### Q9. What is OCIR?

**Answer:**

**OCI Container Registry (OCIR)** is a managed, Open Container Initiative–compliant registry for storing and sharing container images and other artifacts. It is **regional**, integrated with **IAM**, and works with standard Docker and OCI tooling.

#### a. Image Naming

```text
<region-key>.ocir.io/<tenancy-namespace>/<repository>:<tag>
Example: iad.ocir.io/axaxnpcrorw5/shop/orders:1.4.0
```

| Part | Example | Meaning |
|---|---|---|
| Region key | `iad`, `phx`, `fra`, `lhr` | Regional registry endpoint |
| Tenancy namespace | `axaxnpcrorw5` | Unique Object Storage namespace of the tenancy |
| Repository | `shop/orders` | Image name, optionally with a path |
| Tag | `1.4.0` | Version label |

#### b. Key Features

| Feature | Description |
|---|---|
| Private or public repositories | Private by default; public allows anonymous pulls |
| IAM integration | Policies on the `repos` resource type |
| Vulnerability scanning | Integration with the Vulnerability Scanning service |
| Image signing | Sign images with Vault keys and verify them in OKE |
| Auto-create on push | Optional tenancy setting to create repositories on first push |

#### c. IAM Example

```text
Allow group Developers to manage repos in compartment Shop-Dev
Allow group Deployers to read repos in compartment Shop-Prod
```

**Bottom Line:** OCIR is OCI's regional, IAM-integrated container registry; images are addressed by region key, tenancy namespace, repository, and tag.

### Q10. How do you push an image to OCIR?

**Answer:**

Authenticate Docker to the regional endpoint with an **auth token**, tag the image with the full OCIR path, and push it.

#### a. Steps

```bash
# 1. Find the tenancy namespace
oci os ns get

# 2. Log in (password = auth token, not the console password)
docker login iad.ocir.io
# Username: <tenancy-namespace>/<username>
# Federated users may need: <tenancy-namespace>/<identity-domain>/<username>

# 3. Tag and push
docker tag orders:1.4.0 iad.ocir.io/<tenancy-namespace>/shop/orders:1.4.0
docker push iad.ocir.io/<tenancy-namespace>/shop/orders:1.4.0
```

#### b. Pulling From OKE

```bash
kubectl create secret docker-registry ocir-secret \
  --docker-server=iad.ocir.io \
  --docker-username='<tenancy-namespace>/<username>' \
  --docker-password='<auth-token>' \
  --docker-email='<email>'
```

```yaml
spec:
  imagePullSecrets:
    - name: ocir-secret
  containers:
    - name: orders
      image: iad.ocir.io/<tenancy-namespace>/shop/orders:1.4.0
```

#### c. Best Practices

1. Create auth tokens for a dedicated service user, not a personal account.
2. Let OCI DevOps push images using its **resource principal** so pipelines need no tokens.
3. Rotate and revoke tokens regularly (each user can hold only a small number of auth tokens).

**Bottom Line:** Log in with an auth token, tag with the full OCIR path, and prefer resource principals in pipelines.

### Q11. Why deploy by image digest instead of a mutable tag?

**Answer:**

A **tag** is a movable label—`latest` or even `1.4.0` can be overwritten to point to different content. A **digest** (`sha256:...`) is a content hash that always identifies **exactly the same image**.

#### a. Comparison

| Aspect | Tag | Digest |
|---|---|---|
| Example | `orders:1.4.0` | `orders@sha256:9f86d08...` |
| Mutable | Yes | No |
| Reproducible deployments | Not guaranteed | Guaranteed |
| Human readable | Yes | No |

#### b. Usage

```bash
docker inspect --format='{{index .RepoDigests 0}}' iad.ocir.io/<ns>/shop/orders:1.4.0
```

```yaml
image: iad.ocir.io/<ns>/shop/orders@sha256:<digest>
```

#### c. Tagging Strategy

| Tag | Use |
|---|---|
| Semantic version (`1.4.0`) | Human-readable release |
| Git commit SHA (`a1b2c3d`) | Traceability to source |
| `latest` | Avoid in production |

**Bottom Line:** Tag for humans, deploy by digest for machines—digests make rollbacks and audits exact.

### Q12. How should container images be secured?

**Answer:**

Secure the image across its whole lifecycle: **build**, **registry**, and **runtime**. Most container incidents come from vulnerable dependencies, embedded secrets, or over-privileged containers.

#### a. Lifecycle Controls

| Stage | Controls |
|---|---|
| Build | Minimal trusted base images, pinned versions, no secrets, multi-stage builds |
| Registry | Vulnerability scanning, image signing, private repositories, retention policies |
| Runtime | Non-root user, read-only root file system, dropped capabilities, signed-image enforcement |

#### b. Kubernetes Security Context

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop: ["ALL"]
```

#### c. OCI-Specific Capabilities

1. **Vulnerability Scanning** for OCIR repositories reports CVEs in images.
2. **Image signing** with Vault keys, plus OKE **image verification policies**, so clusters run only signed images.
3. Regular rebuilds pick up patched base images.

**Bottom Line:** Build minimal images, scan and sign them, and run them as non-root with the least privileges possible.

## 3. Oracle Kubernetes Engine (OKE)

### Q13. What is OKE?

**Answer:**

**Oracle Kubernetes Engine (OKE)** is OCI's managed, CNCF-conformant Kubernetes service. Oracle operates the **control plane**; you run workloads on worker nodes and integrate with OCI networking, load balancers, storage, and IAM.

#### a. Architecture

```text
Oracle-managed control plane: API server | etcd | scheduler | controller managers
                     │
Customer data plane: Managed node pools | Self-managed nodes | Virtual nodes
                     │
OCI integrations:    VCN networking | Load Balancer / NLB | Block Volume / File Storage | IAM
```

#### b. Basic Versus Enhanced Clusters

| Feature | Basic cluster | Enhanced cluster |
|---|---|---|
| Control plane cost | No cluster fee | Per-cluster hourly fee |
| Virtual nodes | No | Yes |
| Workload identity | No | Yes |
| Cluster add-on management | Limited | Yes |
| Financially backed SLA | No | Yes |

#### c. Creation Options

- **Quick create:** OCI builds the VCN, subnets, and node pool with defaults.
- **Custom create:** use an existing network design (recommended for production).
- **Terraform / Resource Manager:** repeatable, reviewable clusters.

**Bottom Line:** OKE gives you managed Kubernetes on OCI; enhanced clusters add virtual nodes, workload identity, and add-on management.

### Q14. Compare managed nodes and virtual nodes.

**Answer:**

OKE supports several **worker node** types. The choice trades control for operational effort.

#### a. Comparison

| Aspect | Managed nodes | Virtual nodes | Self-managed nodes |
|---|---|---|---|
| Infrastructure | Compute instances in your tenancy | Serverless capacity managed by OCI | Instances you build and register |
| Control | Choose shape, image, and DaemonSets | Limited node-level control | Full control |
| Patching and scaling | You (node pool updates, autoscaler) | OCI | You |
| Billing | Per instance | Per pod resources | Per instance |
| Cluster type | Basic or enhanced | Enhanced only | Enhanced only |

#### b. Virtual Node Limitations

Virtual nodes don't support some node-level features, such as DaemonSets, privileged containers, and host networking. Check the current restrictions before migrating workloads.

#### c. Choosing

- **Managed nodes:** most production workloads, GPU or special shapes, DaemonSet-based agents.
- **Virtual nodes:** spiky or simple stateless workloads where you do not want to manage nodes.
- **Self-managed nodes:** custom images or specialized configurations.

**Bottom Line:** Managed nodes give control, virtual nodes remove node operations, and self-managed nodes allow full customization.

### Q15. Compare flannel overlay and VCN-native pod networking.

**Answer:**

OKE offers two **CNI plugins** that determine how pods get IP addresses and how pod traffic appears in the VCN.

#### a. Comparison

| Aspect | Flannel overlay | VCN-native pod networking |
|---|---|---|
| Pod IP source | Separate overlay CIDR | VCN subnet IP addresses |
| Visibility in VCN | Pods hidden behind node IPs | Pods are first-class VCN endpoints |
| Security | Kubernetes NetworkPolicy (with Calico) | NSGs and security lists on pod VNICs |
| Performance | Encapsulation overhead | Native VCN performance |
| IP consumption | Low | High—every pod uses a VCN IP |
| Required for | — | Virtual nodes |

#### b. Subnet Sizing for VCN-Native

Each node reserves IPs for its maximum number of pods. A pod subnet that is too small causes pods to remain `Pending` with IP allocation errors, so size pod subnets generously (for example, a `/19` or larger for big clusters).

**Bottom Line:** Flannel conserves IPs; VCN-native networking gives pods real VCN addresses with NSG control and native performance.

### Q16. How do you connect `kubectl` to an OKE cluster?

**Answer:**

Generate a **kubeconfig** with the OCI CLI. Authentication uses short-lived tokens issued from your **OCI IAM** identity, and Kubernetes **RBAC** decides what you can do.

#### a. Create the Kubeconfig

```bash
oci ce cluster create-kubeconfig \
  --cluster-id <cluster-ocid> \
  --file $HOME/.kube/config \
  --region us-ashburn-1 \
  --token-version 2.0.0 \
  --kube-endpoint PRIVATE_ENDPOINT

kubectl get nodes
```

For a private API endpoint, connect through OCI Bastion port forwarding, a VPN, or a jump host in the VCN.

#### b. Authorization With RBAC

```bash
# OKE maps IAM users and groups to Kubernetes subjects by OCID
kubectl create clusterrolebinding dev-view \
  --clusterrole=view --user=<user-ocid>

kubectl create rolebinding orders-editors \
  --clusterrole=edit --group=<group-ocid> --namespace=orders
```

#### c. Two-Layer Model

| Layer | Controls |
|---|---|
| OCI IAM | Who can access the cluster and manage cluster resources |
| Kubernetes RBAC | What the user can do inside the cluster |

**Bottom Line:** The OCI CLI creates the kubeconfig, IAM authenticates you, and Kubernetes RBAC authorizes your actions.

### Q17. What is the difference between a Deployment and a StatefulSet?

**Answer:**

A **Deployment** manages **interchangeable** pods for stateless applications. A **StatefulSet** manages pods that need **stable identity** and **dedicated storage**, such as databases and clustered brokers.

#### a. Comparison

| Aspect | Deployment | StatefulSet |
|---|---|---|
| Pod names | Random suffix (`orders-7d9f8-x2k4p`) | Stable ordinal (`kafka-0`, `kafka-1`) |
| Storage | Shared or none | One PersistentVolumeClaim per pod |
| Startup and scaling order | Parallel | Ordered (0, 1, 2, ...) |
| Network identity | Through a Service | Stable DNS through a headless Service |
| Typical use | REST APIs, web front ends | Databases, Kafka, ZooKeeper |

#### b. StatefulSet With OCI Block Volumes

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: kafka
spec:
  serviceName: kafka-headless
  replicas: 3
  selector:
    matchLabels: {app: kafka}
  template:
    metadata:
      labels: {app: kafka}
    spec:
      containers:
        - name: kafka
          image: <kafka-image>
          volumeMounts:
            - name: data
              mountPath: /var/lib/kafka
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        storageClassName: oci-bv
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 100Gi
```

**Bottom Line:** Use Deployments for stateless services and StatefulSets when pods need stable names and their own persistent volumes.

### Q18. Which Service types are used in OKE?

**Answer:**

A Kubernetes **Service** gives pods a stable endpoint. In OKE, a `LoadBalancer` Service automatically provisions an **OCI Load Balancer** or **Network Load Balancer**.

#### a. Service Types

| Type | Purpose |
|---|---|
| ClusterIP | Internal virtual IP for in-cluster traffic (default) |
| NodePort | Port exposed on every worker node |
| LoadBalancer | Provisions an OCI Load Balancer or Network Load Balancer |
| Ingress (resource) | HTTP host and path routing through an ingress controller |

#### b. LoadBalancer Annotations

```yaml
apiVersion: v1
kind: Service
metadata:
  name: orders
  annotations:
    oci.oraclecloud.com/load-balancer-type: "lb"
    service.beta.kubernetes.io/oci-load-balancer-shape: "flexible"
    service.beta.kubernetes.io/oci-load-balancer-shape-flex-min: "10"
    service.beta.kubernetes.io/oci-load-balancer-shape-flex-max: "100"
    service.beta.kubernetes.io/oci-load-balancer-internal: "true"
spec:
  type: LoadBalancer
  selector:
    app: orders
  ports:
    - port: 443
      targetPort: 8080
```

Use `oci.oraclecloud.com/load-balancer-type: "nlb"` for a layer 4 Network Load Balancer.

#### c. Ingress Options

| Controller | Notes |
|---|---|
| OCI Native Ingress Controller | Uses an OCI Load Balancer directly |
| NGINX Ingress Controller | Popular open-source option, also used by OCI DevOps blue-green and canary strategies |

**Bottom Line:** ClusterIP for internal traffic, LoadBalancer for OCI load balancers, and Ingress for HTTP routing of many services behind one entry point.

### Q19. What are readiness, liveness, and startup probes?

**Answer:**

**Probes** let the kubelet check container health. Each probe answers a different question, and mixing them up causes outages.

#### a. Probe Types

| Probe | Question | Failure result |
|---|---|---|
| Startup | Has the application finished starting? | Other probes wait; container restarts if it never starts |
| Liveness | Is the process stuck? | Container is restarted |
| Readiness | Can it serve traffic right now? | Pod is removed from Service endpoints (no restart) |

#### b. Spring Boot Example

```yaml
startupProbe:
  httpGet: {path: /actuator/health/liveness, port: 8080}
  failureThreshold: 30
  periodSeconds: 5
livenessProbe:
  httpGet: {path: /actuator/health/liveness, port: 8080}
  periodSeconds: 10
readinessProbe:
  httpGet: {path: /actuator/health/readiness, port: 8080}
  periodSeconds: 5
```

Spring Boot Actuator exposes separate liveness and readiness health groups for Kubernetes.

#### c. Pitfalls

1. A liveness probe that checks the **database** restarts every pod when the database is slow—check dependencies only in readiness.
2. No startup probe on slow-starting JVM applications causes restart loops.
3. Aggressive timeouts cause false failures under load.

**Bottom Line:** Startup protects slow boots, liveness restarts stuck processes, and readiness controls traffic—keep their checks separate.

### Q20. What is the difference between resource requests and limits?

**Answer:**

**Requests** tell the scheduler how much CPU and memory a container needs. **Limits** cap what it can use. Together they determine scheduling, stability, and the pod's **QoS class**.

#### a. Behavior

| Resource | Request | Limit exceeded |
|---|---|---|
| CPU | Reserved share used for scheduling | Container is throttled |
| Memory | Reserved amount used for scheduling | Container is OOM-killed |

#### b. Example

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "768Mi"
  limits:
    memory: "768Mi"
```

#### c. QoS Classes

| QoS class | Condition | Eviction priority |
|---|---|---|
| Guaranteed | Requests equal limits for all resources | Last |
| Burstable | Requests set below limits | Middle |
| BestEffort | No requests or limits | First |

#### d. JVM Tip

Set `-XX:MaxRAMPercentage` (for example, 75) so the heap fits inside the memory limit with room for metaspace, threads, and native memory.

**Bottom Line:** Requests drive scheduling, limits enforce caps—size both from measured usage and align JVM memory with the limit.

### Q21. How does autoscaling work in OKE?

**Answer:**

OKE scales at two layers: the **Horizontal Pod Autoscaler (HPA)** changes the number of pods, and the **Cluster Autoscaler** changes the number of nodes.

#### a. Layers

| Autoscaler | Scales | Trigger |
|---|---|---|
| Horizontal Pod Autoscaler | Pod replicas | CPU, memory, or custom metrics |
| Cluster Autoscaler | Worker nodes in node pools | Pending pods or underused nodes |
| Vertical Pod Autoscaler (optional) | Pod requests and limits | Historical usage |

#### b. HPA Example

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: orders
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: orders
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

HPA requires the **Kubernetes Metrics Server**. The Cluster Autoscaler can be installed as an OKE cluster add-on on enhanced clusters.

#### c. Flow

```text
Load rises → HPA adds pods → pods Pending (no capacity) → Cluster Autoscaler adds nodes → pods scheduled
```

**Bottom Line:** HPA scales pods from metrics, the Cluster Autoscaler scales nodes for pending pods, and they are used together.

## 4. OCI Functions

### Q23. What is OCI Functions?

**Answer:**

**OCI Functions** is a managed **functions-as-a-service** platform based on the open-source **Fn Project**. You write a handler, the Fn CLI packages it as a container image in OCIR, and OCI runs, scales, and bills it per invocation.

#### a. Key Concepts

| Concept | Description |
|---|---|
| Function | Code plus `func.yaml`, packaged as a container image |
| Application | Group of functions sharing configuration and subnets |
| Invoke endpoint | HTTPS endpoint used to call the function |
| Memory and timeout | Configured per function; billing uses memory × execution time |
| FDKs | Function Development Kits for Java, Python, Node.js, Go, Ruby, and C# |

#### b. Java Function and `func.yaml`

```java
package com.example.fn;

public class HelloFunction {
    public String handleRequest(String input) {
        String name = (input == null || input.isEmpty()) ? "world" : input;
        return "Hello, " + name + "!";
    }
}
```

```yaml
schema_version: 20180708
name: hello-fn
version: 0.0.1
runtime: java
cmd: com.example.fn.HelloFunction::handleRequest
memory: 256
timeout: 60
```

#### c. Limits to Know

Functions have a configurable **memory** size and a **timeout** with a documented maximum (historically 300 seconds for standard invocations). Check current limits before designing long-running work.

**Bottom Line:** OCI Functions runs short-lived, event-driven code as Fn-based containers without servers to manage.

### Q24. How do you create and deploy a function?

**Answer:**

Set up an Fn **context** for OCI, create an **application** bound to a subnet, then initialize, deploy, and invoke the function.

#### a. Configure the Fn Context

```bash
fn create context oci-iad --provider oracle
fn use context oci-iad
fn update context oracle.compartment-id <compartment-ocid>
fn update context api-url https://functions.us-ashburn-1.oci.oraclecloud.com
fn update context registry iad.ocir.io/<tenancy-namespace>/fn-repo
docker login iad.ocir.io
```

#### b. Create the Application

```bash
oci fn application create --compartment-id <compartment-ocid> \
  --display-name orders-app --subnet-ids '["<private-subnet-ocid>"]'
```

#### c. Build, Deploy, and Invoke

```bash
fn init --runtime java orders-fn
cd orders-fn
fn -v deploy --app orders-app        # builds, pushes to OCIR, registers the function
echo -n 'Alice' | fn invoke orders-app orders-fn
```

#### d. What Happens on Deploy

1. The Fn CLI builds the image with the FDK build image.
2. It pushes the image to OCIR.
3. It creates or updates the function in the application.

**Bottom Line:** Context → application with subnet → `fn init` → `fn deploy` → `fn invoke`.

### Q25. When should you not use OCI Functions?

**Answer:**

Functions excel at **short, event-driven, bursty** work. Other workloads are cheaper, faster, or simpler on containers or VMs.

#### a. Decision Table

| Workload | Better option | Reason |
|---|---|---|
| Runs longer than the function timeout | OKE Job, Container Instances | Execution limit |
| Steady high-volume traffic | OKE or Container Instances | Per-invocation cost and cold starts |
| Long-lived connections (WebSockets, streaming) | OKE | Functions are request-scoped |
| Needs local durable state | OKE StatefulSet or managed storage | Function instances are ephemeral |
| Requires special hardware or OS control | Compute | No host control |
| Ultra-low, consistent latency | Always-on service | Cold starts add latency |

#### b. Good Fits

- Reacting to Object Storage uploads or OCI Events.
- Scheduled or on-demand automation tasks.
- Lightweight API back ends with bursty traffic.
- Data transformation in Service Connector Hub.

**Bottom Line:** Use Functions for short, bursty, event-driven tasks—not for long-running, stateful, or constantly busy workloads.

### Q26. What is a cold start, and how do you reduce it?

**Answer:**

A **cold start** happens when no warm container is available, so the platform must pull the image, start the container, and initialize the runtime before handling the request. Java functions can be especially sensitive because of JVM startup.

#### a. Causes and Mitigations

| Cause | Mitigation |
|---|---|
| Large image | Minimal base images and dependencies |
| JVM startup and class loading | GraalVM native image (`fn init --init-image fnproject/fn-java-native-init`) |
| Heavy initialization per request | Create SDK clients and pools once, outside the handler |
| No warm instances | **Provisioned concurrency** for latency-sensitive functions |
| Network setup to private resources | Reuse connections across warm invocations |

#### b. Initialize Once, Reuse Across Invocations

```java
public class OrdersFunction {
    private final ObjectStorageClient objectStorage;

    public OrdersFunction() {
        var provider = ResourcePrincipalAuthenticationDetailsProvider.builder().build();
        this.objectStorage = ObjectStorageClient.builder().build(provider);  // reused while warm
    }

    public String handleRequest(String input) {
        // use objectStorage here
        return "ok";
    }
}
```

**Bottom Line:** Keep images small, initialize once outside the handler, use native images for Java, and buy provisioned concurrency where latency matters.

### Q27. How does a function access OCI APIs securely?

**Answer:**

Functions use **resource principals**: OCI injects short-lived credentials that identify the function itself. You include the function in a **dynamic group** and grant that group a least-privilege policy.

#### a. Setup

```text
Dynamic group "orders-functions" matching rule:
ALL {resource.type = 'fnfunc', resource.compartment.id = '<compartment-ocid>'}

Policies:
Allow dynamic-group orders-functions to read secret-bundles in compartment App-Security
Allow dynamic-group orders-functions to manage objects in compartment App-Data
  where target.bucket.name = 'order-exports'
```

To target a single function, use `resource.id = '<function-ocid>'` in the matching rule.

#### b. Java SDK Usage

```java
var provider = ResourcePrincipalAuthenticationDetailsProvider.builder().build();
var secrets = SecretsClient.builder().build(provider);
```

#### c. Why Not API Keys?

| Aspect | Resource principal | API key in configuration |
|---|---|---|
| Stored secret | None | Private key must be stored |
| Rotation | Automatic | Manual |
| Scope | Defined by the dynamic group | The user's full permissions |

**Bottom Line:** Dynamic group + least-privilege policy + resource principal provider gives functions secure, keyless access to OCI APIs.

### Q28. How can functions be invoked?

**Answer:**

Functions can be called **directly** or **triggered by OCI services**. The invocation path determines whether the call is synchronous, how errors are retried, and how callers authenticate.

#### a. Invocation Methods

| Method | Style | Typical use |
|---|---|---|
| Fn CLI or OCI CLI | Synchronous | Testing and scripts |
| OCI SDK (`FunctionsInvokeClient`) | Synchronous | Calls from other applications |
| API Gateway | Synchronous HTTP | Public or private REST APIs |
| Events | Asynchronous | React to resource changes, such as an object upload |
| Notifications | Asynchronous | Fan-out from alarms or topics |
| Service Connector Hub | Asynchronous | Transform logs or stream data |

#### b. CLI Example

```bash
oci fn function invoke --function-id <function-ocid> --file "-" --body '{"orderId": "42"}'
```

#### c. Design Notes

1. Synchronous callers must handle timeouts and errors themselves.
2. Asynchronous triggers can retry, so the function must be **idempotent**.
3. Pass a **correlation ID** in the payload or headers for tracing.

**Bottom Line:** Choose synchronous invocation for request-response APIs and event triggers for asynchronous automation, and design for retries.

### Q29. How should functions handle retries?

**Answer:**

Assume every invocation may run **more than once** and may fail partway. Separate **transient** failures (retry) from **permanent** failures (stop and park the work).

#### a. Failure Handling Strategy

| Failure type | Example | Handling |
|---|---|---|
| Transient | Timeout, HTTP 503, throttling (429) | Retry with exponential backoff and jitter |
| Permanent | Validation error, HTTP 400 | Do not retry; record and alert |
| Poison message | Payload that always crashes the handler | Move to a dead-letter queue |

#### b. Bounded Retry (Resilience4j)

```java
RetryConfig config = RetryConfig.custom()
        .maxAttempts(3)
        .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(Duration.ofMillis(200), 2.0))
        .retryExceptions(IOException.class)
        .build();
Retry retry = Retry.of("payments", config);
Supplier<Receipt> call = Retry.decorateSupplier(retry, () -> paymentClient.charge(request));
```

#### c. Rules

1. Make side effects idempotent with event IDs or business keys.
2. Keep total retry time below the function timeout.
3. Send unrecoverable work to **OCI Queue** (or a dead-letter destination) for later analysis.

**Bottom Line:** Retry only transient errors with bounded backoff, make side effects idempotent, and park permanent failures in a dead-letter destination.

## 5. API Gateway

### Q30. What is OCI API Gateway?

**Answer:**

**OCI API Gateway** is a managed service that publishes HTTP APIs in front of back-end services. It centralizes cross-cutting concerns—authentication, authorization, rate limiting, CORS, transformations, and logging—so back ends can focus on business logic.

#### a. Architecture

```text
Clients ──HTTPS──> API Gateway (public or private endpoint, in a subnet)
                     ├── /v1/orders   → HTTP back end (OKE service, private LB)
                     ├── /v1/reports  → OCI Functions back end
                     └── /v1/health   → Stock response
```

#### b. Capabilities

| Capability | Examples |
|---|---|
| Routing | Path prefixes, path parameters, HTTP methods |
| Back-end types | HTTP, OCI Functions, stock responses, dynamic routing |
| Security | JWT validation, authorizer functions, mTLS, route-level authorization |
| Traffic control | Rate limiting, usage plans and quotas |
| Transformation | Header and query parameter manipulation |
| Observability | Access and execution logs, Monitoring metrics |

#### c. Gateway Types

| Type | Reachable from |
|---|---|
| Public | Internet (placed in a public subnet) |
| Private | Only within the VCN or connected networks |

**Bottom Line:** API Gateway is the managed front door for HTTP APIs, handling security and traffic policies before requests reach your services.

### Q31. What is an API deployment specification?

**Answer:**

An **API deployment** publishes a set of routes on a gateway under a **path prefix**. Its **specification** defines request policies, routes, methods, and back ends, and should be version-controlled like code.

#### a. Example Specification (JSON)

```json

    "authentication": {
      "type": "JWT_AUTHENTICATION",
      "tokenHeader": "Authorization",

      "audiences": ["orders-api"],

        "maxCacheDurationInHours": 1
      }
    },
    "rateLimiting": { "rateKey": "CLIENT_IP", "rateInRequestsPerSecond": 50 },
    "cors": { "allowedOrigins": ["https://shop.example.com"], "allowedMethods": ["GET", "POST"] }
  },
  "routes": [
```

### Q32. How does API Gateway authenticate clients?

**Answer:**

API Gateway supports **token validation** for standard identity providers and **custom authorizer functions** for anything else. Authentication proves identity; **authorization** then restricts what each caller can do.

#### a. Options

| Option | How it works | Use when |
|---|---|---|
| JWT validation | Verifies signature, issuer, audience, and expiry against the provider's JWKS | Using OCI IAM identity domains, Okta, Entra ID, or Auth0 |
| Authorizer function | Gateway calls your function with request data; the function returns allow or deny | Custom tokens, API keys, legacy schemes |
| Mutual TLS (mTLS) | Gateway verifies client certificates | Partner or machine-to-machine APIs |

#### b. Authorizer Function Response

```json
{
  "active": true,
  "principal": "partner-42",
  "scope": ["orders.read"],
  "expiresAt": "2026-10-07T12:00:00+00:00",
  "context": { "tenant": "acme" }
}
```

#### c. Flow

```text
Client → API Gateway: validate token (JWT or authorizer)
       → check route scopes ("orders.read")
       → forward request (with identity context) → back end
```

**Bottom Line:** Validate JWTs for standard identity providers, use authorizer functions for custom schemes, and always enforce route-level scopes.

### Q33. How do you apply different limits for different customers?

**Answer:**

**Rate limiting** protects the back end from overall overload. **Usage plans** and **subscribers** apply **per-client** limits and quotas, enabling tiered API products.

#### a. Mechanisms

| Mechanism | Scope | Purpose |
|---|---|---|
| Rate limiting | Deployment, per client IP or total | Protect back ends from bursts |
| Usage plan | Set of entitlements (rate limit and quota) | Define a tier such as Free or Gold |
| Subscriber | A client with client tokens | Associate a consumer with usage plans |

#### b. Example Tiers

| Tier | Rate limit | Monthly quota |
|---|---|---|
| Free | 5 requests per second | 100,000 requests |
| Standard | 50 requests per second | 5 million requests |
| Enterprise | 500 requests per second | Unlimited |

#### c. Client Behavior

Clients that exceed limits receive HTTP **429 Too Many Requests** and should retry with exponential backoff and jitter. Expose remaining quota to customers through documentation or dashboards.

**Bottom Line:** Use rate limiting for protection and usage plans with subscribers for per-customer tiers and quotas.

### Q34. How should APIs be versioned?

**Answer:**

Prefer **backward-compatible** evolution so clients never break. When a breaking change is unavoidable, publish a **new version** and run both versions during a migration period.

#### a. Change Classification

| Change | Breaking? |
|---|---|
| Add an optional field or endpoint | No |
| Add a required request field | Yes |
| Remove or rename a field | Yes |
| Change a field's type or meaning | Yes |

#### b. Versioning Strategies

| Strategy | Example | Notes |
|---|---|---|
| URI path | `/v1/orders`, `/v2/orders` | Simple; maps to separate API Gateway deployments |
| Header | `Accept: application/vnd.shop.v2+json` | Clean URLs; harder to test |
| Query parameter | `/orders?version=2` | Easy but less common |

#### c. Deprecation Process

1. Announce the deprecation and the sunset date.
2. Return `Deprecation` and `Sunset` response headers on the old version.
3. Monitor old-version traffic per client.
4. Retire the old deployment when usage reaches zero or the deadline passes.

**Bottom Line:** Evolve APIs compatibly, version explicitly for breaking changes, and retire old versions with a communicated, measured plan.

## 6. Events, Streaming, Queue, and Notifications

### Q35. Compare the OCI messaging and eventing services.

**Answer:**

OCI offers four complementary services. Choosing correctly depends on **who produces the message**, **how many consumers** need it, and whether **ordering and replay** matter.

#### a. Comparison

| Aspect | Events | Notifications | Streaming | Queue |
|---|---|---|---|---|
| Model | Rules on OCI resource changes | Topic pub/sub fan-out | Partitioned log | Point-to-point work queue |
| Producer | OCI services | Alarms, Events, applications | Applications | Applications |
| Consumers | Functions, Notifications, Streaming | Email, HTTPS, Slack, PagerDuty, SMS, Functions | Consumer groups | Competing workers |
| Ordering | No | No | Per partition | No strict ordering |
| Replay | No | No | Yes, within retention | No |
| Retention | None | None | 24 hours by default, up to 7 days | Configurable |

#### b. Quick Decision

```text
React to OCI resource changes?          → Events
Alert people or fan out to endpoints?   → Notifications
High-volume, ordered, replayable data?  → Streaming
Distribute independent tasks to workers? → Queue
```

**Bottom Line:** Events react to OCI changes, Notifications fan out alerts, Streaming carries ordered replayable data, and Queue distributes work.

---

### Q36. How does ordering work in OCI Streaming?

**Answer:**

A stream is split into **partitions**. Ordering is guaranteed **only within a partition**, and messages with the same **key** always go to the same partition.

#### a. Partitioning

```text
key = order-42 → partition 1: [created] → [paid] → [shipped]   (ordered)
key = order-77 → partition 3: [created] → [cancelled]          (ordered)
No ordering guarantee between partition 1 and partition 3.
```

#### b. Producing With a Key (Kafka API, Java)

```java
Properties props = new Properties();
props.put("bootstrap.servers", "cell-1.streaming.us-ashburn-1.oci.oraclecloud.com:9092");
props.put("security.protocol", "SASL_SSL");
props.put("sasl.mechanism", "PLAIN");
props.put("sasl.jaas.config",
    "org.apache.kafka.common.security.plain.PlainLoginModule required "
  + "username=\"<tenancy-name>/<username>/<stream-pool-ocid>\" password=\"<auth-token>\";");
props.put("key.serializer", StringSerializer.class.getName());
props.put("value.serializer", StringSerializer.class.getName());

try (var producer = new KafkaProducer<String, String>(props)) {
    producer.send(new ProducerRecord<>("orders", order.id(), orderJson));  // same key → same partition
}
```

#### c. Design Notes

1. Choose keys with high cardinality to avoid **hot partitions**.
2. Size partition count from peak throughput, because each partition has fixed throughput limits.
3. Plan partitions up front—the partition count is set when the stream is created.

**Bottom Line:** Use a stable business key so related events land in one partition and stay ordered.

### Q37. What are consumer groups and cursors?

**Answer:**

A **cursor** tells Streaming **where to start reading**. A **consumer group** coordinates multiple consumers so each partition is read by one group member and progress (offsets) is tracked for the group.

#### a. Cursor Types

| Cursor type | Starts reading at |
|---|---|
| `TRIM_HORIZON` | Oldest available message |
| `LATEST` | Only new messages |
| `AT_OFFSET` | A specific offset |
| `AFTER_OFFSET` | Immediately after a specific offset |
| `AT_TIME` | First message at or after a timestamp |
| Group cursor | The group's last committed offset |

#### b. Consumer Groups

```text
Stream "orders" (3 partitions)
Group "billing":  consumer A ← partitions 0, 1 | consumer B ← partition 2
Group "analytics": consumer C ← partitions 0, 1, 2   (independent offsets)
```

- Each group receives **every** message; consumers within a group **share** partitions.
- Adding or removing consumers triggers **rebalancing**.
- Committing offsets after processing provides at-least-once delivery.

#### c. CLI Example

```bash
oci streaming stream cursor create-group-cursor --stream-id <stream-ocid> \
  --group-name billing --type TRIM_HORIZON --commit-on-get true \
  --endpoint <messages-endpoint>
```

**Bottom Line:** Cursors choose the start position, and consumer groups share partitions while tracking committed offsets per group.

### Q38. Can existing Kafka applications use OCI Streaming?

**Answer:**

Yes. OCI Streaming exposes a **Kafka-compatible API**, so most Kafka producers and consumers work by changing **connection and authentication settings**.

#### a. Concept Mapping

| Kafka | OCI Streaming |
|---|---|
| Cluster | Stream pool |
| Topic | Stream |
| Partition | Partition |
| Offset | Offset |
| Consumer group | Group |

#### b. Spring Boot Configuration

**Bottom Line:** Point Kafka clients at the stream pool endpoint with SASL/PLAIN credentials, and verify any advanced Kafka features you rely on.

### Q39. How does OCI Queue deliver messages reliably?

**Answer:**

OCI Queue uses a **visibility timeout** and explicit **deletion** to deliver each message **at least once** to one consumer, with a **dead-letter queue (DLQ)** for messages that keep failing.

#### a. Message Lifecycle

```text
Producer PUT → [visible] → consumer GET → [invisible for visibility timeout]
   ├── processed → consumer DELETE → removed
   └── not deleted in time → [visible again], delivery count +1
          └── delivery count > max deliveries → moved to DLQ
```

#### b. Key Settings

| Setting | Purpose |
|---|---|
| Visibility timeout | How long a received message stays hidden |
| Maximum delivery attempts | Failures allowed before moving to the DLQ |
| Retention period | How long unconsumed messages are kept |
| Dead-letter queue | Holds messages that exceeded maximum deliveries |
| Channels | Partition messages for fair processing across tenants |

#### c. Consumer Loop (Java SDK)

```java
var messages = queueClient.getMessages(GetMessagesRequest.builder()
        .queueId(queueId)
        .limit(10)
        .visibilityInSeconds(60)
        .timeoutInSeconds(20)              // long polling
        .build()).getGetMessages().getMessages();

for (var message : messages) {
    process(message.getContent());         // must be idempotent
    queueClient.deleteMessage(DeleteMessageRequest.builder()
            .queueId(queueId)
            .messageReceipt(message.getReceipt())
            .build());
}
```

The client must use the queue's **messages endpoint**. For long-running work, extend visibility before it expires.

**Bottom Line:** Receive, process idempotently, and delete; undeleted messages reappear, and repeated failures go to the DLQ.

### Q40. When should you choose Streaming or Queue?

**Answer:**

Both decouple producers from consumers, but they solve different problems. **Streaming** is an ordered, replayable **log**; **Queue** is a **work distribution** mechanism.

#### a. Decision Table

| Requirement | Choose |
|---|---|
| Ordered processing per entity | Streaming |
| Replay past events (reprocessing, new consumers) | Streaming |
| Several independent consumer groups reading the same data | Streaming |
| Kafka API compatibility | Streaming |
| Each task processed by exactly one worker | Queue |
| Per-message acknowledgement and retry | Queue |
| Built-in dead-letter handling | Queue |
| Scale workers with backlog size | Queue |

#### b. Examples

| Scenario | Service |
|---|---|
| Clickstream or IoT telemetry pipeline | Streaming |
| Order events consumed by billing and analytics | Streaming |
| Image resizing jobs | Queue |
| Sending emails for each order | Queue |

**Bottom Line:** Streaming for ordered, replayable event logs; Queue for distributing independent tasks with per-message acknowledgement.

### Q41. What is Service Connector Hub used for?

**Answer:**

**Service Connector Hub** (called **Connector Hub** in newer documentation) moves data between OCI services **without custom code**. A connector has a **source**, optional **tasks**, and a **target**.

#### a. Components

| Part | Examples |
|---|---|
| Source | Logging, Streaming, Monitoring, Queue |
| Task (optional) | Log filter, Functions transformation |
| Target | Object Storage, Streaming, Functions, Notifications, Monitoring, Logging Analytics |

#### b. Common Patterns

| Pattern | Flow |
|---|---|
| Archive audit logs | Logging (Audit) → Object Storage |
| Alert on specific log entries | Logging → filter → Notifications |
| Enrich or transform logs | Logging → Function → Streaming |
| Ship logs to a SIEM | Logging → Streaming → external consumer |

#### c. Notes

- The Console proposes the IAM policies the connector needs; review and create them.
- Connectors run continuously and scale automatically, replacing polling scripts.

**Bottom Line:** Connector Hub wires OCI data sources to targets declaratively, with optional filtering and function-based transformation.

**Bottom Line:** OCI DevOps provides repositories, build and deployment pipelines, artifacts, and environments for end-to-end CI/CD on OCI.

### Q43. What does a build specification look like?

**Answer:**

The **build specification** (`build_spec.yaml` in the repository root by default) defines the managed build stage: environment variables, Vault secrets, commands, and output artifacts.

#### a. Example

```yaml
version: 0.1
component: build
timeoutInSeconds: 1200
shell: bash
env:
  variables:
    MAVEN_OPTS: "-Xmx1g"
  vaultVariables:
    SONAR_TOKEN: "<vault-secret-ocid>"
  exportedVariables:
    - IMAGE_TAG
steps:
  - type: Command
    name: "Build and test"
    command: |
      ./mvnw -B verify
  - type: Command
    name: "Build image"
    command: |
      IMAGE_TAG=$(echo ${OCI_BUILD_RUN_ID} | rev | cut -c 1-7)
      docker build -t orders:${IMAGE_TAG} .
outputArtifacts:
  - name: orders-image
    type: DOCKER_IMAGE
    location: orders:${IMAGE_TAG}
```

#### b. Key Sections

| Section | Purpose |
|---|---|
| `env.variables` | Plain environment variables |
| `env.vaultVariables` | Secrets resolved from Vault at runtime |
| `env.exportedVariables` | Values passed to later stages (for example, the image tag) |
| `steps` | Commands executed in order |
| `outputArtifacts` | Files or images handed to the deliver-artifacts stage |

The deliver-artifacts stage maps `orders-image` to an OCIR repository path, often parameterized with `${IMAGE_TAG}`.

**Bottom Line:** The build specification is version-controlled CI logic: steps, secrets from Vault, exported variables, and output artifacts.

### Q44. Why should pipelines promote immutable artifacts?

**Answer:**

The artifact that passed testing must be **exactly** the artifact that reaches production. Rebuilding for each environment can pull different dependencies or code and invalidates earlier test results.

#### a. Build Once, Promote Many Times

```text
build → orders@sha256:abc… → dev (tests) → staging (tests) → production
                     same digest everywhere; only configuration differs
```

#### b. Practices

| Practice | Benefit |
|---|---|
| Tag images with version and Git SHA | Traceability to source |
| Deploy by digest | Guaranteed identical content |
| Externalize configuration | Same image in every environment |
| Store artifacts in OCIR or Artifact Registry | Central, auditable source of releases |
| Keep the previous release artifact | Fast rollback |

**Bottom Line:** Build once, promote the same immutable artifact everywhere, and change only configuration between environments.

### Q45. Compare rolling, blue-green, and canary deployments.

**Answer:**

Deployment strategies balance **risk**, **speed**, and **cost**. OCI DevOps supports all three for OKE and compute instance groups.

#### a. Comparison

| Strategy | How it works | Rollback | Cost |
|---|---|---|---|
| Rolling | Replace instances gradually | Slower (roll forward or back) | Low |
| Blue-green | Deploy to an idle environment, then switch all traffic | Instant (switch back) | Double capacity during release |
| Canary | Send a small share of traffic to the new version, then increase | Fast (shift traffic back) | Small extra capacity |

#### b. How OCI DevOps Implements Them

| Target | Blue-green | Canary |
|---|---|---|
| OKE | Two namespaces; NGINX ingress switches traffic | NGINX ingress with traffic-shift stages |
| Instance groups | Two backend sets on the load balancer | Load balancer traffic shifting |

#### c. Choosing

- **Rolling:** routine releases with backward-compatible changes.
- **Blue-green:** releases that need instant rollback.
- **Canary:** high-risk releases validated with real traffic and metrics.

**Bottom Line:** Rolling is cheapest, blue-green gives instant rollback, and canary limits blast radius using real traffic.

### Q46. How should database changes be deployed with applications?

**Answer:**

Use the **expand-and-contract** (parallel change) pattern. Each step keeps the database compatible with **both** the old and new application versions, so rolling deployments and rollbacks remain safe.

#### a. Example: Rename `customer_name` to `full_name`

| Phase | Database change | Application |
|---|---|---|
| 1. Expand | `ALTER TABLE customers ADD full_name VARCHAR2(200);` | v1 unchanged |
| 2. Dual write | — | v2 writes both columns, reads `full_name` with fallback |
| 3. Backfill | `UPDATE customers SET full_name = customer_name WHERE full_name IS NULL;` (in batches) | v2 |
| 4. Switch | — | v3 reads and writes only `full_name` |
| 5. Contract | `ALTER TABLE customers DROP COLUMN customer_name;` | v3 |

#### b. Practices

1. Version migrations with **Flyway** or **Liquibase** and run them in the pipeline.
2. Never combine a destructive change with the release that stops using the column.
3. Test rollback of the application against the expanded schema.

**Bottom Line:** Expand the schema first, migrate gradually, and contract only after no running version depends on the old structure.

### Q47. What should automatically stop a production deployment?

**Answer:**

Automated **quality gates** stop a release before or during rollout when evidence shows risk. Each gate should have a clear threshold and an automatic action.

#### a. Gates

| Gate | Example threshold | Action |
|---|---|---|
| Unit and integration tests | Any failure | Stop build |
| Vulnerability scan | Critical CVE in the image | Stop promotion |
| Approval stage | Missing approval | Pause deployment |
| Smoke tests (shell stage) | Health endpoint not 200 | Roll back |
| Error rate | Above baseline plus 1% | Roll back |
| Latency | p95 above the SLO | Roll back |
| Capacity | Pods not ready within the timeout | Roll back |

#### b. In OCI DevOps

- **Approval stages** for human sign-off.
- **Shell** or **Invoke function** stages to run automated checks.
- Stage **rollback policies** to revert automatically on failure.
- Monitoring alarms to signal problems during canary phases.

**Bottom Line:** Gate releases on tests, security, approvals, and live health metrics, and roll back automatically when a gate fails.

## 8. Observability and Security

### Q48. What are the three observability signals on OCI?

**Answer:**

**Metrics**, **logs**, and **traces** answer different questions. Correlating them with a shared **trace or correlation ID** turns three data sources into one investigation.

#### a. Signals and OCI Services

| Signal | Answers | OCI service |
|---|---|---|
| Metrics | Is something wrong, and how much? | Monitoring (alarms, MQL queries) |
| Logs | What exactly happened? | Logging, Logging Analytics |
| Traces | Where is the time spent across services? | Application Performance Monitoring (APM) |

#### b. Instrumenting a Java Service

```bash
java -javaagent:/opt/otel/opentelemetry-javaagent.jar \
     -Dotel.service.name=orders \
     -Dotel.exporter.otlp.endpoint=<apm-otlp-endpoint> \
     -jar app.jar
```

APM accepts OpenTelemetry data and also provides its own Java agent and browser agent.

#### c. Investigation Flow

```text
Alarm (metric) → filter traces by time and service (APM) → open slow span
              → jump to logs with the same trace ID (Logging) → root cause
```

**Bottom Line:** Metrics detect, traces locate, and logs explain—link them with a shared trace ID.

### Q49. What makes a log entry useful?

**Answer:**

A useful log entry is **structured**, **contextual**, and **safe**. It can be searched and correlated, and it never leaks secrets or personal data.

#### a. Example (JSON)

```json
{
  "timestamp": "2026-10-07T10:15:30.123Z",
  "level": "ERROR",
  "service": "orders",
  "version": "1.4.0",
  "environment": "prod",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "event": "payment_failed",
  "orderId": "42",
  "message": "Payment provider timeout after 3 attempts"
}
```

#### b. Adding Correlation in Java (SLF4J MDC)

```java
MDC.put("traceId", traceId);
try {
    log.info("Order created orderId={} amount={}", order.id(), order.amount());
} finally {
    MDC.remove("traceId");
}
```

#### c. Do and Avoid

| Do | Avoid |
|---|---|
| Structured JSON output | Free-form, unparseable text |
| Trace and correlation IDs | Passwords, tokens, card numbers |
| Stable event names | Logging entire request payloads |
| Appropriate levels | DEBUG noise in production |

On OCI, ship logs to **Logging** through the Unified Monitoring Agent, OKE log collection, or the Logging ingestion API.

**Bottom Line:** Log structured, correlated, non-sensitive events that answer "what happened" without exposing data.

### Q50. How should alarms be designed?

**Answer:**

Alarms should fire on **user impact** and lead to **action**. Too many noisy alarms cause alert fatigue, and important ones get ignored.

#### a. Good Alarm Signals

| Signal | Example |
|---|---|
| Error rate | Percentage of 5xx responses above 2% for 5 minutes |
| Latency | p95 latency above the SLO for 10 minutes |
| Saturation | Queue backlog age or consumer lag growing |
| Availability | Ready replicas below the minimum |
| Failures | Failed function invocations above the baseline |

#### b. Monitoring Query Language (MQL) Examples

```text
CpuUtilization[5m]{resourceId = "<instance-ocid>"}.mean() > 80
orders_api_errors[1m].sum() > 10          # custom metric published by the application
```

Applications can publish **custom metrics** with the `PostMetricData` API (custom namespaces cannot start with `oci_`).

#### c. Alarm Hygiene

1. Define severity levels (warning versus critical) and owners.
2. Route through **Notifications** to email, Slack, PagerDuty, or HTTPS endpoints.
3. Include runbook links in the alarm body.
4. Review and tune alarms after every incident.

**Bottom Line:** Alert on symptoms users feel, with clear owners, thresholds, and runbooks.

### Q51. What is the difference between a user group and a dynamic group?

**Answer:**

A **group** contains **people** (IAM users, including federated users). A **dynamic group** contains **OCI resources** selected by matching rules. Policies grant permissions to either one.

#### a. Comparison

| Aspect | Group | Dynamic group |
|---|---|---|
| Members | Users | Instances, functions, pipelines, gateways, and other resources |
| Membership | Added explicitly | Evaluated from matching rules |
| Credentials | Passwords, API keys, auth tokens | Short-lived principal tokens |

#### b. Matching Rule Examples

| Resource | Matching rule |
|---|---|
| Compute instances in a compartment | `ALL {instance.compartment.id = '<compartment-ocid>'}` |
| Functions in a compartment | `ALL {resource.type = 'fnfunc', resource.compartment.id = '<compartment-ocid>'}` |
| DevOps build pipelines | `ALL {resource.type = 'devopsbuildpipeline', resource.compartment.id = '<compartment-ocid>'}` |
| DevOps deployment pipelines | `ALL {resource.type = 'devopsdeploypipeline', resource.compartment.id = '<compartment-ocid>'}` |
| API gateways | `ALL {resource.type = 'ApiGateway', resource.compartment.id = '<compartment-ocid>'}` |

#### c. Policy Example

```text
Allow dynamic-group build-pipelines to manage repos in compartment Shop
Allow dynamic-group deploy-pipelines to manage cluster-family in compartment Shop
```

**Bottom Line:** Groups are for humans; dynamic groups give workloads keyless, rule-based identities.

### Q52. How should secrets be managed in applications and pipelines?

**Answer:**

Secrets belong in **OCI Vault**. Workloads fetch them at runtime using **principals**, so no long-lived credential is stored in code, images, or configuration.

#### a. Options by Platform

| Platform | Mechanism |
|---|---|
| Any application | OCI SDK with an instance principal, resource principal, or workload identity |
| OKE pods | Secrets Store CSI Driver with the OCI provider |
| OCI Functions | SDK with a resource principal |
| OCI DevOps builds | `vaultVariables` in the build specification |

#### b. Mount Vault Secrets in OKE (Secrets Store CSI Driver)

```yaml
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: orders-secrets
spec:
  provider: oci
  parameters:
    secrets: |
      - name: orders-db-password
        stage: CURRENT
    vaultId: <vault-ocid>
    authType: workload
```

#### c. Rules

1. Rotate secrets with new Vault secret versions, and make applications reload them.
2. Never print secrets in logs or build output.
3. Grant `read secret-bundles` only to the workloads that need each secret.

**Bottom Line:** Store secrets in Vault, fetch them with principals at runtime, and rotate them without code changes.

### Q53. How do IAM and network controls complement each other?

**Answer:**

**IAM** answers *who may call this API*. **Network controls** answer *which paths can reach this endpoint*. Neither is sufficient alone—secure designs apply **defense in depth**.

#### a. Layers

| Layer | Controls | OCI features |
|---|---|---|
| Identity | Who can perform OCI API actions | IAM policies, dynamic groups, workload identity |
| Network | Which sources can reach which endpoints | Private subnets, NSGs, service gateway, private endpoints |
| Application | What an authenticated user can do | JWT scopes, roles, data-level checks |
| Data | Protection at rest and in transit | Vault keys, TLS |

#### b. Example: Function Writing to Object Storage

1. **IAM:** dynamic group policy allowing `manage objects` only on bucket `order-exports`.
2. **Network:** function subnet routes Object Storage traffic through a **service gateway**.
3. **Data:** bucket encrypted with a customer-managed Vault key.
4. **Audit:** OCI Audit records every object write.

**Bottom Line:** Combine least-privilege IAM, private network paths, application authorization, and encryption so that one mistake does not expose everything.

## 9. Scenario-Based Questions

### Q54. OKE pods show `ImagePullBackOff`. How do you fix it?

**Answer:**

`ImagePullBackOff` means the kubelet cannot pull the image. The pod **events** usually state the exact reason.

#### a. Diagnose

```bash
kubectl describe pod <pod-name> -n <namespace>
kubectl get secret ocir-secret -n <namespace> -o yaml
```

#### b. Error Mapping

| Event message (typical) | Cause | Fix |
|---|---|---|
| `unauthorized` or `authentication required` | Missing or expired pull secret or auth token | Recreate the secret with a valid token |
| `not found` or `manifest unknown` | Wrong region, namespace, repository, or tag | Correct the image path |
| `i/o timeout` | Nodes cannot reach OCIR | Add NAT or service gateway routes and egress rules |
| `no matching manifest for linux/arm64` | Image architecture differs from nodes | Build a multi-architecture image |

#### c. Fixes

```bash
# Multi-architecture build
docker buildx build --platform linux/amd64,linux/arm64 \
  -t iad.ocir.io/<ns>/shop/orders:1.4.0 --push .
```

Confirm that the pod spec references `imagePullSecrets` in the **same namespace** as the pod.

**Bottom Line:** Read the pod events, then fix credentials, the image path, network egress, or architecture accordingly.

### Q55. A function times out when calling a private database. What do you check?

**Answer:**

A timeout usually means the function **cannot reach** the database or **spends its time on setup**. Check the network path first, then connection handling.

#### a. Checklist

| Layer | Check |
|---|---|
| Subnet | The Functions application uses a subnet that can route to the database |
| Security | NSG and security-list rules allow the listener port (1521 or 1522 for TLS) |
| DNS | The database host name resolves from the function subnet |
| TLS | Wallet or certificate configuration is correct |
| Credentials | The secret is readable through the resource principal policy |
| Timeout | The function timeout exceeds the connection plus query time |

#### b. Fix Connection Handling

```java
public class OrdersFunction {
    private final PoolDataSource pool;          // created once per container

    public OrdersFunction() throws SQLException {
        pool = PoolDataSourceFactory.getPoolDataSource();
        pool.setConnectionFactoryClassName("oracle.jdbc.pool.OracleDataSource");
        pool.setURL(System.getenv("DB_URL"));
        pool.setUser(System.getenv("DB_USER"));
        pool.setPassword(readPasswordFromVault());
        pool.setInitialPoolSize(1);
        pool.setMaxPoolSize(2);
    }
}
```

```bash
fn update function orders-app orders-fn --timeout 120
```

**Bottom Line:** Verify subnet routing, security rules, DNS, and credentials, then reuse a small connection pool across warm invocations.

### Q56. A function creates duplicate orders from repeated events. How do you fix it?

**Answer:**

Event delivery is **at least once**, so duplicates are expected. The fix is to make processing **idempotent**, not to disable retries.

#### a. Deduplication Table

```sql
CREATE TABLE processed_events (
  event_id     VARCHAR2(64) PRIMARY KEY,
  processed_at TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL
);
```

#### b. Process in One Transaction

```java
try (Connection conn = pool.getConnection()) {
    conn.setAutoCommit(false);
    try (PreparedStatement mark = conn.prepareStatement(
            "INSERT INTO processed_events (event_id) VALUES (?)")) {
        mark.setString(1, event.id());
        mark.executeUpdate();                 // fails on duplicates
    }
    orderRepository.create(conn, event);      // business write in the same transaction
    conn.commit();
} catch (SQLIntegrityConstraintViolationException duplicate) {
    log.info("Duplicate event ignored eventId={}", event.id());
}
```

#### c. Why Keep Retries

| Option | Result |
|---|---|
| Disable retries | Lost orders when transient failures occur |
| Keep retries plus idempotency | No lost orders and no duplicates |

**Bottom Line:** Record each event ID in the same transaction as the business write so duplicates become harmless no-ops.

### Q57. Stream consumers reprocess the same messages after every restart. Why?

**Answer:**

The consumer is not **persisting its progress**. On restart it begins from an old position and replays messages it already processed.

#### a. Causes

| Cause | Fix |
|---|---|
| Offsets never committed | Commit after successful processing |
| Crash before commit | Commit more frequently and make processing idempotent |
| Cursor type `TRIM_HORIZON` on every start | Use a **group cursor** |
| New group name on each deployment | Keep a stable group name |
| Processing exceeds the session timeout, causing rebalances | Process smaller batches or tune timeouts |

#### b. Correct Commit Pattern (Kafka API)

```java
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofSeconds(1));
    for (ConsumerRecord<String, String> record : records) {
        processIdempotently(record);
    }
    consumer.commitSync();   // commit only after the batch succeeds
}
```

**Bottom Line:** Use a stable consumer group, commit offsets after processing, and keep processing idempotent for the replays that still occur.

### Q58. A queue backlog is growing and messages are reaching the DLQ. What do you do?

**Answer:**

Determine whether consumers **cannot keep up** or **keep failing**. Scaling consumers helps the first case but makes the second case worse.

#### a. Triage

| Observation | Likely cause | Action |
|---|---|---|
| DLQ messages share a malformed payload | Poison messages | Fix validation in the producer or consumer |
| DLQ messages show downstream timeouts | Dependency outage | Fix the dependency; pause scaling |
| Processing takes longer than the visibility timeout | Messages reappear while still in progress | Increase or extend the visibility timeout |
| No errors, backlog still grows | Not enough consumers | Scale consumers horizontally |

#### b. Recovery

1. Sample DLQ messages and correlate them with logs by message ID.
2. Deploy the fix.
3. Replay DLQ messages in controlled batches through an **idempotent** consumer.
4. Add alarms on backlog age and DLQ depth.

**Bottom Line:** Diagnose poison messages versus dependency failures before scaling, then replay the DLQ safely after the fix.

### Q59. A canary release raises p95 latency by 40% with no new errors. Should it continue?

**Answer:**

No. **Latency is part of the user experience and the SLO**. A canary exists to catch exactly this kind of regression before it reaches everyone.

#### a. Response

1. **Stop promotion** or shift traffic back to the stable version.
2. Compare canary and baseline traces in **APM** for the same endpoints.
3. Check resource behavior: CPU throttling, GC pauses, connection-pool waits.
4. Look for new downstream calls, N+1 queries, or missing caches.
5. Fix, redeploy, and repeat the canary.

#### b. Canary Analysis Example

| Metric | Baseline | Canary | Gate |
|---|---|---|---|
| Error rate | 0.3% | 0.3% | Pass |
| p95 latency | 180 ms | 252 ms | **Fail** (limit is +10%) |
| CPU throttling | 2% | 18% | Investigate |

#### c. Prevention

Add an automated **latency gate** to the deployment pipeline so the rollout stops without manual review.

**Bottom Line:** A canary that fails its latency gate must stop—errors are not the only signal of a bad release.

### Q60. An auth token was committed to a public repository. How do you respond?

**Answer:**

Assume the token is **already compromised**—automated scanners harvest public repositories within minutes. Revoke first, investigate second, and prevent recurrence.

#### a. Incident Timeline

| Time | Action |
|---|---|
| 0–15 minutes | Revoke the token and create a replacement only if needed |
| 15–60 minutes | Review Audit logs for activity by that user |
| Same day | Remove the secret from Git history and rotate dependent credentials |
| Within a week | Move to principals or Vault and add secret scanning |

#### b. Commands

```bash
# Revoke the token
oci iam auth-token delete --user-id <user-ocid> --auth-token-id <token-ocid>

# Review recent activity
oci audit event list --compartment-id <compartment-ocid> \
  --start-time 2026-10-06T00:00:00Z --end-time 2026-10-07T00:00:00Z
```

Use `git filter-repo` or BFG Repo-Cleaner to purge the secret from history, and treat forks and caches as still exposed.

#### c. Prevention

1. Replace tokens with **resource principals** in OCI DevOps.
2. Enable secret scanning and pre-commit hooks (for example, gitleaks).
3. Use dedicated service users with minimal permissions.

**Bottom Line:** Revoke immediately, investigate with Audit, clean the history, and eliminate long-lived tokens from pipelines.
